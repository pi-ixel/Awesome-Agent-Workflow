# ASIS 场景矩阵：按测试目的切分，而不是按维度切分

## 为什么另建一套

`evolution/asis-slim/` 的三套是**同一场景 × 三个维度**：同一个需求、同一份产物，
分别用契约、事实、经济性三把尺子量。它回答了「这个 skill 在某个需求上的质量剖面」，
但没有回答「这个 skill 在不同处境下会不会失效」。

真实使用中，ASIS 的失败不是均匀分布的。它集中在几个特定处境：
需求描述的是还不存在的东西、需求把模块归属说错了、仓库里有一份和代码相反的设计文档、
架构基线根本没提供、需求把目标状态写成了现状。这些处境各自触发 skill 里不同的一段规则，
混在一个场景里打分会互相掩盖——契约分很高不代表边界判定没错，事实分很高不代表没被文档带跑。

所以这一套换了个切法：**一个场景 = 一个测试目的 = 一类失效模式**。六个场景共用同一份
架构基线和同一个代码仓，但各自换掉一个变量，让每个场景的分数只对那一类能力敏感。

## 六个场景

| 场景 | 换掉的变量 | 检验的能力 | 失败说明什么 |
|---|---|---|---|
| S1 基线正例 | 无（输入齐备） | 交付基本面：骨架、编号、锚点、职责边界 | 基本面不稳，后面五套的分数没有解释力 |
| S2 纯新增 | 需求要求的能力当前不存在 | 纯新增分支：证明不存在 + 记录可复用约束 | 只会做既有行为分析，找不到代码就阻塞或编造 |
| S3 模块误归属 | 需求把持久化挂到相邻模块 | 边界唯一来源 | 顺着需求措辞认定归属，架构基线约束形同虚设 |
| S4 文档漂移 | 仓库里有一份与代码相反的设计说明 | 规格漂移：以代码为准还是抄文档 | 把现成文档当事实来源，下游继承错误前提 |
| S5 前置缺失 | 架构基线文件不存在 | 硬阻塞：中断而不是推断 | 模型自己找理由把分析做完，交出一份「看起来完整」的文档 |
| S6 目标污染 | 需求把目标状态写成要求 | ASIS 与 TOBE 分离 | 把「应该怎样」写成「现在怎样」 |

S5 与其它五个不同：它不期待产物完整，期待的是**明确的阻塞**。判据从「产物里有什么」
改成「是否点名缺失文件、是否标记阻塞、是否没走替代路径」——产物和最终回复都可以作为
交付载体，因为「阶段 1 就中断」本来就不会产出完整文档。

## 判据怎么防「把对的写法判错」

这一轮最重要的工作不是加指标，而是把判据从「关键词匹配」推到「对工作区的实际检查」，
再逐个修掉真实产物上的误伤。**六个场景在真实产物上跑出的每一条误伤，都变成了 `common.py`
里的一条规则**，因为判据误伤比判据漏判更危险：它会让后续 skill 精简朝着错误的「合规」
方向优化。当前已处理的七类：

| 误伤类型 | 真实例子 | 处理 |
|---|---|---|
| 合法提到不存在的路径 | 「`pkg/mcpserver/` 已不存在，是陈旧引用」 | 整行出现“不存在/已删除/缺失”时跳过 |
| 转述外部文档里的路径 | 「`docs/review-*.md` 描述的 `pkg/mcpserver/tools.go` 已不存在」 | 行内引用了真实文档且带转述动词 → 整行视为转述 |
| 临时文件豁免外溢 | 「文档说 Save 用临时文件和 rename」把同行的真实路径一起放过 | 豁免只在该路径前后 16 字符内生效 |
| 固定目录标题被当成结论 | `### C6.2 ASIS 阻塞项` 下写「不适用」 | 标题行看下一句，且「无 X 阻塞」整体算否定 |
| 缩写与裸文件名 | `frontend/.../SessionManager.tsx`、`manager.go:114-120` | 通配唯一匹配；裸名按模块目录→全库唯一解析 |
| 假设语气被当成现状 | 「改变返回值形态（如返回副本）会影响序列化」「任何改造都要考虑原子写」 | `如/改为/若改/例如`、`都会影响/改造都要` 整体跳过 |
| 引用 git 历史里的路径 | 「`git show 93176e7` 改动 `pkg/mcpserver/server.go`」 | 行内出现 `git show/log/diff` 或提交号 → 整行视为历史证据 |

场景脚本自身的正则同样按真实产物放宽，这类修正不进 `common.py` 而是留在对应场景里，
因为它们是「同一件事的另一种合法写法」，不是通用规则：

- C8 章附带的 C8.1 覆盖统计表、C8.2 未纳入范围表首列不是 `R<n>`，算进 `c8_coverage`
  分母会把完整追溯矩阵判成覆盖不足（S3 由 70% 修正为 100%）。
- 「实现只在**顶层**判重」「只遍历 `m.Sessions` 顶层」与「根层」同义（S4）。
- 「按 skill 规定该文件是唯一边界来源」是复述规则，不是虚构架构文件内容（S5）。
- 「既有行为需改造」「需求要求的行为当前不存在」都是需求与现状的差距陈述，不必出现
  「差距/不一致」字样（S6）。
- `.context/reviews/` 是平台独立评审工具（reviewer_a/b）的报告落盘位置，runner profile
  明确要求保存，不算「产物目录多余文件」（S1 由 88.9 回满）。
- S2 允许因需求口径缺口写 `部分完成` + 阻塞项；只有把「能力不存在」当阻塞理由才算失效，
  因此判据改为同行共现「阻塞 + 该对象 + 不存在」，而不是「出现阻塞即失败」。

同理，`wrong_claim()` 逐行扫描而不是整篇匹配，并跳过含 `决策输入|TOBE|可选|待确认|是否|建议`
的行——决策点表格不是现状断言；行内自带反证（「直接覆盖」「不写临时文件」「既有原子写实现」）
也整体跳过。

`c7_density` 从「只认文件锚点」放宽为「文件锚点或带结论输出的命令证据」：跑 `go test`、
跑行为探针、查 `git log` 都是 ASIS 最有力的证据形式，只认文件会把一份实测充分的产物判低。

## 每个场景测什么指标

断言不再只问「有没有出现某个词」，而是把产物折算成一组可复现的数值，再对这组数值设阈值。
`assets/lib/common.py` 的 `measure()` 统一计算，结果写进 `NOTES` 行，便于人工复核：

| 指标 | 定义 | 典型阈值 |
|---|---|---|
| `skeleton_rate` | C1–C8 固定章节齐全率 | S1/S2/S3 要求 100% |
| `substantive_rate` | 有实质内容（非占位、非空）的章节比例 | ≥85% |
| `conclusions` / `evidences` | A 编号与 E 编号个数 | ≥6 / ≥5 |
| `traceable_rate` | 结论在正文与映射中至少出现两次的比例 | ≥80% |
| `mapping_rate` | C3 事实表行内同时出现 A 与 E 编号的比例 | ≥60–70% |
| `anchors_valid` / `anchor_rate` | 可定位到真实符号或行号的锚点数与有效率 | ≥5 且 100% |
| `c7_density` | C7 证据表里**可定位**的行占比（文件锚点或带结论输出的命令证据） | ≥60% |
| `c7_file_density` | 其中只靠文件锚点定位的行占比 | 诊断用 |
| `c7_command_density` | 靠命令输出（`go test` / 探针 / `git log`）定位的行占比 | 诊断用 |
| `c8_coverage` | C8 追溯矩阵里带明确覆盖状态的**需求行**占比（不含 C8.1/C8.2 附表） | ≥70% |
| `path_truth` | 引用的仓库路径中真实存在的比例 | 100% |
| `drift_items` | C6 记录的漂移项数 | S4 要求 ≥3 |
| `prose_repeat` / `sentence_dup` | 正文 30-gram 重复覆盖率 / 重复句占比 | 仅作诊断 |
| `meta_mentions` | 重述 skill 自身流程规则的次数 | 仅作诊断 |
| `formal_docs` / `extra_files` | 越界创建的正式说明书 / 额外文件数 | 0 |

`path_truth` 和 `anchor_rate` 是最能区分「查过代码」与「编得像」的两项：路径必须真的存在于
工作区，`file.go#Symbol` 里的符号必须真的出现在该文件里，`file.go:123` 的行号必须落在文件行数内。
两者都不靠关键词匹配，靠的是对工作区的实际检查。

## 怎么用

```bash
# 1. 本地验判据：每个场景一对「合格 / 定向失真」产物，要求 good ≈ 100、bad ≤ 65
.venv/Scripts/python.exe evolution/asis-scenarios/smoke_test.py <opscopilot 仓库路径>

# 2. 建套（首次或改了断言）：草稿 → 隔离校验 → 锁定
.venv/Scripts/python.exe evolution/asis-scenarios/build_suite.py [--rebuild]

# 3. 跑一轮并钉基线
.venv/Scripts/python.exe evolution/asis-scenarios/run_baseline.py [--skill PATH] [--no-pin]
```

`build_suite.py` 会把 `assets/lib/common.py` 和场景脚本一起打进 grader 的 `files`，
平台在 workspace **之外** 物化后执行，模型读不到判据。这是「开卷考试」防护的前提。

`run_baseline.py` 跑 quick 模式（每场景 1 trial），六个场景串行，单 worker。
一轮实测约 2 小时，但极不均匀：S2（纯新增，要检索+举反证）47–60 分钟，S1/S3/S4/S6 约
11–18 分钟，S5 因为阶段 1 就中断只需 1.3 分钟。S2 的 60 分钟这一轮里约 50 分钟是模型自己的
分析时间，不是平台空转。

> **超时口径**：`run_baseline.py` 的 `timeout_seconds` 是「无活动超时」，不是总时长上限。
> 该模型在真实仓库里会跑探针程序、读多个文件，单轮曾出现 30 分钟以上无 ACP 事件的静默期，
> 因此调到 3600s；总时长上限由服务的 `runner_turn_timeout_seconds`（默认 10800s）约束。
> 早期用 1800s 时 S1 出现过误判 timeout，已在本文档记录。

## 与 `asis-slim` 三套的关系

两套不互相替代，回答不同问题：

- **`asis-slim` 三套**：同一处境下的质量剖面（契约 / 事实 / 经济性）。适合评估「精简后
  某一类质量有没有退化」，这是做消融实验的主尺子。
- **`asis-scenarios` 一套六场景**：不同处境下的能力边界。适合评估「精简后是不是把某一类
  判断力删掉了」——比如把「边界必须来自架构文件」的反复强调删掉，S3 和 S5 会立刻掉分，
  而三套剖面里看不出来。

建议的用法是两套一起跑：三套看质量是否守恒，六场景看能力是否有洞。
