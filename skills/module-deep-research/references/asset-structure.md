# 模块认知资产规范

## 1. 目录结构

```text
.sdd/modules/<module>/
  <模块名>模块认知说明书.md
  业务功能/
    业务流程/
    非流程功能点/
  数据模型与状态.md
  约束与风险.md
  研究过程/
    research-state.json
    findings/
      DR-001.json
      DR-002.json
```

`research-state.json` 是任务、问题、阶段、运行时长和 Git 提交覆盖率的唯一状态源，只能由 CLI 修改。Git 提交先以新到旧的顺序进入内部清单，常规认知任务收敛后再由 CLI 分批实例化。`findings/` 保存每轮结构化研究结果。不要另外维护研究队列、提交清单或待解问题 Markdown。

稳定认知文档的模板位于 `<skill-dir>/assets/templates/`：

- `module-overview.md`
- `business-flow.md`
- `non-flow-feature.md`
- `data-model.md`
- `constraints-risks.md`

初始化由 CLI 创建总览、数据模型和约束风险文档。新增业务流程或非流程功能点时，从对应模板复制并替换标题、元信息和正文。不得删除、改名或重排模板规定的章节；需要扩展时只能在对应章节下增加子标题。

## 2. 稳定认知与过程数据

稳定认知包括：

- 模块职责、边界和关键抽象。
- 可验证的运行路径、分支和状态变化。
- 数据、外部契约、约束和风险。
- 失败恢复、并发一致性、配置差异和诊断入口。
- 低置信推断及其适用范围。

过程数据包括任务状态、运行时间、研究摘要、用户补充问题、Git 提交清单、批次游标、提交研究进度和未解问题，只进入 `研究过程/`。不要把研究计划、问题队列、提交清单、搜索记录、失败尝试和内部调度信息写入稳定认知文档。

Git 提交、commit message、历史 diff 和旧版本文件只能用于发现问题、符号和潜在知识。它们不是当前模块事实的证据。提交反查写入稳定认知的结论必须重新落到当前 HEAD 的模块源码；测试、配置和说明材料只能用于交叉验证。

## 3. 文件职责

### 3.1 `<模块名>模块认知说明书.md`

维护模块总览：

1. 模块定位、目标、代码位置和运行形态。
2. 职责、边界和明确非职责。
3. 上下游、外部系统、内部组件关系和 Mermaid 依赖图。
4. 对模块影响较大的设计模式、关键抽象及其 Mermaid 协作图。
5. 同步入口、异步或后台入口和关键日志点。
6. 业务流程与非流程功能地图，链接到每个功能文档。
7. 数据模型、关键状态和生命周期概览。
8. 启动、调度、失败恢复、配置和运行模式等模块级机制。
9. 并发一致性、安全、性能和可观测性等全局质量属性摘要。
10. 高风险区域、扩展点、稳定接口、变更影响和验证重点。
11. 受仓库材料限制而无法证明的稳定认知边界；具体待解问题仍由 CLI 管理。
12. 名词与术语解释。

说明书是模块认知的全景入口，但只对专项内容做摘要和链接，不复制流程、数据和约束文档的全部细节。不罗列所有目录、文件或普通类。

### 3.2 `业务功能/业务流程/`

一个端到端流程一个文件。固定使用“功能概述、业务流程、关键实现细节、异常路径恢复与局部约束、证据索引”五个宽章节。分支、状态、副作用、并发、配置和可观测性等内容按实际需要放入对应章节，不为不相关维度强行创建标题。

### 3.3 `业务功能/非流程功能点/`

一个横切能力或特殊场景一个文件，例如鉴权、审计、去重、缓存、特定环境适配。固定使用“能力概述、实现机制、作用范围与关键细节、失败降级与局部约束、证据索引”五个宽章节。

有完整端到端调用链的能力进入 `业务流程/`；跨多个流程复用或只在特殊条件触发的能力进入 `非流程功能点/`。

### 3.4 `数据模型与状态.md`

固定使用“核心数据结构、数据关系与状态生命周期、持久化与一致性、数据边界与风险、证据索引”五个宽章节。

存在关系型数据模型时优先使用 Mermaid ER 图。不涉及数据库时说明实际数据承载方式，不编造表结构。

### 3.5 `约束与风险.md`

固定使用“约束、风险、变更注意事项、证据索引”四个宽章节。具体约束类别和风险类别使用三级标题按实际内容展开。

有具体运作过程的内容进入功能文件；没有独立流程、但限制模块行为的规则进入本文件。


## 4. 结论与证据

重要结论使用以下状态：

- `FACT`：代码、测试、配置或文档直接证明。
- `INFERRED`：多个信号支持，但没有直接明示。
- `CONFIRMED`：用户或权威材料确认。
- `BLOCKED`：现有材料无法确认且影响理解。

每个重要结论至少包含：

- 结论及适用范围。
- 证据路径、行号或符号。
- 该证据具体证明的内容。

不要只附一组文件路径。证据必须与具体结论相邻，且足以让后续读者快速复核。各专题文档末尾的“证据索引”只用于汇总复核入口，不能替代正文中的相邻证据。

推荐使用统一写法：

```text
- [FACT] 重复请求由数据库唯一键拒绝，适用于创建支付单路径。
  证据：src/payment/repository.py:84，`insert_payment` 捕获唯一键冲突并返回已有记录。
```

`INFERRED` 必须写明推断链和仍缺失的直接证据；`BLOCKED` 必须同时进入 findings 的 `unresolved_issues`。

## 5. 写入规则

- 增量更新已有内容，保留仍然有效的既有判断。
- 相同事实只维护一个权威表述，其他位置使用链接。
- 使用带序号标题，便于跨文档引用。
- 流程、状态机、时序和依赖关系适合画图时优先使用 Mermaid。
- 空章节保持简短的“待研究”说明；完成审查前必须补全或给出不适用依据。
- 不把个别测试场景提升为普遍规则，除非实现或更多证据支持。

## 6. 格式门禁

每次 `submit` 对 `updated_assets` 执行增量门禁：

- 文件必须属于五类文档契约之一。
- 元信息字段必须完整且非空。
- 固定标题必须存在且只能出现一次。
- 文件内容相对任务开始时必须实际变化。

最终 `recheck` 通过前执行全量门禁：

- 三个根文档必须存在。
- 至少存在一个业务流程或非流程功能文档。
- 不得残留“待研究”“待补充”“TODO”“TBD”等占位内容。
- 每个稳定文档至少包含一条带状态的结论和一处“证据：”说明。
- 每个功能文档必须出现在模块说明书的功能索引中。
- CLI 将文档状态、最后更新日期和最后同步提交统一更新为最终值。
