# task-split

## 定位

任务拆分位于设计门禁与代码实现之间。它只负责把已评审设计组织成一条可调度的实现顺序，不生成第二份设计。

严格模式下，详细设计文档是实现设计的唯一事实来源，测试用例设计文档是验证规格的唯一事实来源；轻量模式下实现设计来自 `dev-design.md`（方案与契约变更章节），验证规格来自 `test-design.md` 的用例集（`dev-design.md` 的验收标准章节为需求侧口径）。`tasks-overview.md` 只保存任务边界和指向权威文档的引用。

任务编号 `T1`、`T2`……仅作为调度、状态和遥测标识。新版流程不生成 `T1-xxx.md`、`T2-xxx.md` 等独立任务文件。

## 输入与前置条件（严格模式）

本节适用于严格模式；轻量模式见下一节。

三个输入均为必需：

| 输入 | 默认路径 | 要求 |
|---|---|---|
| 详细设计文档 | `.sdd/{SR}/{AR}/{模块组名}/模块详细设计说明书.md` | 正式成果物，设计状态允许进入 AICoding |
| 测试用例设计文档 | `.sdd/{SR}/{AR}/{模块组名}/模块测试用例设计.md` | 正式成果物，不存在阻断测试缺口 |
| 模块设计门禁结果 | `.sdd/{SR}/{AR}/{模块组名}/.context/模块设计门禁结果.md` | 当前结论为“通过” |

启动后立即校验：

- 三份文件真实存在，且属于同一个 SR、AR 和模块组。
- 门禁结论为“通过”；不通过或阻塞时不得生成可放行的任务计划。
- 详细设计和测试设计不存在会影响任务边界、实现或验证的待确认项。
- 非标准输入或缺少状态字段时，必须由用户明确确认其可作为任务规划依据；在工作流编排中不得以此绕过门禁。

任一条件不满足时停止，返回对应设计、测试设计或门禁阶段处理。任务拆分不得补设计、补测试规格或用推断掩盖上游缺口。

## 轻量模式分支

仅当工作单声明【轻量模式】时适用。

### 输入

| 输入 | 默认路径 | 要求 |
|---|---|---|
| 轻量设计文档 | `.sdd/{SR}/dev-design.md` | 必需。方案与契约变更章节是实现设计的事实来源；验收标准章节是需求侧验收口径 |
| 轻量测试设计 | `.sdd/{SR}/test-design.md` | 必需。用例集与覆盖矩阵是验证规格的事实来源，含「首次可验证阶段」待回填列 |
| 轻量门禁结果 | `.sdd/{SR}/.context/dev-design-gate.md` | 可选。存在时确认结论为通过 |

启动后校验：

- `dev-design.md` 与 `test-design.md` 真实存在且可读；
- 其方案与契约变更足以确定任务边界，用例集足以确定每个任务的验证范围；
- 不存在影响任务边界、实现或验证的待确认项。

**不要**校验《模块详细设计说明书》《模块测试用例设计》《模块设计门禁结果》是否存在，**不要**因其缺失而中止，**不要**引导用户去执行 module-tobe-design / module-test-design / module-design-gate。

`dev-design.md` 缺失或内容不足以支撑拆分时，停止并返回 `dev-design` 阶段补齐；不得自行补设计或用推断掩盖缺口。

### 与严格模式的差异

| | 严格模式 | 轻量模式 |
|---|---|---|
| 实现设计来源 | 《模块详细设计说明书》 | `dev-design.md` 的方案与契约变更章节 |
| 验证规格来源 | 《模块测试用例设计》的用例编号 | `test-design.md` 的用例编号 |
| 输出路径 | `.sdd/{SR}/{AR}/{模块组名}/tasks-overview.md` | `.sdd/{SR}/tasks-overview.md` |
| 阶段回填 | 无 | 把 `test-design.md` 覆盖矩阵的「首次可验证阶段」列回填为责任任务编号，并在任务中圈定用例 ID |

轻量模式下，拆分完成后执行**阶段回填**：把 `test-design.md` 覆盖矩阵的「首次可验证阶段」列回填为责任任务编号（端到端条目保持"端到端（末阶段）"标注），在任务中圈定负责的用例 ID，并写明任务出口标准——本任务新圈定的用例全部通过 + 此前任务的用例回归通过。确保每条验收标准和每个用例都有责任任务。

### 保持不变的部分

除输入来源、输出路径和测试引用形式外，其余全部沿用本 skill 正文：拆分原则、任务计划边界（允许/禁止写入）、Phase 2-4 流程、`overview_template.md` 骨架、`### T{N}` 小节与 `- 状态：` 字段的格式契约、自检清单、以及“不生成 `T[N]-*.md` 独立任务文件”的约束。

## 任务计划边界

### 允许写入

- 一个可独立验收的任务目标；
- 本任务涉及的模块、组件或工程落点范围（文件路径）；
- 测试设计中的测试用例编号（用于定位验证范围）；
- 真实前置任务、串行位置和状态；
- 跨任务补充验证的最终责任任务。

### 禁止写入

- 重新描述接口字段、方法签名、数据结构、错误码或配置值；
- 复制、重画或简化流程图和时序图；
- 改写算法、状态流转、异常处理、兼容、灰度或回退策略；
- 复制测试步骤、输入参数、断言和预期结果；
- 新增详细设计或测试设计中不存在的技术结论；
- 堆砌详细设计中的决策/契约/流程编号引用——任务描述必须让读者不打开权威文档就能看懂做什么，编号只用于开发时定位；
- 生成独立 `T[N]-*.md` 任务文件；
- 把 `tasks-overview.md` 变成未经评审的实现说明书。

开发阶段必须读取权威文档原文。任务中的引用只用于定位关注范围，不能替代完整阅读。

## 拆分原则

1. **以可验证结果为单位**：不按文档章节、代码文件或技术层次机械拆分。
2. **任务以一次可人工 review 的业务改动为单位**：核心业务代码改动的目标区间为 300-500 行——复杂度高取下限，机械性强取上限；测试代码不计入。行数是锚定不是红线，不机械切割。预计合计改动不足一个审查单位时**默认拆为单个任务**：把一个闭环拆成多个都小于审查单位的薄任务是拆分缺陷——每个任务都要独立走完实现、评审、CodeCheck 与交付，薄任务只增加流程开销与回归次数。
3. **保持纵向闭环**：同一任务尽量同时承接必要实现和其核心验证，按可独立验收的业务结果拆分；不要按技术分层拆任务（如"核心函数一个任务、配置一个任务、接线一个任务"）——分层任务既无法独立验收，也把一个审查单位打碎成数份。
4. **按真实依赖排序**：先构造依赖图，再拓扑排序为唯一串行序列；编号必须与执行顺序一致。
5. **降低冲突和返工**：多个候选任务都可开工时，优先安排边界稳定、共享修改区域少的任务。
6. **引用而不转述**：优先使用稳定编号；没有编号的工程落点使用明确章节锚点，不得用二次摘要代替引用。
7. **覆盖完整**：每个需要实现的设计项至少由一个任务承接，每个测试用例有明确责任任务。
8. **存疑不放行**：无法从权威输入确定任务边界或引用时，记录 `Open Questions`；未清零前不得确认计划。

## 具体流程

### Phase 1：校验输入

**严格模式：**

1. 解析 SR、AR 和模块组名称，确认三份输入位于同一模块目录。
2. 定位并完整读取详细设计、测试设计和门禁结果。
3. 确认门禁通过，且三份输入指向同一设计范围。
4. 提取详细设计中的需求点、设计决策、契约、流程、风险编号和工程落点章节锚点。
5. 提取测试设计中的覆盖目标、测试用例编号和测试缺口。

**轻量模式：**

1. 解析 SR，定位 `.sdd/{SR}/dev-design.md` 与 `.sdd/{SR}/test-design.md`。
2. 完整读取两份文档；存在 `.context/dev-design-gate.md` 时一并读取并确认结论为通过。
3. 提取方案、契约变更、影响文件（工程落点）和存疑项。
4. 提取验收标准条目（覆盖目标）与 `test-design.md` 的用例集、覆盖矩阵（验证规格）。
5. 不校验、不读取、不要求三件套文档。

### Phase 2：形成任务边界

1. 按独立可验证结果形成候选任务。
2. 为每个候选任务确定一句话目标、涉及范围、设计引用和测试引用。
3. 检查任务是否过大、过小、跨越不相关目标或缺少核心验证：用审查单位区间（核心业务改动 300-500 行）作锚——过大的重拆；**预计合计改动不足一个区间的合并为单个任务**，不得按技术分层摊成多个薄任务。
4. 分析真实技术依赖和共享修改区域。
5. 对依赖图进行拓扑排序，形成唯一串行顺序并依次编号。
6. 小改动也必须至少生成一个任务条目；不生成独立任务文件。

### Phase 3：检查覆盖和责任关系（内部核对，不写入 tasks-overview）

1. 将每个需要实现的设计决策、契约、流程、风险或工程落点映射到任务，在分析中核对无遗漏；不在 overview 中单独列出映射表。
2. 将测试用例和覆盖目标映射到责任任务。
3. 跨任务用例归属到最早具备完整执行条件的任务。
4. 只有不影响当前任务主要完成状态的补充验证可以待处理；必须记录依赖、原因、最终责任任务和状态。
5. 核心实现或核心验收不得全部待处理到后续任务。

### Phase 4：生成并检查 tasks-overview

1. 读取并复制 `overview_template.md` 骨架，不得从空白文档自由发挥。
2. 写入真实内容并移除全部占位提示。
3. 检查任务数量、标题、编号、顺序、依赖和 CLI `tasks` 列表完全一致。
4. 检查每个任务的描述是否自包含可读（不依赖编号引用才能看懂）。
5. 检查内部覆盖核对无遗漏（Phase 3），Open Questions 为空。
6. 轻量模式：回填 `test-design.md` 覆盖矩阵的「首次可验证阶段」列，并在每个任务中圈定用例 ID 与出口标准。
7. 交给用户检查任务边界、顺序和覆盖关系。向用户说明计划前，必须同步说明以下放行须知，让用户在确认前对每个任务的成本有知情：
   - 每个任务都会完整经历 开发 → 测试 → 语义 Review → CodeCheck 一条龙流程；
   - 建议一个任务对应一个 MR，核心业务改动约 300–500 行（视复杂度浮动）；
   - 拆分过细会让每个任务各付一遍完整流程，任务越多，总开发用时与流程开销成倍增加——把可合并的改动拆成多个薄任务并不省钱。

若处于 `aaw-workflow`，执行 `done` 后必须停在工作流的用户确认状态；确认前不得开始任何 `task-dev`。若单独执行本 skill，则在用户明确确认前只能将成果视为草案。

## 完成条件

只有同时满足以下条件，任务拆分阶段才可放行：

- `tasks-overview.md` 结构完整且通过自检；
- 权威设计和测试规格没有被复制或改写；
- 设计、测试和任务覆盖关系完整；
- 不存在影响实现的存疑；
- 用户已确认任务计划；
- 工作流完成数据与 overview 的任务标题和顺序一致。
