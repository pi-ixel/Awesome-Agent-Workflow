# dev-design

## 定位

本 skill 服务于个人开发者的轻量链路（dev 入口），位于需求确认与任务拆分之间。

它用**一份文档**承担 SR 入口中由 `sr-design`、`ar-clarify`、`module-boundary-design`、`module-tobe-design` 四个阶段分别承担的职责。目标不是写得更少，而是**写得刚好够开发**：下游 `task-split` 要能据此拆出任务，`task-dev` 要能据此写出代码和测试。

唯一成果物：

```text
.sdd/{SR}/dev-design.md
```

不生成 AR 拆分文档、模块边界文档、独立测试用例设计文档或 `.context` 证据文件。

## 分档策略

开始设计前先判定复杂度，选择档位并**明确告知用户当前档位和理由**。

### 判定信号

按以下信号计分，命中任意一条“复杂档信号”即进入完整档：

**极简档信号（全部命中才用极简档）**
- 改动集中在 1-2 个文件或一个明确的函数/组件内；
- 不新增对外接口、不改数据库结构、不改跨模块契约；
- 没有并发、事务、兼容性或数据迁移问题；
- 验收方式直观（跑通某个流程、某个函数返回正确结果）。

**完整档信号（命中任一条）**
- 新增或修改对外接口、API、CLI 参数、配置项、错误码；
- 涉及数据库表结构、数据迁移或存量数据兼容；
- 跨 3 个及以上模块/文件，或引入新的模块边界；
- 涉及并发、事务、状态机、重试、幂等或回滚；
- 引入新的第三方依赖；
- 用户明确要求写清楚，或需求本身存在多个可选方案需要决策。

### 档位差异

| | 极简档 | 完整档 |
|---|---|---|
| 目标篇幅 | 25-40 行 | 80-150 行 |
| 模板 | `references/dev-design-minimal.md` | `references/dev-design-full.md` |
| 必写章节 | 需求、方案、影响文件、验收标准 | 全部章节 |
| 契约变更 | 无则省略 | 必写，逐项列出 |

不要为了凑篇幅注水，也不要为了显得轻量而省略真正需要决策的内容。**档位是起点不是上限**：极简档写着写着发现有契约变更或多方案决策，立即升级到完整档并告知用户。

## ASIS 取证（按需）

**默认不做。** 仅当需求涉及**改造现有代码**时才执行，纯新增功能直接跳过。

需要取证时：

1. 定位需求涉及的现有实现（文件、函数、调用链）；
2. 读取真实代码，确认当前行为、隐含约束、已有测试覆盖；
3. 把结论**直接写进 dev-design.md 的「现状」章节**，不单独产出 `.context` 文件；
4. 取证只写与本次改动相关的部分，不做模块全景分析。

取证结论必须基于真实读到的代码。不得凭文件名、函数名或记忆推测现有行为；无法确认时在「存疑」中记录，不要写成既定事实。

## 具体流程

### Phase 1：澄清需求

1. 读取工作单 `input` 中存在的 `requirement.md` 和 `software_architecture.md`（都是可选，缺失不阻断）。
2. 判断需求是否足以支撑设计。存在以下情况时**逐个向用户提问**，一次问一个，不要一次抛出问题清单：
   - 需求目标或范围边界不清；
   - 存在多个合理实现方案且取舍影响较大；
   - 涉及外部系统、数据格式或兼容性但未说明；
   - 验收标准无法从需求推导。
3. 用户明确表示“你决定”时，选择最简单可行的方案，并在文档中记录该决策及理由。
4. 不要为了减少提问而自行假设关键决策；也不要把可以从代码中查证的问题抛给用户——那些自己去读代码。

### Phase 2：判定档位与取证

1. 按「分档策略」判定档位，告知用户。
2. 判断是否需要 ASIS 取证；需要则按上节执行。
3. 复用已有成果：文档已存在时先完整读取，保留仍然有效的内容和已确认的决策，只更新变化部分。

### Phase 3：写入设计

1. 读取对应档位的模板骨架，不要从空白文档自由发挥。
2. 按模板写入真实内容，移除全部占位提示。
3. 方案章节必须给出**明确选择**，不能停留在“可以 A 也可以 B”。存在备选方案时写明选了哪个、为什么。
4. 契约变更逐项写全：名称、位置、签名或字段、类型、调用方、错误语义、兼容策略。下游 `task-dev` 直接照此实现，含糊即返工。
5. 验收标准必须可执行、可判定。**dev 入口没有独立的测试用例设计文档，验收标准同时承担测试规格的角色**，因此每条验收标准都要写清楚：验证什么、怎么验证、预期结果是什么。
6. 影响面列出实际要改动的文件路径。不确定的路径先去代码里确认，不要写猜测路径。

### Phase 4：自检

按「自检清单」逐项核对，不通过则补齐后再交付。

## 文档边界

### 必须写入

- 需求目标与范围边界（含明确的不做什么）；
- 选定方案及关键决策理由；
- 契约变更（接口、数据结构、配置、错误码、CLI 参数等）；
- 影响的文件或模块；
- 可执行的验收标准；
- 存疑项（如有）。

### 不要写入

- 逐行代码实现或完整代码块（片段示意可以，整段实现不行）；
- 与本次需求无关的模块全景分析；
- 从模板抄来但本次用不上的空章节；
- 未经确认的推测性结论；
- 为凑篇幅的重复表述。

## 自检清单

- [ ] 只生成或更新了 `.sdd/{SR}/dev-design.md`，没有产出其它设计文档。
- [ ] 已明确告知用户当前档位及理由。
- [ ] 方案是明确选择，不存在未决的“可选方案”。
- [ ] 契约变更逐项写全，下游可直接照此实现。
- [ ] 验收标准可执行、可判定，覆盖需求的全部目标。
- [ ] 影响文件路径经过代码确认，不是猜测。
- [ ] 涉及改造现有代码时已做 ASIS 取证，结论基于真实读到的代码。
- [ ] 没有影响实现或验证的存疑项；确实存在的已明确记录并告知用户。
- [ ] 移除了全部模板占位提示。

## 完成条件

- `dev-design.md` 存在且通过自检；
- 关键决策已确认，不存在阻断实现的存疑；
- 用户已确认设计方向，或成果明确标记为草案。
