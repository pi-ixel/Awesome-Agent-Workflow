# {需求名称} · 完整设计

> 档位：完整档（- [ ] 已在 SKILL 中告知用户）

## 1. 需求与范围

### 1.1 目标
要达成的业务/功能目标，可验证。

### 1.2 范围边界
明确做什么、不做什么、延期项。从需求的原始文字取，不加工不扩充。

### 1.3 存疑与待确认
- 影响实现的未决问题逐条列出；需用户拍板的核心决策单列。

## 2. 现状（ASIS，仅涉及改造现有代码时写）

现有实现的行为、关键调用链、隐含约束、已有测试覆盖。基于真实读到的代码写；未取证则整体删除本节。

## 3. 方案

选定的整体方案与理由。存在备选方案时写明权衡与选择结论，不写“待定”。

- 方案：……
- 备选考虑：…… / 未采纳原因

### 3.1 关键流程/状态变化
改动发生处的处理流程或状态流转说明（带图或有序步骤）。

## 4. 契约变更

新增/修改的每一项，下游 task-dev 直接照此实现。逐项写全：名称、位置、签名/字段、类型、调用方、错误语义、兼容策略。没有则不写“无”，直接省略一节。

- 接口 / 函数：……
- 数据结构 / DTO / 配置项：……
- 错误码 / 异常语义：……
- 兼容 / 灰度 / 回退：……

## 5. 数据与存储

涉及库表结构、迁移、缓存或文件存储时的变更；不涉及则省略。

## 6. 影响面

列出实际要修改的文件路径，逐文件一行；每项标注改动性质（新增/修改/删除）。

- `path/to/file.py` —— 修改：……

## 7. 非功能与约束

并发、性能、安全、第三方依赖、平台限制；没有实质约束可省略。

## 8. 验收标准

每条可执行可判定，验证什么、怎么验证、预期结果。本条同时承担测试规格角色：

- [ ] 验收 1
- [ ] 验收 2
- [ ] 验收 3

## 9. 风险与开放项

风险、待观察点、明确不支持的场景。没有则写“无”或省略。
