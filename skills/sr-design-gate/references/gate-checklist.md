# SR Design Gate 检查清单

## 准入维度

逐项判定为 `达标`、`未达标` 或 `不适用`：

| 维度      | 必查内容                                                              |
| ------- | ----------------------------------------------------------------- |
| 输入有效性   | 原始需求、SR 设计、模板结构和历史门禁结果可读；架构基线为可选输入，缺失时按「架构基线缺失降级」处理，不判未达标                    |
| 需求完整性   | 目标、范围、非目标、主流程与异常场景完整；涉及既有行为变更时写明变更前与变更后，不得只描述新方案；原始需求反查通过（见「原始需求反查」）      |
| 范围清晰性   | 范围内、范围外（非目标）、依赖方职责及不承担内容明确                                             |
| 架构一致性   | 模块职责、所有权和依赖方向符合软件架构；架构基线缺失时改判 `降级检查（无架构基线）`，仅核对 SR 设计内部自洽性，并记 P2 欠账 |
| 契约完整性   | 接口、数据、配置、错误、超时、重试、幂等和兼容策略完整；边界收紧或放宽已判定兼容性并明确通知对象               |
| AR 可拆分性 | 每个 AR 有稳定 ID、标题、范围外、价值、模块、依赖、可并行组和交互契约                                  |
| 需求追溯性   | 每项需求有且仅有明确 AR 承接，无遗漏和冲突性重复；范围裁剪（处置为范围外/延期/不实现）均有显式记录（原文引用、处置结论、用户确认来源）           |
| 验收闭环性   | 主流程、异常、接口契约、数据一致性、性能、安全/可靠/可服务六类均有可执行验收判据                                      |
| 决策与风险闭环 | 待确认项、假设以及安全、迁移、回滚和降级风险闭环；升级、降级和混合版本互操作已分析（E2/E3 时适用）                         |
| 变更影响分析  | 按「变更影响分析检查」和「分级一致性」规则检查；分级为 E0/E1 时只核对压缩表，E2/E3 才查六个覆盖面；全新系统无既有行为基线时判不适用并说明依据  |
| 敏感参数安全  | 按 SKILL 的密码学适用性判定执行 `crypto-gate-checklist.md`；判定不涉及时记录检索依据后可判不适用 |
| 文档内部一致性 | 同一事实在文字、表格、时序图、AR 和验收章节中一致；同一事实在多处重复写实质内容时记 P2                                          |

> **全新项目适配**：代码仓为空或本次为全新系统时，「前提与约束」承载技术选型与平台约束（而非现状限制），此时不得因缺少现状描述判「需求完整性」未达标；「变更影响分析」判不适用；「架构一致性」按架构基线缺失降级处理。其余维度照常检查。

## 原始需求反查

以 `.sdd/{SR}/original-requirement.md` 的完整原文为对照基线检查 `SR-design.md` 的
覆盖情况，不得仅依据设计文档中已整理过的需求列表：

1. 按原文中的明确条目、段落和约束逐项检查；
2. 每项明确需求必须在 `SR-design.md` 中找到可定位的设计落点；
3. 该设计落点必须继续关联到 AR，或明确说明由 SR 整体承接；
4. 原文明确要求的可验收行为必须在 SR 验收标准中有对应覆盖；
5. 标记为范围外、延期或不实现的原始需求，必须在需求追溯表中有显式裁剪记录，
   至少包含：原始需求原文引用（或可定位的原文位置）、处置结论、用户确认来源。
   Gate 只认文档内的显式记录——追溯表中无记录、或记录缺少用户确认来源的裁剪，
   一律视为静默省略。

结论规则：

- 明确原始需求没有设计落点：记 P1，结论为 `不通过`；
- 原始需求被裁剪但缺少显式记录（含缺少用户确认来源）：视为静默省略，记 P1，
  结论为 `不通过`；
- 设计内容与原始需求发生实现方向或接口语义冲突：沿用「冲突分级」口径；
- 无法判断某段原文是否属于本次范围，且没有用户确认：列为待确认项，结论为 `阻塞`；
- 原始需求缺失或不可读：结论为 `阻塞`。

## 变更影响分析检查

检查 SR 设计正文（含其变更影响说明，无论以章节还是附表形式呈现）是否完成变更
影响分析。SR 设计侧没有独立的自检交付物；缺失的分析视为设计缺口，整改回
sr-design 补齐：

### 分级口径

- E0：外部可观察行为、结果和资源约束均不变。
- E1：存在兼容性对外变更，既有用法仍受支持。
- E2：仅部分条件下兼容或行为发生变化。
- E3：既有合法用法不再兼容。
- 设计阶段证据不足时标记 `待确认`，不得直接形成确定分级。

### 覆盖面检查

先读取 SR 设计的变更影响分级结论，按分级决定检查深度：

- **判为不适用**（全新系统、无既有行为基线）：本维度判 `不适用`，核对依据是否写明即可，不再检查覆盖面。
- **E0 / E1**：只检查压缩表是否完整——变更对象、变更前、变更后、兼容性判定、影响的调用方、验证方式六列均有实质内容，且分级理由成立。**不得**因未展开下列六个覆盖面而判维度未达标。
- **E2 / E3**：除压缩表外，正文或附录必须展开以下方面，缺失即维度未达标：

- 分析基线：所依据的版本、配置、平台和既有行为基线；逐项写明变更前与变更后。
- 对外变化识别：API/接口签名、参数与返回语义、错误码、输出格式与顺序、
  副作用与状态、调用顺序与幂等、并发与线程安全、CLI/配置/环境变量默认值、
  协议与持久化格式、日志与可观测输出；逐项判断既有正确用法是否仍得到
  语义等价结果，并明确受影响对象和所需适配。
- 上层影响传导：从变更点追踪直接调用方、封装/适配/框架层直至上层功能和
  用户场景；检查资源与性能变化向超时、重试、限流和容量的传导。
- 边界与异常：边界收紧或放宽的兼容性判定；失败语义、部分执行副作用、
  失败后能否重试及状态恢复。
- 资源与性能：先分级为 `较小`/`较大`/`待确认`——`较小` 允许有依据的定性或
  数量级评估；`较大` 或 `待确认` 必须给出变更前后预估、增量或比例、峰值和
  估算模型，并说明变化原因；无论大小均须定义开发阶段的实测计划。
- 兼容与发布：源码/二进制/行为/数据/配置兼容性分别判断；升级、降级、回退和
  混合版本互操作；调用方适配、文档和发布说明更新；灰度观测与回退触发条件。

### 证据规则

- 每项 `无影响`/`不变` 结论必须有可反查的证据（设计章节、现有接口或代码位置、
  调用链检索结果、计划测试用例、估算依据或评审结论）；无证据记 P1。
- 无效证据否决：`改动行数小`、`仅内部重构`、`接口签名未变`、`单元测试通过`
  均不得单独作为无对外影响的证据；以此类证据支撑的结论视同无证据。
- 证据时限：设计阶段证据不得要求代码提交、PR、运行日志或性能实测结果；
  Gate 也不得以缺少实测数据为由判定未达标。
- `无上层影响` 结论必须写明追踪边界、调用方清单和证据；缺失记 P1。
- `待确认` 项必须有责任人和完成时间，并计入待确认问题。

## 分级一致性

按上节分级口径复核以下三条：

1. 分级结论与逐项分析矛盾（如存在已确认的非兼容对外变更却定级 E0/E1）：记 P0。
2. 存在 E3 非兼容变更但未给出审批计划、迁移或回退设计：结论不得为 `通过`。
3. 对外行为、上层影响、资源或性能任一项为 `待确认` 却形成确定的 E0 结论：
   结论不得为 `通过`。

## 关键事实台账

在本轮分析上下文中全量抽取并临时记录。该台账不是独立交付物；仅在触发门禁报告生成规则时，把相关事实、问题和证据写入报告：

- 模块：名称、职责、不承担范围、上下游和依赖方向。
- 接口：调用方、提供方、协议、同步方式、请求响应、错误、超时、重试、幂等和兼容；
  涉及密码算法时同步标记传递敏感参数的接口。
- 数据：对象、字段、类型、必填、默认值、单位、所有者、生命周期和一致性要求。
- 配置：名称、类型、默认值、单位、生效范围和安全约束。
- AR：ID、标题、范围、范围外、模块、前置依赖和交互接口。
- 指标：SLA、超时、性能、并发、可用性、重试次数和降级条件。

## 权威定义和交叉位置

先从当前 SR 设计模板识别承担下列语义职责的章节，再按语义进行交叉核对，不依赖固定章节号。当前模板缺少适用的语义位置时，应记录模板完整性问题。

| 信息类型 | 权威语义位置 | 交叉检查语义位置 |
|---|---|---|
| 需求范围和目标 | 描述需求背景、范围内/外和非目标的章节 | 关键设计决策、需求追溯和验收 |
| 模块边界 | `software_architecture.md`（缺失时降级为仅用 SR 设计的架构增量说明）以及描述模块职责的章节 | 关键设计决策、时序、AR 概览与范围外、架构增量 |
| 对外接口 | 描述对外接口契约的章节 | 时序、异常场景、AR 接口和验收 |
| 数据模型 | 描述数据模型与存储的章节 | 时序说明、AR 接口和验收 |
| 异常语义 | 描述异常与冲突场景的章节 | 对外接口、时序、AR 接口和验收 |
| DFX 指标与验收 | 描述 DFX 要求与验收标准的合并章节 | 反向覆盖需求、接口、数据、时序和 AR |
| AR 身份、范围与依赖 | 描述 AR 概览（含依赖、可并行组、范围外）的章节 | AR 接口契约、需求追溯和时序 |
| AR 交互契约 | 描述 AR 间接口契约的章节 | 对外接口、时序、数据和验收 |
| 配置项 | 附录中描述配置设计的部分 | 外部依赖、异常、DFX 与验收 |
| 前提与约束 | 描述前提与约束的章节 | 关键设计决策的理由部分 |

## 一致性链

逐对象交叉核对以下链路：

1. 主流程时序 ↔ 时序文字说明（分支、状态流转、数据变换）↔ 异常场景 ↔ 验收。
2. 对外接口 ↔ 主流程时序 ↔ AR 间接口 ↔ 数据模型 ↔ 异常场景 ↔ 验收判据。
3. AR 概览（依赖、可并行组、范围外）↔ AR 间接口契约 ↔ 需求追溯。
4. 外部依赖 SLA ↔ DFX 与验收 ↔ 配置 ↔ 变更影响的验证方式。
5. 关键设计决策 ↔ 前提与约束 ↔ 受影响的接口/数据/模块 ↔ 承接 AR：
   每个决策声明的影响面，必须在对应的接口、数据或 AR 章节有落点。
6. 变更影响 ↔ SR 设计正文 ↔ E0-E3 分级结论 ↔ 验收：
   分析中承认的每项对外变化，正文契约、兼容策略和验收章节必须有对应落点；
   分析与正文冲突按冲突分级口径处理。

AR ID、标题、范围外、依赖、接口、字段、类型、错误码、配置、单位、阈值、主流程和关键失败路径必须全量检查。

## 冲突分级

- P0：会造成实现分叉、接口不兼容、数据错误或错误验收，例如字段类型、依赖方向、同步模型、事务或安全策略冲突；密码学场景中密钥跨用途复用、敏感参数明文持久化、密码学用途使用非 CSPRNG 随机源亦属 P0。
- P1：使开发或测试无法确定真实设计，例如默认值、超时、重试、范围、流程步骤、DFX 或验收阈值冲突。
- P2：不影响实现的明确表达差异，可作为非阻断改进项。

存在 P0/P1 时结论必须为 `不通过`。缺少权威决策且无法判断时结论为 `阻塞`。
