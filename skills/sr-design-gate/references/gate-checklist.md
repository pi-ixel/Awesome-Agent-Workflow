# SR Design Gate 检查清单

## 准入维度

逐项判定为 `达标`、`未达标` 或 `不适用`：

| 维度      | 必查内容                                                                  |
| ------- | --------------------------------------------------------------------- |
| 输入有效性   | 原始需求、SR 设计、模板结构和历史门禁结果可读；架构基线为可选输入，缺失时按「架构基线缺失降级」处理，不判未达标             |
| 需求完整性   | 目标、范围、主流程、异常和兼容场景完整；逐项写明变更前与变更后，不得只描述新方案；每项明确原始需求均在 SR 正文中有实质设计落点（见「原始需求反查」）          |
| 范围清晰性   | 范围内、范围外、依赖方职责及不承担内容明确                                                 |
| 架构一致性   | 模块职责、所有权和依赖方向符合软件架构；架构基线缺失时改判 `降级检查（无架构基线）`，仅核对 SR 设计内部自洽性，并记 P2 待补项   |
| 契约完整性   | 外部依赖与对外接口均逐接口定义完整输入输出字段、错误模型、治理属性、协议专属属性、版本和兼容策略；修改接口有差异表；复杂结构有完整示例；复用规范引用可定位且带版本                   |
| 验收闭环性   | 功能、异常、接口、数据、DFX 和关键风险均有可执行验收                                          |
| 关键规格     | 第 6 章关键规格逐项量化（目标值/阈值与测量条件）、依据可溯源、映射 9.2 验收用例；与第 5 章 DFX 手段无重复数值 |
| 决策与风险闭环 | 待确认项以及安全、迁移、回滚和降级风险闭环；升级、降级和混合版本互操作已分析；无未经用户确认的假设（默认假设机制已取消，正文残留假设即不闭环） |
| 敏感参数安全  | 按 SKILL 的密码学适用性判定执行 `crypto-gate-checklist.md`；判定不涉及时记录检索依据后可判不适用     |
| 文档内部一致性 | 同一事实在文字、表格、图、AR 和验收章节中一致                                              |
| 图表变更表达  | 按「图表变更表达检查」核对方案图是否以现状为基线突出变化、使用固定配色与图内图例，并选择正确的增量图或前后对照图              |
| 文档简洁性   | 每段有新增设计事实、无同粒度整段复述、阅读顺序不成环；按「文档简洁性检查」判定，仅结构级问题判未达标                    |

## 原始需求反查

以 `.sdd/{SR}/original-requirement.md` 的完整原文为对照基线检查 `SR-design.md` 的
覆盖情况，不得仅依据设计文档中已整理过的需求列表：

1. 从原文中逐项抽取明确的功能、约束和可验收行为；
2. 背景、动机、示例和参考信息不强制形成设计项，但 Gate 报告必须记录其非需求判定依据；
3. 每项明确需求必须在 `SR-design.md` 的功能、接口、数据、异常、模块设计或验收章节中找到可定位的实质设计落点；
4. 原文明确要求的可验收行为必须在 SR 验收标准中有对应覆盖；
5. 不允许将明确需求标为范围外、延期或不实现；出现此类处置时记 P1，结论为 `不通过`。

结论规则：

- 明确原始需求没有设计落点：记 P1，结论为 `不通过`；
- 明确原始需求被标为范围外、延期或不实现：记 P1，结论为 `不通过`；
- 设计内容与原始需求发生实现方向或接口语义冲突：沿用「冲突分级」口径；
- 无法判断某段原文是否属于本次范围，且没有用户确认：列为待确认项，结论为 `阻塞`；
- 原始需求缺失或不可读：结论为 `阻塞`。

## 关键事实台账

在本轮分析上下文中全量抽取并临时记录。该台账不是独立交付物；仅在触发门禁报告生成规则时，把相关事实、问题和证据写入报告：

- 模块：名称、职责、不承担范围、上下游和依赖方向。
- 接口：调用方、提供方、协议、同步方式、请求响应、错误、超时、重试、幂等和兼容；
  涉及密码算法时同步标记传递敏感参数的接口。
- 数据：对象、字段、类型、必填、默认值、单位、所有者、生命周期和一致性要求。
- 状态：状态集合、初始状态、触发条件、转换方向、失败和终止状态。
- 配置：名称、类型、默认值、单位、生效范围和安全约束。
- 指标：SLA、超时、性能、并发、可用性、重试次数和降级条件。

## 权威定义和交叉位置

先从当前 SR 设计模板识别承担下列语义职责的章节，再按语义进行交叉核对，不依赖固定章节号。当前模板缺少适用的语义位置时，应记录模板完整性问题。

| 信息类型 | 权威语义位置 | 交叉检查语义位置 |
|---|---|---|
| 需求范围和目标 | 描述需求背景、目标以及范围内/外的章节 | 功能设计和整体验收 |
| 模块边界 | `software_architecture.md`（缺失时降级为仅用 SR 设计的架构章节）、描述功能定位与架构分层的章节以及描述模块划分与职责的章节 | 模块交互和架构变更 |
| 对外接口 | 描述对外接口契约的章节 | 主流程、模块划分、异常和验收 |
| 数据模型 | 描述数据模型和存储的章节 | 对外接口和验收 |
| 异常语义 | 描述异常、冲突和兼容场景的章节 | 对外接口、主场景和验收 |
| DFX 指标 | 描述可靠性、安全性、可服务性和性能的章节 | 外部依赖、配置、风险和验收 |
| 配置项 | 描述可服务性中配置项与开关的章节 | 外部依赖、异常、DFX 和验收 |
| 验收标准 | 描述验收总览和黑盒用例的章节 | 反向覆盖需求、接口、功能和 DFX |

## 一致性链

逐对象交叉核对以下链路：

1. 主流程时序 ↔ 关键步骤说明 ↔ 黑盒验收。
2. 对外接口 ↔ 模块交互 ↔ 数据设计 ↔ 异常场景 ↔ 验收断言。
3. 外部依赖 SLA ↔ DFX ↔ 配置 ↔ 风险处理 ↔ SR 验收标准。

模块、接口、字段、类型、状态、错误码、配置、单位、阈值、主流程和关键失败路径必须全量检查。

### 接口契约完整性判定

对外部依赖和对外接口两部分的各接口逐接口检查，不得抽样：

1. 基本契约包含调用方、提供方、交互类型、接口标识、协议专属属性、契约版本和变更类型；
2. 每个实际使用的请求/输入及响应/输出字段均包含字段路径、位置或结果状态、类型、必填/必返、可空、默认值、约束、业务语义、敏感级别和示例；
3. 错误模型包含错误码/状态、触发条件、错误响应语义、调用方处理、可重试性、幂等影响和部分成功/副作用；
4. 治理属性覆盖认证鉴权、幂等/去重、超时、重试、限流/配额、SLA、熔断/降级和版本兼容性；
5. 修改既有接口时存在目标完整契约和差异表，且兼容性影响与调用方适配明确；
6. 复用既有外部接口时，权威规范引用包含名称、路径/URL、接口标识和版本/修订号，SR 同时摘录本需求实际使用的契约子集；
7. 嵌套对象、数组、联合类型、分页、批量接口或复杂错误响应存在完整请求/响应示例。

任一适用项缺失或仅有接口用途、描述、“关键字段”等概括内容，记 P1 且「契约完整性」未达标。存在多个合理方案但缺少用户确认时列为待确认项，结论为 `阻塞`。只有明确写出“不适用：<可反查依据>”的属性才允许豁免。

## 图表变更表达检查

检查所有表达系统方案的 Mermaid 图是否让读者直接识别目标方案相对现状的变化，而非只
展示模块或流程结构。变化基线为当前代码与现有架构文档；架构基线缺失时依据当前代码和
SR 设计中可核对的现状事实降级检查，不得凭空推断变化状态。

### 适用范围

- 主流程时序图和架构分层图均适用。
- 纯数据统计图或不表达方案变化的辅助图不适用，但必须说明其用途，不得用辅助图替代
  模板要求的方案图。

### 表达规则

1. **聚焦变化**：只展示新增、变更、删除对象及理解这些变化所必需的不变上下文。
   大量罗列与变化无关的节点、参与者或连线，导致变化无法直接识别，判未达标。
2. **独立判定**：节点与连线分别依据基线判为新增、变更、删除或不变。仅相邻连线
   发生变化而自身职责、契约未变的既有节点，应判为不变，不得连带标为变更。
3. **业务文字保持纯净**：业务节点、参与者、消息和连线只写对象或交互本身，不添加
   “新增：”“变更：”“删除：”“不变：”等状态前缀，避免渲染溢出；状态词只出现在图例。
4. **固定色板**：
   - 新增：浅蓝底 `#dbeafe`、蓝色边或线 `#2563eb`；
   - 变更：浅橙底 `#ffedd5`、橙色边或线 `#ea580c`；
   - 删除：浅红底 `#fee2e2`、红色边或线 `#dc2626`，`graph/flowchart` 中节点边框与
     连线均使用虚线；
   - 不变：浅灰底 `#f3f4f6`、灰色边或线 `#6b7280`。
5. **图内图例**：每张适用图都必须包含图内图例，并且只列该图实际使用的状态。
   `graph/flowchart` 使用紧凑的图例 `subgraph`；`sequenceDiagram` 使用短 `Note` 与对应
   颜色的 `rect`。业务图中使用了某种状态却无对应图例，或图例包含未使用状态，均判未达标。
6. **图形语法**：`graph/flowchart` 的业务节点使用 `classDef`/`class`，业务连线使用
   `linkStyle` 独立着色；不得只给节点着色而遗漏连线。`sequenceDiagram` 使用同色 `rect`
   标识连续交互片段；删除交互放在“变更前”图的红色片段中，不把已删除路径画成目标流程。
7. **单图与对照图**：默认使用单张增量图。若删除路径在单图中可能被误认为仍可执行、
   同一对象前后职责无法在一个节点内说清，或新旧流程存在互斥分支，必须改用
   “变更前/变更后”对照图。其他场景不得无意义重复绘制两张结构近似的图。

### 未达标判定

命中以下任一项，该维度即判未达标并阻断通过：

1. 适用的方案图只表达目标结构或流程，无法识别相对现状的变化。
2. 变化状态与代码、架构文档或正文中的变更前后事实不一致。
3. 使用了非固定色板、遗漏节点或连线状态、删除状态未使用虚线，或业务文字携带状态前缀。
4. 缺少图内图例、图例包含未实际使用的状态，或图例颜色与业务图不一致。
5. 应使用前后对照图的复杂变化被塞入单图而产生语义歧义。
6. 图中保留大量无关不变对象，变化重点被系统全景淹没。

## 文档简洁性检查

检查 SR 设计是否以最低阅读成本传递完整设计事实。判定依据是当前 SR 设计模板
「使用说明」中已声明的撰写规则——同一事实只在权威位置写实质内容、其他位置引用
而不复述，以及模板声明为必填的 mermaid 图清单。不依赖固定章节号，随模板演进。

### 有效信息判定

对正文每一段判定：该段是否包含至少一条本文档其他位置未出现过的、可落到具体
对象上的设计事实。具体对象指接口、字段、模块、状态、错误码、配置项、阈值、
AR ID、前置或后置条件。判定只依据当前文档，不得推演下游阶段的执行结果。

判为无效段时，举证必须采用以下两种格式之一：

- `本段无任何可落到具体对象的设计事实`；
- `本段全部事实已在<权威语义位置>出现，本段未新增`。

以下四类为高频无效段，命中即按上述格式举证：

1. 复述图：正文用文字把 mermaid 图的节点或步骤逐条叙述一遍，未新增图上无法
   表达的约束。
2. 元描述：只说明文档自身结构、不含设计事实的句子，例如「本章描述了……」
   「如上所述……」。
3. 万能话：更换需求后依然成立、无具体阈值、对象或行为的表述，例如
   「需保证系统的可靠性和可维护性」。
4. 空占位：保留章节但只写「无」「暂无」「详见后续」，且未说明为何不适用。

### 重复判定

同一事实多处出现时，按「本次出现是否新增本位置特有的设计事实」判定：

- 判为合理引用：换视角、换粒度或换职责的再现。例如权威位置定义接口完整签名，
  模块交互补充调用方向与超时，验收标准补充断言。
- 判为无意义重复：同粒度、同视角的整段搬运，例如同一份字段表在两处各贴一遍、
  同一段异常说明原样出现两处、图上已有步骤被正文逐条复述。

以下位置永不判重复：验收标准、关键规格，以及图后用于补充
图上无法表达约束的必要说明。

本维度不得要求删除「文档内部一致性」和「一致性链」所依赖的交叉出现事实。
两者冲突时以一致性链优先。

### 阅读顺序判定

按以下三项检查，逐项给出可定位的举证：

1. 前向依赖：某节的理解必须先跳到后文才能成立。举证格式
   `<位置 X> 依赖 <位置 Y> 才能理解，Y 在 X 之后`。
2. 未定义先用：专有术语、缩写或内部概念首次出现处既无定义也无引用锚点。
   举证格式 `术语 T 首次出现于 <位置 X>，全文无定义`。
3. 粒度跳变：同一章节内混杂相差两级以上的抽象层，例如业务目标与字段类型
   写在同一节。举证格式 `<位置 X> 同时包含业务级 A 与字段级 B`。

本节三项默认只记 P2，不判维度未达标；前向依赖成环时按下节升级。

### 未达标判定

命中以下任一条即判维度未达标，且必须写明具体位置：

1. 模板中的某个章节（含子节）整体无新增设计事实。
2. 模板声明为必填的 mermaid 图中，任一张的节点或步骤被正文逐条文字复述且
   未新增图上无法表达的约束。
3. 同粒度整段搬运累计 3 处及以上。
4. 前向依赖成环：位置 A 需先读位置 B，位置 B 又需先读位置 A，读者无入口。

以上之外的全部简洁性发现一律记 P2，不阻断通过。

### 发现记录规则

- 结构级发现（上节四条）逐条编号，按「多轮复检」规则逐条闭环。
- P2 零散项在门禁报告的非阻断改进项中按「位置 + 类型 + 举证」列出清单，在问题
  编号台账中合并为一条聚合项，复检时按「已整改 M / N，剩余 K 处保留」整条闭环。
- `summary.p2_findings` 按实际处数计入，聚合项不改变计数口径。

## 冲突分级

- P0：会造成实现分叉、接口不兼容、数据错误或错误验收，例如字段类型、状态转换、依赖方向、同步模型、事务或安全策略冲突；密码学场景中密钥跨用途复用、敏感参数明文持久化、密码学用途使用非 CSPRNG 随机源亦属 P0。
- P1：使开发或测试无法确定真实设计，例如默认值、超时、重试、范围、流程步骤、DFX 或验收阈值冲突。
- P2：不影响实现的明确表达差异，可作为非阻断改进项。

存在 P0/P1 时结论必须为 `不通过`。缺少权威决策且无法判断时结论为 `阻塞`。
