# 模块详细设计门禁结果模板

门禁以模块目录下的正式《模块详细设计说明书.md》和独立《模块测试用例设计.md》为准，结果写入同目录的 `.context/模块设计门禁结果.md`。门禁阶段不得编辑正式说明书、测试设计正文或 `.context/详细设计上下文.md`。

## 设计原则：只输出结论和行动项

本模板只记录评审者和开发者需要看的信息：**门禁结论、阻断问题、整改清单、上游反查结果和遗留问题闭环**。gate 的内部工作过程（执行 todo-list、逐维度达标判定、ASIS 采样记录、严格探索记录、大纲符合性检查、五链摘要、风险专题复核）不落盘到结果文件——这些是 gate 执行检查时的内部步骤，发现的问题直接进入阻断问题或非阻断改进项，不需要逐项记录"我检查了什么、结果是通过"。

这样做的目的：让门禁结果文件聚焦于"有什么问题、怎么改"，而不是用大量"达标/通过"行淹没真正需要关注的阻断项。

## C2. 阻断问题

每个阻断问题必须关联至少一个未达标维度，并写明下一轮重试通过条件。

| 问题编号 | 类型 | 严重级别 | 关联维度 | 关联章节/编号 | 问题描述 | 为什么阻断 AICoding | 返工阶段 | 整改要求 | 下一轮重试通过条件 |
|---|---|---|---|---|---|---|---|---|---|
| G1 | EVIDENCE / UPSTREAM / BOUNDARY / EXECUTION / RISK | P0 / P1 / P2 |  |  |  |  | ASIS / TOBE / 测试设计 / 上游设计对齐 / 模块间交互设计 |  |  |

阻断类型说明：

- `EVIDENCE`：证据不足或不确定性被伪装成事实。
- `UPSTREAM`：模块详设或测试设计与 SR/AR-clarify 已确认的设计决策矛盾，或存在关键性遗漏。
- `BOUNDARY`：边界、职责、交互或防腐化不成立。
- `EXECUTION`：TOBE 不足以支撑后续 AICoding 拆分、测试设计不可执行、验证不可追踪，或正式说明书丢失开发必需信息。
- `RISK`：触发风险没有缓解、验证或回退。
