# 模块详细设计维度化门禁检查清单

本清单是辅助检查，不替代门禁结论。门禁结论以八个准入维度是否达标为准；五链检查用于支撑、解释或反证维度结论。正式《模块详细设计说明书》和独立《模块测试用例设计》必须能支撑后续开发与验证。`.context/详细设计上下文.md` 只用于证据和过程复核，不能弥补正式成果物缺失的开发或验证指导内容。

## 0. 正式成果物与写入职责

- 正式说明书按 9 个一级章节组织：需求背景/当前 AR 描述、外部依赖、整体方案、模块详细方案、对外接口、数据库/表设计、受影响模块与交互、关键契约清单、附录/三方件约束。
- 未涉及章节写明“不涉及，原因”，没有生成大量空表。
- 第 4 章按需求点展开，不能只用一个总表替代正文。
- 每个需求点至少包含需求描述、现状约束摘要、TOBE 设计说明、类/接口/数据结构变化、处理流程、异常回退边界场景、日志可观测性、可测试性与验收口径。
- TOBE 不生成测试用例和 AICoding 任务；测试用例必须来自独立《模块测试用例设计》，任务拆分交由后续 AICoding 流程。
- 正式说明书和测试设计不包含 ASIS 检索过程、证据编号表、TOBE 推导过程、反证记录、门禁采样、追踪矩阵等过程性内容；测试设计自身的覆盖矩阵除外。
- ASIS 阶段只写 `.context/详细设计上下文.md`，TOBE 阶段只写正式说明书和详细设计上下文中的 TOBE 章节，测试设计阶段只写测试设计成果物，Gate 阶段只写 `.context/模块设计门禁结果.md`，不编辑前三者。

## 0.1 维度化门禁建议

每轮门禁必须按维度输出检查结果，并给出可重试的整改建议。

| 维度 | 达标标准 | 未达标时建议 |
|---|---|---|
| 上游完整性 | 模块详设和测试设计与 SR/AR-clarify 已确认的设计决策不冲突，无关键性遗漏 | 回 TOBE 补承接后重试；必要时回 ASIS 或上游确认 |
| 证据充分性 | 需求、ASIS 结论、证据索引足以支撑 TOBE | 回 ASIS 补证据后重试 |
| 边界清晰性 | 模块边界、职责、不承担范围、跨模块关系清楚 | 回 ASIS 或上游架构确认 |
| 决策定稿性 | 影响实现和验证的方案、范围、接口、验收口径均已定稿 | 回 TOBE 补设计后重试 |
| 契约完整性 | 新增/修改的函数、接口、DTO、配置、错误码、路径规则等契约完整 | 回 TOBE 补设计后重试 |
| 工程可执行性 | TOBE 给出工程落点、契约、流程、异常、配置和风险处理，足以后续 AICoding 拆分任务 | 回 TOBE 补设计后重试 |
| 验证闭环性 | 测试设计以最小充分验证集覆盖 P0/P1 设计目标、失败路径和触发风险，并给出输入、前置条件、断言、观察点和建议位置 | 回测试设计补用例；必要时回 TOBE 补可测试性输入或回 ASIS 补测试证据 |
| 风险处置性 | 触发风险有缓解、验证和回退 | 回 TOBE 补设计后重试或上游确认 |

只要任一适用维度未达标，门禁建议不能是 `可进入 AICoding`。若给出 `拆分范围后有限进入 AICoding`，必须在正式说明书和测试设计中明确可进入范围、隔离边界和验证方式。

## 1. 证据链支撑检查

- 需求/AR 能追溯到详细设计上下文中的 ASIS 结论和证据编号。
- ASIS 证据编号能在证据索引中反查。
- ASIS 结论状态在详细设计上下文中保持为事实 / 推断 / 待确认 / 阻塞相关。
- 推断、待确认、低置信度或阻塞相关结论没有被 TOBE 当成事实。
- 关键 TOBE 决策能在详细设计上下文中反查 ASIS 证据。
- 正式说明书用用户可读的现状约束摘要承接关键 ASIS 约束，没有输出内部证据编号或检索过程。
- 纯新增场景下，不要求 ASIS 提供不存在的既有实现证据；但必须有模块边界、新增对象不存在的检索证据、相邻同类实现或不存在相邻实现时可替代的模块惯例证据。
- 已做 ASIS 倾向采样；高风险、跨模块、低置信度、规格漂移或核心链路场景已风险加抽。

## 1.1 上游设计反查

以 `SR-design.md` 和本 AR 的 `AR-clarify.md` 为对照基线，检查模块详设和测试设计是否与上游已确认的设计决策冲突，或存在关键性遗漏。SR 中的状态机图、数据流图等可能只是辅助理解，其约束往往已落实到具体接口、字段或代码中——模块详设用其他形式表达等效约束不构成问题，本检查不要求复刻 SR 的表达形式。

**只判两类问题**：

1. **冲突**：上游明确给出的设计决策、契约口径、行为约束或验收要求，与模块详设的实现方向、接口语义、状态流转或验收口径矛盾。例如：上游规定某个状态只能单向转换，模块详设设计成可双向；上游定义的接口语义是同步，模块详设改成异步。
2. **关键性遗漏**：上游明确要求本模块承担的行为、约束或验收口径，在模块详设中完全没有承接，且无法从已有设计中推导出来。

**不判的情况**：

- SR 画了状态机/数据流图，但模块详设用接口表、流程图或其他形式表达了等效约束——表达载体不同，不是遗漏。
- SR 的某个约束已隐含在模块详设的具体设计里（如 DFX 性能要求体现在接口超时配置中）——属于合理落实，不是丢失。
- 模块详设明确标注某上游内容"不涉及"并给出依据——属于范围裁剪，不是遗漏。

**判定与分级**沿用本清单「冲突分级」口径：冲突按造成实现分叉、接口不兼容、数据错误或错误验收的程度判 P0/P1；关键性遗漏按是否影响实现或验证判 P0/P1。SR-design.md 或 AR-clarify.md 缺失或不可读时结论为 `阻塞`。

## 2. 边界链支撑检查

- 模块边界来自当前工作区 `.sdd/software_architecture.md` 的直接声明。
- 本模块承担和不承担的内容清楚。
- TOBE 没有越界承担其他模块职责。
- 跨模块交互符合模块影响性分析和模块间交互设计。
- 没有引入循环依赖、跨层调用、外部模型穿透、共享状态扩散、旁路写入或隐式耦合。
- 跨边界改动已说明防腐层、DTO/模型翻译、依赖方向和禁止穿透内容。

## 3. 执行链支撑检查

- 每个关键 TOBE 决策落到工程位置。
- 纯新增场景下，TOBE 承接 ASIS 中的模块边界、相邻同类实现或模块惯例，没有脱离现状约束凭空设计。
- 正式说明书自洽可读，不需要阅读详细设计上下文才能理解设计结论。
- 正式说明书没有出现 ASIS 检索过程、证据编号表、TOBE 推导过程、反证记录、门禁采样、追踪矩阵等过程性章节或表格。
- 上文或上游产物中已经明确给出的接口定义、方法/函数签名、入参出参、DTO/字段、JSON/序列化名称、错误码、状态值、Topic、Path、配置项和数据结构，已在正式说明书中原样或结构化等价保留。
- 被触发的包/模块结构、类/接口、业务流程、REST、Kafka/MQ、内部接口、数据库、配置/开关变化均已按需展开。
- 字段、DTO、接口、配置项、事件名、状态值、错误码、topic、path、时间单位和 JSON/序列化名称在权威位置（4.1.4）唯一定义，其他章节通过契约编号引用；引用编号与权威位置定义不冲突。一致性指定义不矛盾，不要求同一实质内容在多处重写。
- TOBE 足以支撑后续 AICoding 流程拆分任务；Gate 不要求 TOBE 内置任务表。
- TOBE 写清具体工程落点、函数/类型/调用点、契约、异常语义、配置和完成判定所需设计信息。
- 新增或修改的函数、接口、DTO、配置、错误码、路径规则等写清名称、所在文件/包、导出性或可见性、签名/字段/类型、调用方、错误语义和兼容策略。
- 影响实现的“建议 / 可选 / 如有需要 / 推荐 / 尽量 / 是否需要 / 待定”已消除，或明确标为非阻断改进项且不影响当前 AICoding 范围。

## 4. 验证链支撑检查

- 测试设计中的覆盖矩阵能从 TOBE 决策/契约/风险追踪到测试用例和断言/观察点；ASIS 证据追踪保留在详细设计上下文。
- 测试设计采用最小充分验证集，优先覆盖 P0/P1 设计目标、关键失败路径和触发风险；关键失败路径不能只写成可选测试。
- 测试设计没有机械枚举测试类型或一设计点一用例导致用例爆炸；可合并目标已合并，P2/低价值用例没有挤占 P0/P1 清晰度。
- 测试用例写清建议位置、前置条件/Fixture/Mock、输入/触发步骤、预期结果、断言方式和自动化方式。
- 主路径、边界输入、失败路径、兼容/回归和触发风险均已覆盖，或明确说明不适用/阻塞原因。
- 测试层级选择合理：单元测试覆盖规则和边界；模块内功能集成测试覆盖同一模块/包内业务流程和多类协作；契约、兼容、数据、配置、观测和风险专项只在 TOBE 触发时补充。
- 测试设计没有替 TOBE 补设计；若自行发明 TOBE 未定义的错误码、字段语义、状态流转或阈值，验证闭环性不通过。
- 不存在必须等全部实现完成后才能验证的关键设计。

## 5. 风险链支撑检查

只检查被触发的风险专题；未触发专题要有不适用说明。

- 架构防腐化风险有防护策略和验证方式。
- 安全风险按普通/增强强度处理。
- 性能风险按普通/增强强度处理。
- 日志可观测性能串联主流程、定位错误路径，并避免海量日志和敏感信息泄露。
- 兼容、迁移、回滚策略可执行。
- 并发、事务、幂等、重试、超时、降级、补偿按需处理。

## 6. 遗留问题闭环

- 上一轮门禁阻断问题、整改清单、复检记录、正式说明书待确认问题、正式说明书阻塞项、测试设计缺口、测试设计阻塞项、ASIS 待确认问题、ASIS 阻塞项和 TOBE 部分完成/阻塞说明已全部读取。
- 每个遗留问题保留原始编号、来源轮次和来源章节，没有用新编号覆盖或掩盖原始问题编号。
- 每个遗留问题都有闭环状态：已关闭 / 转为非阻断 / 仍阻断 / 阻塞。
- 已关闭的问题能反查到正式说明书章节、测试设计章节、详细设计上下文证据/推导记录、ASIS/TOBE 更新记录或外部输入确认。
- 转为非阻断的问题说明了不影响 AICoding 准入的理由、剩余风险和后续跟踪位置。
- 仍阻断或阻塞的问题继续进入本轮阻断问题或阻塞说明，没有被静默移除。
- 存在未逐项复核的遗留问题时，本轮门禁结论不能为通过。

## 6.1 前置问询检查

- 影响模块边界、核心方案、数据/权限/兼容策略、性能目标、验收阈值或任务拆分的待确认项，是否已在 ASIS 或 TOBE 阶段触发问询。
- 如果没有问询条件，成果物是否标记为 `需前置确认` 并阻止相关决策定稿。
- 如果待确认项可能推翻当前设计，不得给出 AICoding 准入通过结论。

## 6.5 冲突分级

上游设计反查和各链检查中发现的冲突或遗漏，按以下口径分级：

- **P0**：会造成实现分叉、接口不兼容、数据错误或错误验收。例如字段类型、状态转换方向、依赖方向、同步模型、事务或安全策略与上游矛盾；上游明确要求的行为在模块详设中完全缺失且无法推导。
- **P1**：使开发或测试无法确定真实设计。例如默认值、超时、重试、范围、流程步骤、DFX 或验收阈值与上游不一致；上游要求的验收口径在测试设计中缺失。
- **P2**：不影响实现的明确表达差异，可作为非阻断改进项。

存在 P0/P1 时，关联维度（上游完整性或对应链维度）判未达标，结论为 `不通过`。缺少权威依据且无法判断时结论为 `阻塞`。

## 6.6 严格探索

门禁要主动探索 TOBE 正确性，不只读表格逐项判定。以下探索动作用于发现维度检查可能遗漏的反例，发现的问题必须进入阻断问题或非阻断改进项：

- **模拟 AICoding 拆分**：从正式说明书抽取工程落点和关键契约，判断是否能在不读取详细设计上下文、不追问用户的情况下拆出编码任务；不能则归类为 `EXECUTION` 阻断。
- **架构反证**：是否可构造出边界腐化或依赖方向错误的反例。
- **替代方案对比**：是否存在更小、更贴合现有架构的方案。
- **主流程追踪**：入口到副作用是否走通。
- **失败路径追踪**：至少覆盖输入异常、外部依赖失败、部分成功或回退场景中的适用项。
- **契约保真追踪**：抽取上文已经明确给出的接口定义或方法签名，核对正式说明书是否保留完整签名、每个入参出参、字段名、JSON 名称、错误码和来源；若只保留自然语言概要，判定执行链不通过。

## 7. 阻断分类

- `EVIDENCE`：证据不足或不确定性被伪装成事实。
- `UPSTREAM`：模块详设或测试设计与 SR/AR-clarify 已确认的设计决策矛盾，或存在关键性遗漏（上游明确要求的行为、约束或验收完全没有承接且无法推导）。表达载体不同或约束已隐含落实到具体设计的不属此类。
- `BOUNDARY`：边界、职责、交互或防腐化不成立。
- `EXECUTION`：TOBE 不足以支撑后续 AICoding 拆分、测试设计不可执行、验证不可追踪，或正式说明书丢失上文已经明确给出的接口契约、方法签名、入参出参、DTO/字段等开发必需信息。
- `RISK`：触发风险没有缓解、验证或回退。

每个阻断问题必须关联至少一个未达标维度，并给出下一轮重试通过条件。
