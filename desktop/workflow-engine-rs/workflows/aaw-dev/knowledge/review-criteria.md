# 设计检查要求

独立检查设计动作的完成质量。输入包括需求、设计候选、设计所附的取证与提问记录及可获取的证据；检查时区分事实、推断和未能确认的内容。

## 检查范围

1. 需求目标、范围和明确不做的事项是否得到覆盖；设计是否作出明确方案选择及理由。
2. 现状摘要、契约变更、影响文件和调用方等是否具体；涉及已有代码的关键结论是否可定位，影响路径是否经过查证。
3. 需求验收标准是否可判定并覆盖目标；是否仍有模板占位、影响实现的存疑，或使下游测试设计与任务拆分无法继续的缺口。
4. 是否存在取证与提问尚未收敛、用户决策未完成或设计方向未确认但没有标为草案等问题。查询本次工作流的问题池和相关取证记录核实历史；没有证据时标记无法确认，不能凭文档猜测。

## 结果契约

返回 `decision`、`report`、`issues` 和 `safe`。`decision` 为 `pass` 或 `revise`；报告和问题说明使用文本，注明证据、影响和处理建议。

- `pass`：必要条件已满足，或宿主允许的草案已明确标记。
- `revise`：问题可以在既有授权和已确认决策范围内修改，此时 `safe` 为 `true`。
- 需求、方案等必须由用户决定时，在当前会话提问并等待答复；不得自动代替用户决策。
- 必要证据、输入或能力不可用时，如实说明并继续查证或与用户确认；无法完成检查时不得虚构结论。

此检查只关注设计动作的完成情况；下游可另设设计和测试之间的一致性门禁。不得将未确认的结果当作通过。
