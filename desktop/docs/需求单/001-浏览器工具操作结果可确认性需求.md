# 1. 引言

## 1.1 目的

明确 AAW 内嵌浏览器 Agent 工具在“操作结果可确认性”上的需求，使 Agent 在多数操作中能直接判断操作是否成功、是否达到预期，仅在确有必要时使用快照或截图辅助确认。本文作为后续功能设计、测试设计和验收评审的基线候选。

## 1.2 范围

适用于 AAW Desktop 内嵌浏览器 Agent 工具（MCP）的结果语义，包括填表、点击、导航、标签、提交、上传、脚本执行等动作的后置事实、变化摘要、可选期望条件以及确认方式文档化。

不包含：最终业务判断、视觉理解、整页语义分析，以及 036、038、040 已立项内容。

## 1.3 定义与缩略语

| 术语       | 含义                                                                    |
| ---------- | ----------------------------------------------------------------------- |
| 执行完成   | 工具调用的脚本或原生命令已被执行，不代表动作产生了预期效果              |
| 后置事实   | 动作完成后由页面或宿主直接给出的客观状态，如填后值、URL、标题、加载状态 |
| 变化摘要   | 用于判断动作是否产生效果的精简线索，如 URL 变化、导航发生、目标移除     |
| 期望条件   | 调用方提供的可选验证条件，如 URL 包含、文本包含、元素存在、元素值相等   |
| 快照       | `browser_snapshot` 返回的页面语义节点集合，存在节点数量截断             |
| A/B/C/D 类 | 本需求对操作确认方式的分层：后置事实、可选期望、变化摘要、必须快照      |

# 2. 总体描述

## 2.1 产品视角

内嵌浏览器已支持 Agent 导航、观察、填表、点击、提交、上传、截图等能力，但工具结果主要表达“执行完成”。Agent 为判断“点对没有”，往往必须追加 `browser_snapshot` 或截图，导致调用轮次增加、上下文膨胀，且快照截断后仍可能无法确认。

本需求在不改变既有安全审批、会话归属、页面代次和快照能力的前提下，优化工具结果语义，使“执行完成”“效果达成”“业务确认”三层信息各归其位。

## 2.2 产品功能概述

- A 类：为常规动作提供后置事实，Agent 直接判断成败。
- B 类：为效果不确定动作提供变化摘要，指导是否需要快照。
- C 类：为高价值动作提供可选期望条件，一次调用完成常见业务验证。
- D 类：文档化必须快照或截图的场景，保留辅助确认能力。

## 2.3 用户特征

| 角色         | 特征与诉求                                                   |
| ------------ | ------------------------------------------------------------ |
| Agent        | 需要低成本、可判读的操作结果，避免盲试和频繁快照             |
| AAW 用户     | 希望 Agent 操作可靠、少绕路、不因误判反复操作真实页面        |
| 桌面端维护者 | 需要结果结构稳定、可测试、可追踪，不能破坏既有安全和性能基线 |

## 2.4 约束

- 不得改变 036 审批统一、040 审批等待化、038 快照分页的既有结论。
- 不得引入全文档高频监听；性能不得劣于 037 整改后的水平。
- 返回 URL 必须与快照一致脱敏；不得返回敏感表单值。
- 只新增返回信息，不改变既有错误码、审批、会话归属、代次和脚本能力限制。

## 2.5 假设与依赖

- 原生导航事件、页面 DOM 与 CDP 可提供足够的后置事实，无需新增页面观察框架。
- Agent 能理解结构化结果并在需要时继续使用快照。
- 可选期望条件依赖有界、可取消的等待机制，复用 040 的等待与取消约束。

## 2.6 需求分配（建议实施顺序）

A 类后置事实 → C 类可选期望条件 → B 类变化摘要 → D 类文档分层。每期均可独立验收，不以后期内容阻塞前期交付。

# 3. 具体需求

## 3.1 功能需求

| 编号  | 需求描述                                                                              | 优先级 | 验收要点                                                                                                  |
| ----- | ------------------------------------------------------------------------------------- | ------ | --------------------------------------------------------------------------------------------------------- |
| FR-01 | 填表返回填后值、焦点状态、禁用与只读状态                                              | 必须   | 填后值与页面实际值一致；只读或禁用导致未生效时可直接区分                                                  |
| FR-02 | 点击返回目标信息、禁用、目标是否消失、是否导航、URL、标题、加载状态、对话框与下载线索 | 必须   | 跳转时返回新页面信息；无效果时返回“未导航、目标仍在、页面未变化”                                          |
| FR-03 | 导航与标签返回提交完成后的 URL、标题与加载状态                                        | 必须   | 返回与最终提交事实一致；未提交时按有界等待给出明确状态                                                    |
| FR-04 | 提交返回是否导航、URL、标题及可用的原生校验信息                                       | 必须   | 原生校验拦截时识别“未提交”；成功跳转时识别新页面                                                          |
| FR-05 | 上传明确返回“已绑定文件到控件，未代表上传完成”及文件名、接受类型                      | 必须   | 不再被理解为上传成功；需要结果时另行取证                                                                  |
| FR-06 | 高价值动作支持可选期望条件，返回是否满足与实际值                                      | 应该   | 满足与不满足均明确；等待有界可取消；未提供条件时行为不变                                                  |
| FR-07 | 效果不确定动作提供变化摘要：URL、标题、导航、目标移除、页面变化、对话框与下载         | 应该   | 有变化与无变化可明确区分；不得依赖全文档高频监听                                                          |
| FR-08 | `browser_capabilities` 与工具描述写清各类确认方式和必须快照的场景                     | 应该   | Agent 不再默认每次追加快照；快照用于布局、复杂组件、画布、反爬与最终业务语义                              |
| FR-09 | 返回机器可读的确认等级与建议动作：`confirmed`、`changed`、`unchanged`、`failed`       | 必须   | `confirmed` 不查快照；`changed` 用快照确认语义；`unchanged` 不算成功、需重新定位或诊断；`failed` 附错误码 |

## 3.1.1 确认决策规则（用户已认可）

| 确认等级  | 返回证据                                   | Agent 动作                                           |
| --------- | ------------------------------------------ | ---------------------------------------------------- |
| confirmed | 后置事实直接证明预期效果，或期望条件已满足 | 不使用快照，直接继续                                 |
| changed   | URL、标题或页面有变化，但变化语义不能确定  | 使用 `browser_snapshot` 确认具体变化                 |
| unchanged | 未导航、目标仍在、页面未变、校验拦截       | 不得当成成功；重新定位或换策略，需要诊断原因时才快照 |
| failed    | 明确错误码或拒绝                           | 按错误码处理，需要现场确认时才快照                   |

以下情况即使返回信息完整也必须辅助观察：布局、样式、遮挡、画布等视觉问题使用截图；复杂组件内部状态、反爬弹窗、多步流程的最终业务语义使用快照；返回证据与 Agent 预期冲突时使用快照诊断；上传等只能证明“绑定”的动作，需要页面或网络证据时再确认。

判断原则：证据充分就不查，证据不足才查，没有证据说明成功时不得当成成功。确认等级只描述客观证据，不替 Agent 做最终业务判断。

## 3.2 性能需求

- 不引入全文档高频 MutationObserver；等待必须有界、可取消。
- 连续操作在 3000 元素页面上不得出现明显卡顿，不劣于当前实现。
- 返回结构保持精简，不返回大段 DOM；变化摘要只包含判读必需字段。

## 3.3 接口需求

- 结果结构只增不改：新增后置事实、变化摘要和期望结果字段，既有字段、错误码和 MCP 调用方式不变。
- 未提供期望条件时，既有调用行为保持不变。
- 返回 URL 与快照一致脱敏，去除用户名、密码、查询串和片段。

## 3.4 设计约束

- 优先使用原生导航事件、CDP 与有界采样获取事实，不新增页面观察框架。
- 审批、人工接管、会话归属、页面代次和脚本能力限制不得改变。
- 未覆盖的安全路径继续拒绝或显式报错，禁止静默降级。

## 3.5 质量属性

| 属性   | 要求                                                             |
| ------ | ---------------------------------------------------------------- |
| 可靠性 | 不把技术执行成功误述为业务成功；未提交、未生效、未上传必须可区分 |
| 安全性 | 审批与隔离不变；敏感信息不进入返回                               |
| 兼容性 | 既有 Agent 不感知新增字段时行为不变                              |
| 可维护 | 每类动作的后置事实可独立测试、独立验收，追踪关系明确             |

# 附录 A：原始需求

## A.1 用户原话

> 我们的浏览器工具调用是不是只有是否完成的反馈给 AI，AI 得通过快照确认操作是否正确是否成功？分析下可不可以优化下，让 AI 在某些操作上可以直接知道操作是否成功是否正确，在某些操作上，让 AI 使用快照辅助确认？

> 这个当成需求做。建立需求单，写清楚原始需求。

## A.2 需求转述

1. 对结果可直接确定的操作，工具在返回中直接给出成功与效果证据，Agent 不必再查快照。
2. 对效果不确定或需要业务判断的操作，工具提供足够的变化线索，Agent 再有针对性地使用快照或截图辅助确认。
3. 优化不得削弱既有的安全审批、会话隔离和性能表现。

# 附录 B：现状证据

| 工具类别   | 代表工具                                                   | 当前返回内容                                            | 能否直接判断成功                   |
| ---------- | ---------------------------------------------------------- | ------------------------------------------------------- | ---------------------------------- |
| 导航与标签 | open、navigate、select、close、back、forward、reload、stop | `Tab`：`committedUrl`、`isLoading`、`canGoBack/Forward` | 部分可以；缺少标题与导航提交完成态 |
| 页面动作   | click、fill、press、scroll                                 | `action`、`requestId`、`result.status="completed"`      | 不能；仅表示脚本已执行             |
| 表单提交   | submit                                                     | `action`、`approvalId`、`result.status="completed"`     | 不能；不知道是否跳转或被校验拦截   |
| 文件上传   | upload                                                     | `status="completed"`、`path`、`nodeId`                  | 不能；实际仅完成“绑定文件到控件”   |
| 脚本执行   | execute_script                                             | 脚本表达式返回值                                        | 取决于脚本本身                     |
| 等待       | wait                                                       | completed / TIMEOUT / CONDITION_MET                     | 只有状态，没有现场信息             |

由此产生的问题：Agent 被迫追加快照或截图；快照截断后仍可能无法确认；“执行成功”与“业务成功”混淆；上传“绑定成功”存在误述风险。

# 附录 C：风险与缓解

| 风险                       | 影响           | 缓解                                             |
| -------------------------- | -------------- | ------------------------------------------------ |
| 动作效果异步，返回过早     | 后置事实不准确 | 有界、可取消的提交等待；未落地时明确返回中间状态 |
| 把技术成功误当业务成功     | Agent 误判流程 | 文档区分执行、效果与业务语义；保留快照确认路径   |
| 返回信息过多               | 上下文膨胀     | 只返回判读必需字段，必要时分层返回               |
| 页面观察引入性能回退       | 再次出现高 CPU | 优先原生导航事件与有界采样，禁止全文档高频监听   |
| 可选期望条件被当成无限等待 | Agent 调用悬挂 | 统一有界等待与取消规则，超时返回实际值           |
