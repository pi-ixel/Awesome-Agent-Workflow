## ADR 023 引擎只管流程，会话归 Desktop

2026-11-09 · 已实施

- **决定**：引擎只保留四件事——推进流程（含持久化与恢复）、核验结果、给每个节点下发需求单（提示词、工作目录、工具清单）、结果不确定时停下来交人工核验或授权重试。Agent 会话的拉起、消息、审批卡、呈现与会话历史全部由 Desktop 承担。两边经一组请求协作：拉起会话、开始一轮、等这一轮结束、停止会话、问题池中继。
- **为什么**：早期引擎和 Desktop 各有一套会话状态与呈现，验收中出现「分不清工作中还是等你回复」「补充消息像卡住」等问题。会话归谁管，呈现和语义就归谁管。
- **边界**：引擎只看信封（身份、状态、需求单），看不到会话内容。Python 脚本节点没有会话，仍由引擎直接执行。

## ADR 024 工作流以插件形态接入 Desktop

2026-11-10 · 已实施

- **决定**：工作流整体是一个 Cordis 插件（`src/plugins/workflow/`）：引擎客户端、节点会话宿主、画布状态、面板 UI 都在插件内，经平台服务与其他插件协作。插件监听会话广播感知平台状态；引擎的「拉起 / 开始一轮 / 等结束」由插件作为宿主应答。
- **§9-1 节点会话进标准会话体系**：节点会话经 `project.sessions.adoptExternalSession` 收养，出现在侧栏、在中央会话区打开，与用户会话同一套审批和历史规则。
- **§9-3 结果提交工具按 Agent 能力选择连接方式**：Agent 声明支持 HTTP 方式的 MCP 就用 HTTP，否则用 stdio（ACP 基线）。一整轮结束都没列出过结果工具，节点以 `RESULT_CHANNEL_UNREACHABLE` 失败，不冒充「等你回复」。不为任何特定 Agent 写死规则。

## ADR 025 流程阶段字段；节点记录本（延后）

2026-11-12 · 阶段字段已实施，记录本延后

- **阶段字段**：定义顶层可选 `stages`（有序 `{id, label}`），`phase.stage` 引用它；引用不存在的阶段则定义加载失败（`INVALID_PHASE_STAGE`）。只用于画布分带，不参与调度与恢复。没有 `stages` 时整层画布一个条带；未标注的 phase 归入「其他」。
- **节点记录本（设计已定，未实现）**：结果通道加一个自由格式工具（暂名 `update_workflow_notes`），Agent 每次提交整份清单，条目 `{text, status: todo|doing|done}`，写什么由 Agent 决定。提交结果时若还有未完成条目只提醒、不拒绝；节点结束时引擎把未完成条目封存为「节点已结束」。记录本存入运行记录，画布显示分段进度和当前条目。实现前，界面不得用定义里的静态步骤文案冒充进度。
- **未决**：条目是否需要「跳过」状态；封存时是否区分 Agent 主动收尾与系统代封。

## ADR 026 「等你回复」由引擎标记

2026-11-12 · 已实施

- **决定**：节点一轮结束、结果还没交时，引擎在运行记录上标记该节点「在等用户回复」（`action_awaiting_input`），新一轮开始即清除。面板卡片、横幅和侧栏都读这个标记显示「等你回复」。
- **为什么**：只有引擎知道「这一轮结束了且没交结果」；Desktop 自己猜会把「Agent 在干活」和「在等你」混在一起。

## ADR 027 侧栏按运行分组节点会话

2026-11-12 · 已实施

- **决定**：project 插件提供通用的会话分组扩展点（`registerSessionGroups`），只负责存放与渲染，不理解分组含义；工作流插件把一次运行的节点会话发布为一组（数据来自引擎 `session-links`）。
- **呈现规则**：进行中和等你回复的运行固定排在最前；已结束的运行占它最近一条会话的位置，默认收起。运行进行中时，节点都已做完的会话收进组内默认折叠的「已完成」。分组行可直接打开 AAW 面板并切到该运行。
- **限制**：引擎只返回当前项目的运行，其他项目的节点会话仍平铺。

## ADR 028 界面重新加载后节点续跑

2026-11-12 · 已实施

- **问题**：引擎进程在 WebView 重载后继续存活，但节点会话的连接与「这一轮何时结束」的状态在 WebView 里，随重载消失。引擎会一直等一个不会再来的信号；普通会话流程重新打开该会话时也不带结果工具。
- **决定**：
  - Desktop 的节点会话宿主就绪后向引擎宣告上线（`host-reset`）。引擎把旧宿主的挂起请求一律以 `HOST_RESET` 结束。
  - 正在跑的 Agent 节点用原会话 id、原结果通道经新宿主重新打开会话，发一轮续跑提示：已完成就直接提交，否则继续。中断前已提交的结果直接收尾。同一轮最多续跑 5 次。
  - 收养会话时，若同一会话已被普通流程打开，由收养方接管并关闭普通连接，避免两条连接驱动同一会话。
- **不做**：结果工具改为「按会话 id 认身份、挂给所有会话」。节点会话总由工作流按原需求单打开后，这一改动收益不足以抵消对结果通道身份机制的改造。
- **限制**：原会话恢复失败时节点报错，进入既有的人工核验与重试。

## ADR 029 工作流成为对象：工作流库与 YAML 源码

2026-11-12 · 已实施

- **问题**：产品里只有「运行」，没有「工作流」。两个定义写死在引擎里，用户看不到、选不了、改不了；入口代号 dev / sr / ar 没有解释；版本号写死，分不出新旧运行。
- **决定**：
  - 工作流是一个目录：`workflow.yaml`（名称、版本、起点、阶段、初始变量）+ `flows/*.yaml`（一个文件一个流程）+ `knowledge/*.md`。预置的随应用安装、只读；用户的在应用数据目录 `workflow-engine/workflows/`，由「复制为我的」得到。存储与编译都归引擎（`package.rs`、`source.rs`），Desktop 只做界面。
  - 源码用 YAML：节点和步骤用有意义的名字，条件写成一行表达式（`expr.rs`），结果用字段类型声明。引擎把源码编译成原有的内部定义，运行时不变。编译时检查引用、条件、字段、可达性，诊断带文件、行号与原因；`workflow_service check` 在命令行做同样的检查，供 AI 改源码后自查。
  - 起点写进源码（`entries`，含所需输入），取代写死的入口映射；启动请求统一为「工作流 id + 起点 + 输入」（`start`）。运行记录带标题（缺省取需求第一行）、需求、起点、工作流版本与内容哈希、创建与更新时间。
  - AAW 面板分三层：工作流库 → 工作流（流程图、源码、本项目的运行、启动表单）→ 运行，顶部面包屑表达从属。打开面板时，最近一次运行没顺利结束就先看它，否则进工作流库。
- **为什么**：模板与实例分开，入口、编辑、分享才有地方挂；源码选可编译验证的声明式格式而不是可执行代码，分享时不会执行任意代码，AI 也能按诊断自行修正。
- **转换**：两个预置流程由脚本从原 JSON 转成 YAML，编译产物与原定义逐项比对一致后删除原 JSON 与公共知识目录。
- **不做**：拖拽式编辑器。流程图只用于理解与展示；编辑的对象是源码，后续由 AI 编辑。

## ADR 030 入口理顺，首版 CLI 工作流在 Desktop 里退场

2026-11-12 · 已实施

- **决定**：
  - 发起运行只有一套表单（选起点 → 填起点声明的输入 → 可选附件与标题），入口有四处：AAW 面板的工作流库与工作流页、会话输入框「/」菜单里每个工作流起点一条、空会话的「启动工作流」、项目总览的工作流区块。
  - 工作流插件提供 `workflowUi` 服务：会话状态卡与空会话按钮读进行中的运行；节点会话顶部显示回指条（哪次运行、哪个节点、是否在等你回复，一键回到那次运行）；侧栏分组标题用运行标题。
  - 删除首版痕迹：会话里的流程时间线与 `.sdd` 状态摘要、建议按钮里让 Agent 走首版 skill 的提示、项目总览按 `.sdd/` 判断有无工作流、设置页的 uv 命令与 aaw 脚本路径、uv / aaw CLI / `.sdd/` 健康检查与相应的脚本来源依赖。健康检查改为：工作流服务能否应答、工作流库里有没有可用的工作流、节点 Agent 是否已配置。
- **为什么**：同一个词「工作流」曾指向两套互不相通的系统；按全新发布处理，不保留兼容。
- **后续落实**：`skills-v2/aaw-practices` 承接原技能的工作方法并与流程控制解耦；旧 `skills/aaw-workflow` 保持原状。旧目录的清理时机另定。

## ADR 031 人工干预运行：检查点、游标与声明式清理

2026-11-12 · 已采纳

- **原则**：引擎在一个混沌的外部环境里追求结果正确。它精确管理自己拥有的流程状态；对外部世界（文件、代码、外部系统）只按节点的声明尽力清理，没有声明的一律不管——重做时环境里多一些噪声，由重做的节点自行处理。不要求 Agent 额外登记自己改了什么。参照 Cordis：框架不理解插件做了什么，只按插件的声明回收。
- **检查点**：每进入一个步骤，引擎存一份流程状态（位置、变量、各节点最近结果、访问次数、子流程进度）。子流程的每个实例有自己的一串检查点；在外层看来，整个实例是一个步骤。
- **一个原语：挪游标**。所有人工干预都是「从某个检查点（或当前状态）继续，下一步是某个步骤」：

  | 干预 | 状态 | 下一步 |
  |---|---|---|
  | 回退到某步 | 恢复进入该步时的检查点 | 该步 |
  | 重跑当前步 | 恢复进入当前步时的检查点 | 当前步 |
  | 跳过 / 由我指定下一步 | 当前状态，当前节点记为「人工跳过」 | 用户选的步骤（同一流程内） |
  | 采用已有结果继续 | 当前状态，登记候选结果（即现有的核验） | 按路由 |

  被越过的节点记录不删除，标为「已作废」，画布上可回看；每次干预写一条审计（谁、何时、从哪到哪、原因）。回退只能退到当前流程层级里已经走过的步骤；要重来整个子流程或整个循环，在外层退到它之前。并行步骤以整个步骤为单位重跑。
- **声明式清理**：节点在源码里写 `cleanup`，列出撤销时要删除的文件。条目是表达式，可以引用这次执行自己的结果（`result.files`、`result.reference`），因此不需要事先知道路径。节点也可以写 `irreversible: 原因`，标明它对外的影响撤不回（例如发了通知）。回退时用户二选一：
  - **保留成果返工**：不清理，沿用原会话，给节点的提示是「已有成果在，按新意见修改」；
  - **丢弃重做**：按声明删除文件，开新会话从头做。
  
  没写 `cleanup` 的节点不清理；回退越过 `irreversible` 节点前必须额外确认。
- **确认关卡**：去向上写 `confirm: must`（必须确认）或 `confirm: ask`（默认确认，这次运行可设为自动放行）。走到这条去向时运行停在「等你确认」，用户选继续或退回（退回即回退）。预置流程放两处：任务计划之后、进入写代码之前；最终交付之前。
- **预览**：任何干预执行前先返回预览：会作废哪些节点、会删除哪些声明过的文件、有没有撤不回的节点、会话怎么处理。用户确认后才执行。
- **运行收尾**：引擎启动时检查运行的属主进程是否还活着；已经退出的，释放占用并把运行标为已中断，可以继续或干预。
- **Desktop**：节点检视器里放「处置」菜单（重跑、跳过、由我指定下一步、回退到这里、采用已有结果），取代手填 JSON 的核验页；确认关卡在横幅和节点卡片上给按钮；停止前确认。
- **不做**：精确撤销（执行前快照、自动恢复改过的文件）、要求 Agent 登记副作用、交给 Agent 撤销、分叉历史（回退覆盖原有的一条线）。
- **实现要点**（2026-11-12）：
  - 检查点存的是「该层流程实例」在进入步骤时的状态，不是整个运行：回退只替换这一个实例，并行的兄弟实例和它们正在执行的动作不受影响。目标实例必须还在执行树上（根实例完成后也可回退）；兄弟实例也阻塞着时拒绝（`ANOTHER_INSTANCE_BLOCKED`），要么先处理它，要么在外层退到循环之前。
  - 动作编号全局单调、实例的访问计数取较大值，重做的节点和新建的子流程实例不会与作废的同名；作废的动作结果晚到也不会被接受。
  - 每条节点记录记下所在步骤的检查点和当时的检查点时钟：回退时「同一实例（含子实例）里、时钟不早于目标的记录」作废；仍在执行的标为 `cancelled`，改道跳过的标为 `skipped`。
  - `cleanup` 用节点自己的名字引用结果（与去向条件写法一致），如 `[design.files]`；清理只在提交后按计划执行，删不掉的条目回报给用户。
  - 「丢弃重做」把涉及角色的会话标为重置：下次该角色开新会话，旧记录仍指向原会话。「保留成果返工」沿用会话，并给重做步骤附一句返工提示和用户意见。
  - 确认关卡是新的运行状态 `waiting`；放行请求 `confirm`，退回即 `intervene` 回退。启动参数 `autoConfirm` 放行 `ask`。预置流程：任务计划之后（企业版去掉了节点自报的 `confirmed`）、最终交付完成之前。
  - 服务请求：`intervene`（`preview: true` 只算影响）、`confirm`；快照增加 `checkpoints`、`gates`、`interventions`，节点记录增加 `checkpoint`、`mark`。干预与放行只在运行停着时执行，之后由调用方继续运行。
  - 服务启动时释放属主进程已退出的运行，记失败码 `OWNER_PROCESS_EXITED`；中断时在执行的动作仍需核对或授权重试，不会被悄悄重跑。

## ADR 032 等待回复与节点会话恢复

- **等待回复**：运行视图列出所有等待的节点，每项可打开对应会话。界面展示当前收到的 Agent 消息节选；没有消息时引导用户查看会话。引擎标记只表示一轮结束且尚未提交结果，不能据此断定 Agent 提出了什么问题。
- **会话归属**：Desktop 在首次创建节点会话时固定运行的 Agent，并在向引擎确认会话创建前保存项目、会话与 Agent 的绑定，以及 Agent 启动配置的摘要。后续新节点与运行继续沿用运行所属 Agent；恢复已有会话时校验其原 Agent，配置缺失或发生变化时停下并说明原因。摘要不保存启动配置明文。丢弃重做产生新会话，建立新的会话绑定。
- **连接与交互**：工作流会话按 Agent 配置使用独立于当前选择的 ACP 连接池，并继续由 Project 收养和呈现。切换工作台当前 Agent 不应关闭已收养的工作流会话。工作流面板和分组会话入口按会话所属 Agent 打开。
- **恢复失败**：Agent 未声明 `loadSession` 时不发送恢复请求；原 Agent 不可用、归属缺失或配置变更均明确提示，不换用其他 Agent。Project 在创建动作前暂时拒绝收养时可有限重试，其他结果不明的动作仍走核验与人工处置。
- **验证边界**：受控测试连接真实 Rust 引擎进程与 Desktop 节点会话宿主，使用标准 ACP 测试对端验证运行中重载、切换 Agent 和不支持恢复；它不等于 Tauri WebView 中真实 Agent 的重载验收。

## ADR 033 启动前环境检查

- **原则**：不新增依赖声明，按选定起点和引擎已有执行条件检查。确定缺失且必需的条件阻止启动；条件分支可能用到但无法确认的条件提示用户，由用户知情后继续。
- **检查范围**：引擎编译工作流、检查项目目录和包内引用的知识与脚本；对所选起点可到达的 Agent 节点检查启动程序与问题池，对可到达的 Python 节点探测 Python。检查不要求先填写需求等运行输入，启动时再校验必填输入。单一路由上必定执行的 Python 缺失时阻止启动，其他可能用到 Python 的情况给出提醒。探测 Python 只运行版本命令，不执行工作流脚本。
- **请求与界面**：`preflight` 只返回检查结果，不创建运行；启动表单展示原因与处理建议。`start` 在创建运行前复查，阻止确定的缺项，新的提醒需要用户确认；工作流版本或启动配置变化后需重新检查。
- **边界**：找到 Agent 程序不代表 ACP 连接、登录或模型可用，检查不会启动 Agent 或调用模型；条件路径不能静态确定时不会假装必然执行。运行期间环境仍可能发生变化，执行失败按原有处置机制处理。
