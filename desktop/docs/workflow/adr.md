## ADR 023 引擎只管流程，会话归 Desktop

2026-11-09 · 已实施

- **决定**：引擎只保留四件事——推进流程（含持久化与恢复）、核验结果、给每个节点下发需求单（提示词、工作目录、工具清单）、结果不确定时停下来交人工核验或授权重试。Agent 会话的拉起、消息、审批卡、呈现与会话历史全部由 Desktop 承担。两边经一组请求协作：拉起会话、开始一轮、等这一轮结束、停止会话、问题池中继。
- **为什么**：早期引擎和 Desktop 各有一套会话状态与呈现，验收中出现「分不清工作中还是等你回复」「补充消息像卡住」等问题。会话归谁管，呈现和语义就归谁管。
- **边界**：引擎只看信封（身份、状态、需求单），看不到会话内容。Python 脚本节点没有会话，仍由引擎直接执行。

## ADR 024 工作流以插件形态接入 Desktop

2026-11-10 · 已实施

- **决定**：工作流整体是一个 Cordis 插件（`src/plugins/workflow/`）：引擎客户端、节点会话宿主、画布状态、面板 UI 都在插件内，经平台服务与其他插件协作。插件监听会话广播感知平台状态；引擎的「拉起 / 开始一轮 / 等结束」由插件作为宿主应答。
- **§9-1 节点会话进标准会话体系**：节点会话经 `project.sessions.adoptExternalSession` 收养，出现在侧栏、在中央会话区打开，与用户会话同一套审批和历史规则。
- **§9-3 结果提交工具按 Agent 能力选择连接方式**：Agent 声明支持 HTTP 方式的 MCP 就用 HTTP，否则用 stdio（ACP 基线）。一整轮结束都没列出过结果工具，节点以 `RESULT_CHANNEL_UNREACHABLE` 失败，不冒充「等你回复」。不为任何特定 Agent 写死规则。

## ADR 025 流程阶段字段；节点记录本（延后）

2026-11-12 · 阶段字段已实施，记录本延后

- **阶段字段**：定义顶层可选 `stages`（有序 `{id, label}`），`phase.stage` 引用它；引用不存在的阶段则定义加载失败（`INVALID_PHASE_STAGE`）。只用于画布分带，不参与调度与恢复。没有 `stages` 时整层画布一个条带；未标注的 phase 归入「其他」。
- **节点记录本（设计已定，未实现）**：结果通道加一个自由格式工具（暂名 `update_workflow_notes`），Agent 每次提交整份清单，条目 `{text, status: todo|doing|done}`，写什么由 Agent 决定。提交结果时若还有未完成条目只提醒、不拒绝；节点结束时引擎把未完成条目封存为「节点已结束」。记录本存入运行记录，画布显示分段进度和当前条目。实现前，界面不得用定义里的静态步骤文案冒充进度。
- **未决**：条目是否需要「跳过」状态；封存时是否区分 Agent 主动收尾与系统代封。

## ADR 026 「等你回复」由引擎标记

2026-11-12 · 已实施

- **决定**：节点一轮结束、结果还没交时，引擎在运行记录上标记该节点「在等用户回复」（`action_awaiting_input`），新一轮开始即清除。面板卡片、横幅和侧栏都读这个标记显示「等你回复」。
- **为什么**：只有引擎知道「这一轮结束了且没交结果」；Desktop 自己猜会把「Agent 在干活」和「在等你」混在一起。

## ADR 027 侧栏按运行分组节点会话

2026-11-12 · 已实施

- **决定**：project 插件提供通用的会话分组扩展点（`registerSessionGroups`），只负责存放与渲染，不理解分组含义；工作流插件把一次运行的节点会话发布为一组（数据来自引擎 `session-links`）。
- **呈现规则**：进行中和等你回复的运行固定排在最前；已结束的运行占它最近一条会话的位置，默认收起。运行进行中时，节点都已做完的会话收进组内默认折叠的「已完成」。分组行可直接打开 AAW 面板并切到该运行。
- **限制**：引擎只返回当前项目的运行，其他项目的节点会话仍平铺。

## ADR 028 界面重新加载后节点续跑

2026-11-12 · 已实施

- **问题**：引擎进程在 WebView 重载后继续存活，但节点会话的连接与「这一轮何时结束」的状态在 WebView 里，随重载消失。引擎会一直等一个不会再来的信号；普通会话流程重新打开该会话时也不带结果工具。
- **决定**：
  - Desktop 的节点会话宿主就绪后向引擎宣告上线（`host-reset`）。引擎把旧宿主的挂起请求一律以 `HOST_RESET` 结束。
  - 正在跑的 Agent 节点用原会话 id、原结果通道经新宿主重新打开会话，发一轮续跑提示：已完成就直接提交，否则继续。中断前已提交的结果直接收尾。同一轮最多续跑 5 次。
  - 收养会话时，若同一会话已被普通流程打开，由收养方接管并关闭普通连接，避免两条连接驱动同一会话。
- **不做**：结果工具改为「按会话 id 认身份、挂给所有会话」。节点会话总由工作流按原需求单打开后，这一改动收益不足以抵消对结果通道身份机制的改造。
- **限制**：原会话恢复失败时节点报错，进入既有的人工核验与重试。

## ADR 029 工作流成为对象：工作流库与 YAML 源码

2026-11-12 · 已实施

- **问题**：产品里只有「运行」，没有「工作流」。两个定义写死在引擎里，用户看不到、选不了、改不了；入口代号 dev / sr / ar 没有解释；版本号写死，分不出新旧运行。
- **决定**：
  - 工作流是一个目录：`workflow.yaml`（名称、版本、起点、阶段、初始变量）+ `flows/*.yaml`（一个文件一个流程）+ `knowledge/*.md`。预置的随应用安装、只读；用户的在应用数据目录 `workflow-engine/workflows/`，由「复制为我的」得到。存储与编译都归引擎（`package.rs`、`source.rs`），Desktop 只做界面。
  - 源码用 YAML：节点和步骤用有意义的名字，条件写成一行表达式（`expr.rs`），结果用字段类型声明。引擎把源码编译成原有的内部定义，运行时不变。编译时检查引用、条件、字段、可达性，诊断带文件、行号与原因；`workflow_service check` 在命令行做同样的检查，供 AI 改源码后自查。
  - 起点写进源码（`entries`，含所需输入），取代写死的入口映射；启动请求统一为「工作流 id + 起点 + 输入」（`start`）。运行记录带标题（缺省取需求第一行）、需求、起点、工作流版本与内容哈希、创建与更新时间。
  - AAW 面板分三层：工作流库 → 工作流（流程图、源码、本项目的运行、启动表单）→ 运行，顶部面包屑表达从属。打开面板时，最近一次运行没顺利结束就先看它，否则进工作流库。
- **为什么**：模板与实例分开，入口、编辑、分享才有地方挂；源码选可编译验证的声明式格式而不是可执行代码，分享时不会执行任意代码，AI 也能按诊断自行修正。
- **转换**：两个预置流程由脚本从原 JSON 转成 YAML，编译产物与原定义逐项比对一致后删除原 JSON 与公共知识目录。
- **不做**：拖拽式编辑器。流程图只用于理解与展示；编辑的对象是源码，后续由 AI 编辑。

## ADR 030 入口理顺，首版 CLI 工作流在 Desktop 里退场

2026-11-12 · 已实施

- **决定**：
  - 发起运行只有一套表单（选起点 → 填起点声明的输入 → 可选附件与标题），入口有四处：AAW 面板的工作流库与工作流页、会话输入框「/」菜单里每个工作流起点一条、空会话的「启动工作流」、项目总览的工作流区块。
  - 工作流插件提供 `workflowUi` 服务：会话状态卡与空会话按钮读进行中的运行；节点会话顶部显示回指条（哪次运行、哪个节点、是否在等你回复，一键回到那次运行）；侧栏分组标题用运行标题。
  - 删除首版痕迹：会话里的流程时间线与 `.sdd` 状态摘要、建议按钮里让 Agent 走首版 skill 的提示、项目总览按 `.sdd/` 判断有无工作流、设置页的 uv 命令与 aaw 脚本路径、uv / aaw CLI / `.sdd/` 健康检查与相应的脚本来源依赖。健康检查改为：工作流服务能否应答、工作流库里有没有可用的工作流、节点 Agent 是否已配置。
- **为什么**：同一个词「工作流」曾指向两套互不相通的系统；按全新发布处理，不保留兼容。
- **未做**：首版 `skills/aaw-workflow` 本身的瘦身（去掉流程性内容、保留哪些技术能力）留待确认范围后处理。
