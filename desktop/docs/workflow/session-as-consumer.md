# 设计说明：节点会话就是普通会话，工作流只消费事件

状态：已采纳（ADR 037），本文是实施依据。

## 1. 一句话

工作流创建的会话和用户自己开的会话一模一样，由应用的会话管理统一负责。工作流在会话里只做两件事：像一个参与者那样**发消息**，以及**订阅事件**判断节点进展。它不再自己转发和排队消息。

## 2. 现在怎么做，问题在哪

现在节点会话走「收养」（ADR 024 §9-1）：

- 会话连接由工作流宿主（`sessionHost/nativeSessionHost.ts`）自己打开和关闭，项目侧（`adoptExternalSession`）只负责显示。
- 用户在节点会话里打的字不直接发给 Agent，而是经 `onUserMessage` 交给工作流宿主的内部队列，只有引擎正在「等这一轮结束」时才转发出去。

由此产生的问题：

| 场景 | 现在的结果 |
| --- | --- |
| 运行停止后，在会话里发消息 | 消息显示出来，但只进了内部队列，没人处理，Agent 不回，也没有任何提示 |
| 停止后再「继续运行」 | 重新打开会话时队列是新建的，那条消息丢了 |
| 停止后重启应用，再打开会话 | 会话变成普通会话，用户能和 Agent 正常对话，但工作流完全不知道 |
| 代码 | 收养会话和普通会话是两条路：`adopted` 标记、`bindAdopted`、工作流队列、合成的用户消息回显、同一会话被两边打开时的接管（ADR 028） |

## 3. 新做法

```
            应用的会话管理（project.sessions）
            ┌──────────────────────────────┐
 用户打字 ──►│  普通会话：连接、发送队列、   │──► Agent
 工作流发消息►│  历史、审批、侧栏             │
            └──────────────┬───────────────┘
                           │ 会话事件（轮次开始/结束、停止原因）
                           ▼
                    工作流（只读事件）
                           │ 有没有交结果？
                           ▼
                    引擎（推进流程）
```

- **会话谁管**：全部由应用的会话管理打开、保持和关闭，和普通会话同一套连接、发送队列、历史和审批。工作流不持有连接，也不关闭会话。
- **工作流发消息**：每个节点的任务说明作为一条普通消息，经正常发送入口发出，带「工作流发的」标记（`origin: "workflow"`，已有）。界面照旧把它折叠成「工作流给 Agent 的说明」。
- **用户发消息**：任何时候都是正常发送，直接给 Agent，不经过工作流。
- **工作流怎么知道进展**：订阅会话事件。每当一轮结束，看 Agent 有没有交结果，再告诉引擎。

先例：定时任务插件已经用 `project.sessions.runBackgroundPrompt` 在普通会话里发消息并观察状态（`scheduledTasks/index.ts`）。

## 4. 引擎不用改：它的四个请求换个实现

引擎对会话只提四个请求（ADR 023），换成新做法后依然成立：

| 引擎的请求 | 新实现 |
| --- | --- |
| 拉起会话（`spawn_node_session`） | 请会话管理打开（或恢复）一个普通会话，附带结果工具；返回会话 id |
| 开始一轮并等它结束（`prompt_turn`） | 经正常发送入口发出任务说明，等这条消息对应的那一轮结束 |
| 等下一轮结束（`wait_turn_ended`） | 等这个会话的下一个「轮次结束」事件，**不管这一轮是谁发起的** |
| 停止会话（`stop_node_session`） / 停止运行（`cancel_waiting`） | 取消正在进行的那一轮，并结束等待；会话本身保留，变回可自由对话的普通会话 |

引擎判断节点完成的循环（`runtime.rs`「轮次边界后的交付核验」）本来就是「每到一轮结束就看有没有结果，没有就等下一轮」，正好对应事件消费。

## 5. 四个需要定下来的规则

### 5.1 一轮结束了，算不算这一步做完

| 这一轮怎么结束的 | 有没有交结果 | 节点状态 |
| --- | --- | --- |
| 正常结束 | 交了 | 完成 |
| 正常结束 | 没交 | 等你回复（现有 ADR 026 标记） |
| 被用户在会话里点停止打断 | — | 等你回复，**不算失败**（现在会报 `ACP_TURN_NOT_COMPLETED`，要改） |
| 出错（连接断开等） | — | 按现有规则：结果不确定就停下交人工核验/重试 |

### 5.2 运行停止期间，Agent 交结果会怎样

**原则：停止只是「流程别自己往下走、Agent 先别干了」，不是「这一步的会话失效了」。** 只要运行还没结束（还能继续），节点会话就完全正常，包括交结果。不能让任何实现上的限制变成需要向用户解释的特殊状态。

**背景**：每个节点开始时，工作流给 Agent 装一个工具 `submit_workflow_result`，Agent 做完后调用它交结果。它背后是引擎为运行开的本机收件服务（`result_channel.rs`）。交上来的结果会立即作为候选记进运行记录（`result_candidates` 表，状态 `submitted`），本轮正常结束后才被采用（`applied`）。

**现在的问题**：收件服务随运行线程一起关闭。停止后 Agent 再交结果连不上，stdio 中转进程直接退出，Agent 只看到工具坏了。

**新做法，用户看到的**：

1. 停止后，用户在会话里和 Agent 聊、让它把活干完。Agent 交结果，回复和平时一样是「已提交」。
2. 运行面板上这一步显示「已完成」。运行仍然停着，因为是用户让它停的，不自动往下走。
3. 用户点「继续运行」：这一步已经有结果，直接进入下一步，不再让 Agent 交一次。
4. 停止期间 Agent 没交结果：继续运行时，这一步照常接着做（同一会话，重发这一步的任务说明，现有行为）。

**实现要点**：

- **收件服务不随停止关闭**：运行停止时，该运行的收件服务交给服务进程保管（按运行 + 角色），继续接收并照常写候选记录。地址和口令不变，Agent 手里的工具一直有效；继续运行时运行线程取回同一个收件服务。运行结束（完成、失败后放弃、删除）时才关闭。
- **继续运行先看候选**：一个 Agent 节点开始前，若该节点已有通过校验、状态为 `submitted` 的候选结果，就直接采用并收尾，不再发任务说明。这和 ADR 028「中断前已提交的结果直接收尾」是同一条规则，只是从内存扩展到运行记录。
- **停止期间交结果时面板要更新**：候选写入后发运行变化事件，面板把这一步显示为「已完成」，侧栏和横幅同步。
- **应用重启后**：服务进程重启，收件服务不存在了，Agent 进程也已经随应用退出。用户再打开这个会话时，只要运行还没结束，就由「会话附加工具」提供者（见 5.4）按需重新开一个收件服务并装上，行为与重启前一致。
- **中转进程兜底**：stdio 中转进程连不上收件服务时（只会出现在运行已经彻底结束的会话上），不退出，回一条普通的工具错误，避免 Agent 把整个工具当成坏掉。

### 5.3 用户和工作流同时发消息

走普通会话的发送队列：先到先发，正在进行的那一轮结束后再发下一条。不需要额外设计。注意同一个角色的多个节点共用一个会话（引擎按角色复用会话），所以下一个节点的任务说明也可能排在用户消息后面，这是期望的行为。

### 5.4 会话谁来开、谁来关

- **开**：工作流向会话管理提要求：工作目录、用哪个 Agent 和模型、恢复哪个会话 id、附带哪些 MCP 工具（结果工具和需求单里的工具）、侧栏标题。会话管理按普通流程打开。需要给会话管理加上「打开时附带额外 MCP 工具」的能力。协议层已经支持（`AcpSession` 的 `mcpServers` 选项），所以对任何标准 ACP Agent 都适用，不依赖 chrys。
- **重新打开**：用户在侧栏打开一个节点会话时，如果它所属的运行还在进行，会话管理要能问到「这个会话需要附带哪些工具」，保证用户打开和工作流打开是同一个连接、同样的工具。做法：工作流在会话管理那里登记一个「会话附加工具」提供者，运行停着就不提供。这样不用做 ADR 028 里否决的「结果工具挂给所有会话」，也不再需要「接管并关闭普通连接」。
- **关**：和普通会话一样，由会话管理按自己的规则关闭（切换项目、归档、退出应用等）。工作流结束不关会话。

## 6. 走一遍：停止 → 聊天 → 继续

1. 节点「实现与测试」正在跑，用户在运行面板点「停止」。
2. 工作流取消正在进行的那一轮，运行显示「已停止」，收件服务照旧开着。
3. 用户在这个会话里说「先把登录那块的测试补上」。这是普通消息，Agent 照常回复、改文件。
4. Agent 做完，调用交结果工具，收到「已提交」。面板上「实现与测试」变成「已完成」，运行仍是「已停止」。
5. 用户点「继续运行」。这一步已有结果，流程直接进入下一步。

工作流全程不碰用户的消息，只在每轮结束、每次交结果时更新状态。用户看不到任何特殊状态。

## 7. 代码上的变化

**删掉**

- 项目侧收养通路：`adoptExternalSession`、`SessionRuntime.adopted` / `bindAdopted` / `sessionIdOfAdoption`、`onUserMessage` 路由
- 工作流宿主的消息队列：`queue`、`pendingWait`、`queueUserMessage`、`driveQueuedMessageTurn`、`registerNativeMessageQueue`
- 宿主合成的用户消息回显（`emitTurnContext` 中补发 `user_message_chunk`）
- ADR 028 的「同一会话被普通流程打开时接管」

**新增 / 改动**

- `project.sessions`：
  - 打开会话时可附带 MCP 工具，并指定 Agent 和模型；
  - 以「工作流发的」身份往会话发一条消息，返回这条消息对应那一轮的结束结果；
  - 订阅某个会话的轮次事件；
  - 登记「会话附加工具」提供者。
- `nativeSessionHost.ts`：按第 4 节的表重写四个请求，变成薄薄一层；轮次被打断按 5.1 的规则返回「没交结果」，不再算失败。
- 引擎：运行停止时收件服务交给服务进程保管，继续时取回；Agent 节点开始前先采用已有的 `submitted` 候选；停止期间写入候选时发运行变化事件（5.2）。
- 引擎 `result_channel.rs` 的 stdio 中转：连不上时回普通工具错误，不退出。
- 会话横幅 `WorkflowSessionBanner.tsx`：沿用现有的运行状态显示和「查看运行」，不新增特殊提示。

## 8. 和旧决定的关系

- **ADR 024 §9-1**（节点会话经收养进标准会话体系）：改为节点会话本身就是标准会话，收养取消。
- **ADR 028**（重载后续跑）：续跑机制保留（`host-reset`、同一会话 id 重开、续跑提示），去掉「接管普通连接」。「不做」一条的理由仍成立，本设计用「附加工具提供者」绕开，不改结果工具的身份机制。
- **ADR 032**（会话归属与连接池）：归属记录、恢复校验规则不变，连接改由会话管理统一持有。
- **ADR 023**（引擎只管流程）：不变，并且更彻底，消息流完全不过工作流。

## 9. 拆分与验证

1. **PR 1：会话管理的能力**。打开时附带工具、以工作流身份发消息、订阅轮次事件、附加工具提供者。现有普通会话行为不变，用测试证明。
2. **PR 2：工作流改为事件消费**。重写宿主，删掉收养和队列，打断不算失败；收件服务跨停止保留，继续时先采用已交的结果。
3. **验证**：
   - 受控测试（真实 Rust 引擎 + 标准 ACP 测试对端）覆盖：正常完成、没交结果等你回复、用户打断、停止后聊天再继续、停止期间交结果、运行中重载、同角色多节点共用会话；
   - 真机走查同样几个场景，重点看停止后聊天再继续。

## 10. 一并收回的越界（自审结果）

标准：会话归应用，工作流只发消息、看事件；平台代码不认识工作流。

| # | 越界 | 改成 |
| --- | --- | --- |
| 1 | 工作流自己做会话握手（`openAdoptedSession`：初始化、新建/恢复、设模型），切 profile 用 chrys 私有的 `_session/switch_agent`，问答卡自建方言接 `_chrys/request_input` | 应用打开会话，工作流只提要求（模型、工具）。profile 不再由工作流切换；需要时作为应用对所有会话的通用能力另议 |
| 2 | 宿主把 Agent 事件再投影一遍（`projectNativeEvent`），并合成 `workflow_context`、初始需求的用户消息、`workflow_waiting_input` 塞进会话 | 删除。工作流订阅应用的会话事件；「等你回复」是运行状态，由工作流自己的横幅/侧栏显示 |
| 3 | 会话归属记三份：应用会话目录、引擎 `actor_sessions`、工作流自存的 `sessionOwner.ts`。对不上时悄悄放弃恢复、新开会话，随后引擎报 `ACTOR_SESSION_MISMATCH` | 用哪个 Agent 归应用会话目录；引擎只记角色↔会话；删 `sessionOwner.ts`。恢复不了就按现有规则停下说明原因，不悄悄新开 |
| 4 | 平台认识工作流：project 引用工作流类型；会话页写死「启动工作流」「回复进行中的工作流」；状态浮层列工作流运行；`sessionStore` / `historyCompaction` / `UserMessage` 特判 `origin: "workflow"`；正文里的「工作流说明」文字标记；`AcpSession.prompt` 的 `echo: "workflow"` | 应用提供通用扩展位：替插件发的消息（来源、折叠标题作为消息属性由应用保存，不写进正文）、会话横幅位、状态浮层位、斜杠命令登记。工作流经扩展位接入，平台代码不出现 workflow |
| 5 | 引擎在重载后向对话发「（工作流提示）会话刚刚重新连接……」 | 连接归应用、重载照常恢复，不再需要；删除 `RESUME_AFTER_HOST_RESET_PROMPT` 及其续跑路径 |
| 6 | 引擎内置第二套会话实现 `headless_host.rs` + `acp.rs`（约 1100 行，不带参数时默认使用），自己起 Agent、排队、转发审批与回答；服务方法 `answer` / `permission` | 已无使用方（2026-11-18 确认）。删除；测试改用模拟宿主；`workflow_service` 只保留桌面端宿主方式 |
| 7 | 协议里的 `stop_node_session` 引擎从不发送 | 删除 |

不算越界、保留：交结果工具与问题池（工作流给 Agent 的工具）、「等你回复」标记、侧栏按运行分组（应用扩展点）、文件快照、运行面板读会话事件显示消息节选。

拆分调整：第 4 条与「打开会话时附带工具」一起进 PR 1；第 1、2、3、5、7 条进 PR 2；第 6 条单独一个 PR（只删引擎代码和改测试，可最先做）。

## 11. 还没定的

- 用户在运行进行中、但不是「等你回复」时插话（Agent 正在干活时插一句），这条消息排在当前轮之后发出。是否需要在输入框提示「会在 Agent 这一轮做完后发出」？普通会话已有排队显示，倾向于不额外处理。
- 停止期间这一步已经交了结果，「继续运行」之外是否还要在别处提示「这一步已完成，可以继续」？倾向于不加：面板上这一步本来就显示已完成，运行停着是用户自己的选择。
