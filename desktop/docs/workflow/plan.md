# 工作流修改方案与迭代计划

2026-11-12 · 方向已确认。缺口编号（A1、D2 等）见 [`gaps.md`](gaps.md)。

## 已确认的决定

1. 工作流包的存储与校验归引擎，Desktop 只做界面。
2. 按全新发布对待：不考虑升级和迁移，不为旧数据、旧接口、首版流程保留兼容。
3. 流程图只用于理解和展示，不可编辑。编辑的对象是定义源码，用户通过 AI 来改。
4. 全部迭代做完才上线，中间没有对外版本。
5. 定义源码用 YAML，由引擎编译成现有的 JSON；JSON 只作为引擎的运行格式，不再给人和 AI 编辑。

## 一、方案

### 1. 工作流成为一个对象

- **工作流是一个包**：一个目录，里面是定义源码、知识文件、脚本，以及元信息（名称、说明、来源、版本）。
- **存放在应用级**：应用数据目录下 `workflow-engine/workflows/<id>/`。预置的随应用打包、只读；用户「复制为我的」之后才能改。
- **引擎管存储和编译校验**：提供列出、读取、保存、删除、编译、导入、导出。
- **版本用定义内容的哈希**，另带一个给人看的版本号。运行按启动时存下的定义显示；工作流之后被改过，界面提示「这次运行用的是旧版」。
- **起点写进定义**：定义声明有哪些起点、各自的名称、说明和需要的输入，取代引擎里写死的 dev / sr / ar。
- **启动接口统一**为「工作流 id + 起点 + 输入」。
- **运行有身份**：标题（默认取需求首行，可改）、需求原文、创建时间、开始和结束时间。

### 1.1 定义源码与编译

- **源码是 YAML**，一个子流程一个文件；提示词放单独的 Markdown 文件；可以写注释。
- **写法面向阅读**：节点用有意义的名字；条件写成一行表达式（如 `需求确认.status == "ready"`）；节点结果用简单的字段类型声明；默认值（如访问次数上限）不必写出。
- **引擎内置编译器**：源码 → 现有的 JSON 定义。运行时仍然只认 JSON，不改。
- **编译时检查**：
  - 引用了不存在的节点、步骤、文件；
  - 步骤走不到，或进去后没有出口；
  - 条件用了节点未声明的结果字段，或类型对不上；
  - 回环没有次数上限；循环的对象不是列表；
  - 出现不认识的字段（严格解析，拼错即报错）。
- **报错带文件、行号、原因和改法**，供 AI 按「改源码 → 编译 → 看报错 → 再改」循环使用。
- **不选可执行代码（TypeScript / Python）作源码**：加载即执行代码，分享不安全，可解释性也差。

### 2. 面板分层与入口

- **AAW 面板分三层**：工作流库 → 工作流详情（流程图、说明、起点、历史运行）→ 某次运行。顶部用面包屑表达从属。
- **发起流程只有一套**：选工作流 → 看流程图 → 选起点、填需求（可附文件）→ 启动。
- **入口**：会话输入框的斜杠命令、空会话的建议按钮、项目概览、工作流库里的「运行」，都进这一套流程。
- **首版痕迹直接删除**：建议按钮的旧文案、项目概览的 `.sdd` 状态、健康检查里的 uv / aaw 脚本 / `.sdd/` 检查、插件里保留的首版类型与兼容代码。健康检查改为检查新引擎。
- **侧栏分组**标题改用运行标题；节点会话顶部加一行回指（哪次运行、哪个节点、回到画布）。

### 3. 运行控制

- **确认关卡**：连线上可配 跳过 / 询问 / 必须确认。走到「必须确认」时运行进入「等你确认」，界面给「继续」和「退回」。
- **回退**：先预览——退到哪个节点、哪些下游记录作废、涉及哪些成果文件；再由用户选「保留成果后返工」或「删除成果后重做」。作废的记录标为已作废，可回看。
- **节点声明产出文件**：定义里写明节点产出哪些文件、哪些必需。回退、必需产出检查、成果展示都以它为准。
- **处置面板**取代现在的核验页，三个选择题：采用已有结果继续、重跑这个节点、由我指定下一步。手填 JSON 降为高级选项。
- **重跑某节点就是回退到该节点**，不另做一套。

### 4. 过程可见

- **通知**：等你回复、等你确认、失败、完成四种情况发系统通知，点击回到对应运行。
- **时间**：已运行时长、等待时长、整次耗时。
- **运行总结页**：做了什么、产出文件、各评审结论、耗时、查看代码变更的入口。
- **报错**：错误码补齐人话说明；服务退出给「重启服务」按钮。
- **节点记录本**按 ADR 025 实现。

### 5. 用 AI 编辑工作流

- **编辑的是定义源码**。工作流详情里可以查看源码，旁边是只读的流程图。
- **用户对 AI 说要改什么**：从工作流详情发起一个编辑会话，Agent 修改定义源码。
- **保存前必须过三步**：引擎编译通过；展示改动前后的流程图对比和源码差异；用户确认。
- **新建同理**：用户描述诉求，Agent 从空白或某个预置出发写出定义。
- **为此要补的基础**：
  - 定义格式的说明文档和示例，作为编写工作流的 skill 的内容；
  - 校验错误说人话，并指出是哪个节点、哪条连线，Agent 才能自己改对；
  - 定义里的角色可以指定 Agent 和模型，未指定用默认。
- **分享**：导出为单个文件；导入时列出包内的脚本，确认后才可运行。

### 6. 工作流技能

- 新版放在 `skills-v2/`：`aaw-practices` 承接工作方法，流程推进交给引擎；原 `skills/` 保持原状。旧目录何时清理另行决定。

## 二、迭代计划

进展（2026-11-12）：迭代 0、1、2 已完成，见 ADR 029、030；新版技能已在 `skills-v2/` 中建立。迭代 3 的主体见 ADR 031：确认关卡、回退 / 重跑 / 改道与预览、声明式清理与撤不回提醒、处置面板、停止确认、属主进程退出后的自动收尾。

D6 与 D7 的实现和受控跨进程测试见 ADR 032。真实 Tauri WebView 重载及真实 Agent 的恢复效果仍需单独记录。D8 启动前环境检查见 ADR 033；D3 的需求变化通过回退时补充返工意见处理，不单设「修改需求后继续」功能。


顺序只按依赖排。每个迭代结束时在真实应用里走一遍，但只有迭代 7 通过才上线。

### 顺序的理由

- 迭代 1 最先：入口、层级、编辑、分享都要挂在「工作流」这个对象上。定义格式说明和可定位的校验报错也放在这里，因为迭代 5 的 AI 编辑完全依赖它们。
- 迭代 2 紧随：改动不大，直接消除「同一个词指向两套东西」。
- 迭代 3 在迭代 5 之前：确认关卡和产出声明会改定义格式，格式定下来之后再教 AI 写，免得返工。
- 迭代 4 在迭代 3 之后：通知要包含「等你确认」，总结页要用到产出声明。
- 迭代 6 最后：不改数据和接口，放在格式和层级都稳定之后。
