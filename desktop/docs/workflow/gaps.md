# 工作流功能缺口清单

2026-11-12 · 依据：阅读 Desktop 工作流插件、`workflow-engine-rs`、首版 `skills/aaw-workflow` 的代码与文档。没有在应用里逐项实测；标「待核实」的条目尚未确认。

这份清单只回答「缺什么」，不写方案。每条标了要动哪一层：

- **引擎**：`workflow-engine-rs`
- **插件**：`src/plugins/workflow/`
- **Desktop**：工作流插件之外的界面（会话区、侧栏、项目概览、设置）
- **内容**：流程定义与提示词

## 已定的前提

- 首版 `aaw-workflow` skill 退化为技术性 skill，不再承载流程；流程只由新引擎承载。新引擎可以在约定位置写自己的记录文件或 sqlite。
- 用户自定义的工作流存在应用级，可共享，将来能分享给别人。
- 「不改 Desktop 整体界面」不是死规则，必要时可以改，但要慎重。

## 进展

- 迭代 1、2 已覆盖：A1–A4、A6、B1、B2（标题、需求、时间）、B5、B6 中的侧栏标题、C1–C4；E2 只做了运行级的开始时间与用时。
- 仍待处理：C5（首版 skill 本身的瘦身）、B6 中「已完成」折叠区的自动展开与整次运行归档，以及其余各组。

## 根因

产品里只有「运行」，没有「工作流」。用户看不到、选不了、管不了工作流本身，所以模板和实例混在一起，入口无处安放，从属关系也画不出来。A 组是其他各组的前提。

## A. 工作流作为对象（模板）

| 编号 | 缺口 | 现状 | 层 |
|---|---|---|---|
| A1 | 工作流不可见 | 画布结构取自运行快照，没有运行就看不到流程图。引擎的 `catalog` 请求能在不启动时返回结构，Desktop 没用 | 插件 |
| A2 | 没有工作流库 | 不能列出、查看、复制、编辑、删除。预置的和用户自己的没有区分 | 插件、引擎 |
| A3 | 没有定义的存放处 | 两个定义文件随引擎打包，写死在代码里。引擎的 `start-flow` 能用任意定义启动，Desktop 没用。应用级存储、导入导出都没有 | 引擎、插件 |
| A4 | 没有版本 | 版本号在引擎里写死为 `definition-v1`。定义改动后，新旧运行无法区分，也没有「这次运行用的是旧版」的提示（首版有定义漂移告警） | 引擎 |
| A5 | 不能创作 | 没有编辑界面（首版有 Studio 和 yaml 配置）。没有「让 AI 生成工作流」的路径。定义校验失败只有错误码 | 插件、引擎 |
| A6 | 「入口」概念没有产品化 | 用户选的是 dev / sr / ar 三个代号，其中 sr 和 ar 是同一个定义的两个起点。界面没有解释它们是什么、差在哪 | 插件、内容 |
| A7 | 不能配置谁来执行 | 整次运行所有节点共用一条 Agent 启动命令，不能按节点或角色选 Agent、模型 | 引擎、插件 |
| A8 | 分享的打包与信任 | 定义依赖知识文件和 Python 脚本，目前没有把它们打成一个可传递单元的格式；导入他人的工作流会执行脚本，没有信任提示 | 引擎、插件 |

## B. 从属关系与导航

完整的链是：工作流 → 运行 → 节点 → 轮次 → 会话。

| 编号 | 缺口 | 现状 | 层 |
|---|---|---|---|
| B1 | 没有一处展示完整的链 | 侧栏只有「运行 → 会话」，面板只有运行下拉框 | 插件、Desktop |
| B2 | 运行没有身份 | 名字是「流程名 · 8 位编号」。需求原文启动后在界面上看不到。引擎的运行列表不返回创建时间和需求 | 引擎、插件 |
| B3 | 运行不能管理 | 历史是原生下拉框，不能搜索、筛选、重命名、归档、删除。引擎没有删除运行的接口 | 引擎、插件 |
| B4 | 没有跨项目视图 | 只能看当前项目的运行；其他项目的节点会话在侧栏平铺不分组 | 引擎、插件 |
| B5 | 会话里没有回指（待核实） | 打开节点会话后，看不到它属于哪次运行的哪个节点、要交什么结果，也不能跳回画布上的位置 | Desktop |
| B6 | 侧栏定位 | 打开的会话落在「已完成」折叠区时不会自动展开；不能归档整次运行 | Desktop、插件 |

## C. 发起入口

| 编号 | 缺口 | 现状 | 层 |
|---|---|---|---|
| C1 | 入口深且放错了地方 | 唯一可用路径：右栏新标签页 → AAW 工作流面板 → ＋ 新运行 → 选代号 → 填文本框。发起动作藏在查看进度的面板里 | 插件、Desktop |
| C2 | 会话侧的入口断了 | 输入框的工作流斜杠命令、会话顶部的工作流时间线、项目概览的工作流状态，代码还在，但提供数据的服务已不装配 | Desktop、插件 |
| C3 | 多处仍指向首版 CLI | 空会话的「启动一条工作流」建议会让 Agent 走首版 skill 的流程；项目概览读 `.sdd` 状态；工作区健康检查查的是 uv、aaw 脚本和 `.sdd/` 目录，而不是新引擎 | Desktop、插件 |
| C4 | 启动时能给的信息太少 | 只有一段文字。不能附文件、引用已有需求文档、从当前会话转入；启动前没有流程预览和确认 | 插件、引擎 |
| C5 | 首版的清退没有做 | 首版 skill 的流程性内容还在；已有 `.sdd` 进行中流程的项目如何过渡，没有安排 | 内容、Desktop |

## D. 运行控制

| 编号 | 缺口 | 现状 | 层 |
|---|---|---|---|
| D1 | 不能回退 | 首版可回退到任一步，先预览目标步骤、失效的下游步骤、受影响的成果物，再由用户选「保留后返工」或「删除后重做」。新引擎没有 | 引擎、插件 |
| D2 | 没有确认关卡 | 首版的连线可配 跳过 / 询问 / 必须确认，现有流程里有三处必须确认。新引擎一路跑到底，人只在出错时被叫进来 | 引擎、内容、插件 |
| D3 | 干预动作只有停止和继续 | 不能跳过节点、从某个节点重跑、评审有发现时由人放行、修改需求后继续 | 引擎、插件 |
| D4 | 停止没有说明 | 没有确认，不说明停了之后能否继续；没有暂停 | 插件 |
| D5 | 核验流程门槛过高 | 要用户手填合法 JSON 作为「真实输出」，证据必填；「核验」「登记」「解除占用」是引擎的说法 | 插件 |
| D6 | 「等你回复」不知道回什么 | 横幅只说这一轮结束了、没交结果。多个节点同时等时只能打开第一个 | 插件、引擎 |
| D7 | 重载续跑未在真实应用验证 | ADR 028 只有引擎测试 | 引擎、插件 |
| D8 | 环境缺项让整次运行白跑 | 实例：OpsCopilot 的运行 51a503f0 做完了设计、门禁、实现、两路评审，最后 CodeCheck 节点因项目没配检查器报 blocked，整次运行以「已阻塞」结束，原因字段为空。Desktop 从不传检查器配置；启动前不检查流程依赖的环境；用户也不能放行 | 引擎、插件、内容 |
| D9 | 运行的属主进程死后，记录永远停在「运行中」 | 开发库里 4 条运行停在运行中，没有存活的属主；其中一条的占用记录指向已退出的进程。ADR 028 只覆盖 WebView 重载、引擎进程存活的情况；应用关闭或引擎退出后，没有自动收尾 | 引擎 |

## E. 运行过程与结果的可见性

| 编号 | 缺口 | 现状 | 层 |
|---|---|---|---|
| E1 | 没有通知 | 等你回复、失败、完成只在面板和侧栏里显示，人切走就不知道 | Desktop、插件 |
| E2 | 没有时间信息 | 节点开始时间、已运行时长、等待时长、整次耗时都不显示；引擎给了开始等待的时间，界面没用 | 引擎、插件 |
| E3 | 节点内部没有进度 | 运行中的节点只有 360 字的最新消息节选。节点记录本（ADR 025）未实现 | 引擎、插件 |
| E4 | 跑完没有交代 | 没有运行总结：做了什么、改了哪些文件、产出了哪些文档、各评审结论。没有查看代码变更的入口 | 插件、引擎 |
| E5 | 结果解读靠猜 | 按字段名推断含义，认不出的字段直接显示英文键名；自定义工作流的结果会更难读 | 插件、内容 |
| E6 | 报错不可读 | 引擎的错误码远多于界面翻译过的十几个；服务退出时让用户去翻 stderr 日志；面板自己的报错会盖住运行的失败原因 | 插件 |
| E7 | 内部标识外露 | 卡片上的 `R1`、`AGENT / PYTHON / FLOW`，检视器里的 `节点id#序号` | 插件 |

## 依赖关系

- A1–A4 是 B、C 的前提：先有「工作流」这个对象，层级和入口才有东西可挂。
- A3、A4 是 A5、A8 的前提：先有存储和版本，才谈得上编辑、生成、分享。
- D1、D2、D3 都要引擎先提供能力，界面才能接。
- C3、C5 与「首版 skill 退化为技术性 skill」是同一件事的两面，需要一起做。
- E、F 两组大多可独立进行，不依赖以上各项。

## 核实记录（迭代 0）

- **B5 确认缺失**：收养节点会话时只传了侧栏标题，会话区拿不到运行和节点信息。
- **C2 确认**：提供会话侧工作流能力的服务没有任何地方装配，斜杠命令、会话时间线、项目概览的工作流区都不会出现。
- **C3 确认**：
  - 空会话建议按钮依赖的「当前 SR」永远为空，所以总是显示「启动一条工作流」，点了会让 Agent 走首版 skill 的 sr 入口；
  - 工作区健康检查仍注册的是 uv、aaw 脚本、`.sdd/` 三项。
- **G 表两行确认**：结论已写进上表。
- **新发现**：D8、D9。
- **D7 按代码核实**：重载续跑链路每一段都有实现，大部分有测试——
  - 页面重新加载时，Tauri 回收旧页面的 Agent 进程，不会出现两个进程驱动同一会话（Rust 测试）；
  - 新页面的节点会话宿主就绪后宣告上线（单测）；
  - 引擎把旧请求以 HOST_RESET 结束，按原会话 id 重新拉起并发续跑提示（引擎测试）；
  - 恢复会话时按同一规则带上结果通道（单测）；
  - 同一会话已被普通流程打开时由收养方接管（集成测试）。
- **D7 的残留风险**（代码能确认，但没有测试覆盖）：
  - 恢复会话用的是重载时「当前选中」的 Agent，不是节点启动时的 Agent；用户中途切换过 Agent，恢复必然失败；
  - Agent 不支持恢复会话（`loadSession`）时直接失败，报错不说明原因；
  - 除 HOST_RESET 外，恢复时的任何错误都让节点立即失败、不重试，例如恰好在切换 Agent 时被拒绝收养；
  - 没有把真实引擎进程与 Desktop 宿主连起来跑的端到端测试。
- **顺带发现**：Tauri 已经装了系统通知插件，E1 不需要新增原生依赖。
- **已清空**开发环境的引擎数据（运行库、旧版库、问题池目录）。
