## 1. 根因与引入轨迹

### 1.1 机制层根因

1. `session/load` 请求失败发生在 `AcpSession.loadSession` 给 `session.sessionId` 赋值之前，因此运行时的协议会话 ID 保持 `null`，证据为 `desktop/src/plugins/acpRuntime/protocol/session.ts:309-332`。
2. 恢复失败分支把旧历史 ID 写入视图状态 `activeSessionId` 和 `recovery.state="failed"`，证据为 `sessionCoordinator.ts:1005-1019`。
3. `openWorkspaceNow` 的草稿复用只判断 `runtime.session.sessionId===null`，没有同时判断视图的 `activeSessionId` 和恢复状态，证据为 `sessionCoordinator.ts:805-819`。
4. 用户点击“新建会话继续”时，`forceNew+draft` 命中该旧恢复失败运行时并直接返回 `{sessionId:null}`，没有创建或聚焦新草稿。前台继续显示旧历史、旧恢复错误和旧草稿。

因此，“打开操作成功”只是复用旧运行时后的快速返回，不代表新会话已建立。

### 1.2 引入轨迹

- 草稿复用和恢复失败状态均随提交 `08e174b` 引入；该提交父版本没有 `sessionCoordinator.ts` 和 `sessionStart.ts` 对应路径。
- 002 只修改销毁清理，没有修改草稿复用判断，不是引入者。
- 现有测试覆盖普通草稿复用和恢复失败，但没有覆盖“恢复失败后新建”的交叉场景。

## 2. 整改方案

### 2.1 最小改法

草稿复用必须同时满足：

- 协议会话 ID 为 `null`；
- 视图 `activeSessionId` 也为 `null`；
- 既有同项目、非列表、草稿模式、无首选历史 ID 和无 Agent 崩溃条件继续成立。

恢复失败运行时因为视图 `activeSessionId` 是旧历史 ID，不再命中复用，流程继续创建并聚焦真正的新草稿。普通连接失败的新草稿两个 ID 都为 `null`，仍可复用并重试，不退化现有能力。

### 2.2 明确不改变

- 不删除 `shouldFocus`、`isCurrent`、revision 或迟到连接防抢焦点守卫。
- 不删除旧历史、不清空旧运行时、不取消正在执行的旧任务。
- 不改变 `session/load`、ACP、Browser MCP、会话持久化和 002 销毁语义。
- 不新增模块、适配器或通用状态框架，不引入循环依赖。
- 不修改 iCode。

### 2.3 失败与兼容约束

- 新连接失败仍留在当前新草稿并展示真实错误，不能回退到旧恢复失败页。
- 普通新草稿重试继续复用连接，避免重复进程。
- 快速切换项目或会话时，迟到的打开结果不得抢回焦点。
- 本方案只有一个额外有效性条件，不属于过度设计。
