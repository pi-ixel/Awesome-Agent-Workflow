# 015 SkillSplice 可维护定义与 Unit 边界

> 状态：已确认的设计方向。本文规定人工维护形式、翻译和执行边界；具体运行能力以实现及验证记录为准。

## 能力与维护形式

SkillSplice 将可组合的流程、执行知识、引用和输入输出契约组织为 Unit。可维护源是一个目录：入口 Markdown 表达该能力的职责、输入和实际流程；子 Unit 各自维护职责、指令和引用；模板、检查标准及其他知识按独立维护和复用需要放在引用文件中。

人审阅、修改的流程是参与编译的流程，不维护一份看似可编辑、实际无效的流程说明。索引和使用说明可以单独作为导航，但不承担执行语义。源目录编译为 Runtime 使用的定义和知识快照；支持的定义可以反向导入为可维护目录。往返必须保留执行关系、参数、条件、循环、知识名称、引用和内容；无法表达时明确拒绝，不得静默丢失或添加行为。

翻译 Skill 时，应将其中需要的流程、方法、约束与模板转化为 SkillSplice 自己的组成内容。可以保留合适的独立模板和引用，但不得把完整原 Skill 作为执行兜底，以回避未完成的翻译。执行时实际使用的指令及知识来自已加载并锁定的 Unit 定义与其引用。

编辑后的源生成新定义供后续运行选择，不修改已启动运行的定义。Unit 的配置、知识和快照属于能力定义；实际产物的存储和解析由宿主提供，不能规定为某个本地路径。

## Unit 拆分原则

拆分的核心问题是：动作是否容易在长任务中被 Agent 遗漏、敷衍或执行变形，以及独立调度后能否提供明确输入、输出和有效检查。可独立验证、需要独立判断或需由 Runtime 控制的动作适合单独成 Unit；需要同一上下文持续交织的推理和工具调用可以保留在一个原子 Agent 动作内。

原 Skill 的章节或自然语言步骤不自动等同于 Unit。拆分不保证质量：每个关键 Unit 仍需定义输入、输出和适合的验证方式；涉及历史行为的判断必须有可访问证据，缺证据时不能报告已确认。

对于属于单次 Agent 动作内部的常规工作方法，应写入该动作的指令或引用知识，不因其中提到某类资料就自动增加独立 Unit、输入输出字段或宿主专用数据装配。是否需要查找、读取和使用项目中可访问的既有资料，由该 Agent 依任务上下文判断；不可访问时如实说明。

## 问题池、交互与 Runtime

问题池是由 question-tracker MCP 提供的独立能力。设计 Agent 在一个原子动作内部使用问题池完成取证、提问和收敛；问题池内部操作不自动翻译为 Runtime 节点。宿主负责为 Agent 提供实际可用的 MCP 连接和相应会话，不能仅因定义中有资源名称就认为能力已经接入。

Agent 在原子动作内向用户提问时，通过 ACP 及宿主交互；Runtime 不替代 ACP 问答。用户未回答、连接中断或状态不明时，不得伪造答案或盲目重试。当前实现是否支持中断后恢复原 ACP 会话，必须按接入代码和测试结果说明。

## dev-design 已确认结构

`dev-design` 定义为组合 Unit，包含设计、独立检查和有界修正：

1. 设计 Agent 在一次动作中通过问题池进行取证与用户问答，撰写设计并自检，输出设计候选和可用证据。
2. 独立检查审阅设计及证据，区分通过、可修正、需要用户决定和无法确认。
3. 只对明确可自动修正的问题执行修正并复查；循环有上限，耗尽时保留反馈并停止。用户决策、权限扩大和缺失事实不能由自动修正猜测。

设计完成检查关注设计自身的完成条件；下游设计门禁可以同时检查设计与测试设计的一致性，两者应避免重复。用户确认设计方向或明确标为草案等条件，必须以可核对证据为依据。
