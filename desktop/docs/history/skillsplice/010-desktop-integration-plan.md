# 010 SkillSplice Desktop 集成迭代计划

> 状态：计划，尚未代表 Desktop 接入或各阶段验收完成。本文安排真实定义、运行观察、模板编辑和运行控制的接入顺序；协议与执行边界以 [核心模型](001-model.md)、[执行语义](002-execution.md)及 [PoC 定义格式](../../poc/skillsplice/definitions/FORMAT.md) 为准。

## 目标与范围

在 AAW Desktop 右侧提供 SkillSplice 窗口，让用户能阅读真实流程、理解 Unit 的嵌套及执行关系、查看运行状态，随后再逐步支持修改模板和发起运行。

按以下顺序交付，每阶段通过验收后再推进下一阶段：

| 阶段 | 交付能力 | 明确边界 |
| --- | --- | --- |
| 1. 真实定义与历史运行 | Desktop 右侧只读查看定义，选择已有运行并查看可核实的节点状态 | 不启动任务、不编辑模板；历史状态不等于实时订阅 |
| 2. 实时运行观察 | 接入真实 Runtime 状态变化和事件驱动动效 | 观察运行，不引入启动、确认或恢复操作 |
| 3. 模板编辑 | 增删改、校验并保存为新模板 | 只影响后续选择该模板的新运行，不修改运行中的实例 |
| 4. 运行控制 | 在边界明确后支持启动、确认和安全恢复 | 不以 UI 操作替代 Runtime 校验、执行门禁和安全恢复判断 |

第一阶段包含**历史运行记录的只读查看**，以满足定义和节点状态映射的验收；第二阶段在此基础上接入实时更新。阶段编号与既有 PoC 报告中的“第二阶段”不是同一套编号。

## 当前基础

- [task-dev 根定义](../../poc/skillsplice/definitions/task-dev/task-dev.json)包含五组顺序 Call：`implementation`、`review`、`resolution`、`codecheck`、`delivery`。[semantic-review](../../poc/skillsplice/definitions/task-dev/semantic-review.json)声明 A、B 两路并行；[finding-resolution](../../poc/skillsplice/definitions/task-dev/finding-resolution.json)声明按 `when` 条件执行的重验和定向复核。
- PoC [Journal 实现](../../poc/skillsplice/runtime.py)记录运行、定义快照、节点和事件；仓库已有 [r5 证据](../../poc/skillsplice/evidence/r5-20261102/)和 [r11 证据](../../poc/skillsplice/evidence/r11-20261102-final/)。现有记录中，跳过可由事件体现，不一定存在对应节点记录；记录不足不能推断状态。证据适用范围和结果以 [证据说明](../../poc/skillsplice/evidence/README.md)及 [008 结果报告](008-poc-results.md)为准。
- [右侧面板状态](../../src/stores/rightPanelStore.ts)和 [面板入口](../../src/ui/right-panel/RightPanel.tsx)已有标签与视图框架；当前 Desktop 尚无 SkillSplice 标签及定义、运行读取接口。现有 [界面原型](../../poc/skillsplice-ui/index.html)使用示例数据，并非真实接入。
- 真实定义中的 `implementation` 和 Reviewer 等为 atomic Unit；原型中为便于展示而写出的内部普通步骤，不能作为定义中存在的步骤呈现。定义中没有内部步骤时，应如实展示 Unit 的类型、说明等已声明信息。
- [009 报告](009-phase2-results.md)记录了 AAW 全链的受控验证与真实运行限制；不能以界面接入或历史可视化，宣称自然需求全链已通过。

## 交互原则

- **执行与包含分开表达**：同一层级的执行顺序、并行分叉和汇合、条件分别依据定义展示；子步骤与父 Unit 的归属使用可辨认的包含层级。展开子 Unit 不改变父级主流程的执行关系。
- **从真实定义生成画布**：展示来自 Call、Unit 和条件的实际结构；不通过节点名称硬编码并行或条件语义。Unit 的显示名称可做可追溯的展示处理，但不能改变 Call 身份或执行含义。
- **保持上下文**：支持右侧窗口内平移、缩放、适应画布、逐层展开和返回，复用 Desktop 现有颜色、面板及放大能力。运行状态和结构展开的动效分别对应真实状态变化和用户操作。
- **定义与运行分开**：查看模板时读模板定义；查看已有运行时，优先依据该运行的定义快照及身份映射，不把当前模板的变化套用到历史运行上。身份不匹配或快照不可读取时明确提示，禁止猜测映射。
- 循环示例仅供界面讨论。PoC 格式 v1 没有通用循环原语；有限重试或适配器内部循环不等于通用循环流程支持。

## 阶段 1：真实 Desktop、定义与历史运行

### 工作内容

1. 在 Desktop 右侧面板注册 SkillSplice 标签，接入已有标签管理、项目上下文及面板放大能力。将原型的图形交互转换为 React 组件，沿用 Desktop 样式和组件规范；隐藏尚不能真实工作的编辑、启动、确认等入口。
2. 建立只读的数据访问边界：加载指定的 PoC v1 bundle，解析 Unit、Call、`groups`、`parallel`、`when` 及引用关系，向 UI 输出稳定的定义视图。选择复用现有加载逻辑或构建等价适配层时，应保持校验语义一致；加载失败、缺失文件、未知格式和不支持的语义要明确提示。
3. 用真实定义构建横向流程和可展开的包含层级；按组表达顺序，按声明表达并行、条件和汇合。显示可追溯的 Call / Unit 信息，并提供进入子 Unit、返回和定位。
4. 提供已有运行的选择及**只读**读取能力，以 run id、调用路径、Unit 身份和运行快照为依据映射节点；允许从既有归档中选择记录。读取 SQLite 时采用只读访问和一致性读取，不修改证据或影响运行。跨进程访问方式和接口由实现确定，不假定现成服务已存在。
5. 建立状态投影：保留原始状态和证据来源；把 node 状态与相关 event 合并展示，明确区分运行中、已完成、失败、跳过、未开始和无法确认。只有有明确证据时才显示“跳过”；缺失记录、定义不匹配、无法读取和执行结果不明不得被推断为成功或跳过。历史记录没有的时间、时长或细节不臆造。

### 验收

- 在真实 Desktop 打开右侧 SkillSplice；页面读取实际 bundle，准确展示 task-dev 的五个一级 Call 及其顺序。
- 展开或进入 `semantic-review`，看到属于该 Unit 的两个并行 Call `a`、`b`，分别引用 `reviewer-a`、`reviewer-b`；展开 `finding-resolution` 可见真实条件及其来源。
- 用户能从归档选择一份已有运行，画布节点状态能逐项追溯到该 run 的 node / event；运行与定义身份对不上时明确提示，不显示伪造状态。
- 至少用两份不同结果核对映射：[r5](../../poc/skillsplice/evidence/r5-20261102/) 的 `/implementation`、`/review/a`、`/review/b` 为 `passed`，`/codecheck` 为 `unknown`，条件跳过可从 `skipped` 事件核对；[r11](../../poc/skillsplice/evidence/r11-20261102-final/) 的五个一级 Call 与两个 Reviewer 记录为 `passed`。保留各自证据的适用限定，不跨 run 拼接结果。
- atomic Unit 不出现定义中没有的内部步骤；读不到定义、记录或遇到未支持语义时有可理解的错误或未知状态。演示计时器、示例节点和假运行操作不进入真实数据视图。
- 在正常和较窄右侧窗口验证展开、返回、平移、缩放及标签切换；组件与数据映射测试覆盖并行、条件、跳过、未知及定义身份不匹配，并进行真实 Desktop 冒烟验证。

## 阶段 2：实时运行记录与状态动效

### 工作内容

1. 在阶段 1 的历史状态投影上，定义并接入 Runtime 到 Desktop 的只读快照及事件接口；先验证真实 run、调用路径、Unit 身份、尝试次数与画布节点的对应关系，再接实时推送。事件字段和运输方式以实际实现为准。
2. 处理并行运行、重复或乱序事件、断线、重连和快照补齐，避免旧事件覆盖新状态或不同运行互相串扰；无法确认连接或节点状态时如实显示。
3. 运行中节点和活动分支以克制动效突出，完成、失败、跳过、无法确认有可辨认的静态状态；动效由真实状态或事件驱动，支持减少动态效果。禁止前端定时器自行推进业务状态。
4. 提供可选的当前节点定位或跟随；用户手动操作画布后不持续抢夺视角。

### 验收

- 使用可复现的真实 Runtime 事件验证并行节点各自的状态变化；终态与同一 run 的 Journal / 快照一致。
- 断线显示连接或状态不可确认；重连后以可信快照补齐，重复、乱序及跨 run 事件不造成错误状态。
- 节点动效随真实状态开始和停止；无事件时不自动向下一节点推进。历史记录静态展示不被误称为实时运行。

## 阶段 3：模板编辑与保存

### 工作内容

1. 在真实定义模型上提供步骤和子 Unit 的添加、编辑、删除及顺序调整，按已支持的定义语义编辑并行组和条件；不支持的结构明确提示，不静默改写。
2. 保存前复用或对齐 PoC 加载器校验，检查引用、身份、输入、条件、知识快照等约束，定位到可修正的位置。保存方式应避免部分写入并保留可恢复的原模板。
3. 编辑形成可识别、可重新加载的新模板版本或新定义身份；不覆盖历史运行的定义快照。保存后需由用户或后续流程明确选择新模板供新运行使用。

### 验收

- 在副本上完成增删改、并行和条件编辑，保存后重新加载与展示一致；无效引用、条件或格式被拒绝并可定位。
- 修改前的历史运行仍绑定原定义快照；新模板有可区分的身份，且不会改变正在运行或已完成实例。
- 编辑仅改变模板；无启动或重试请求被隐式发出。

## 阶段 4：启动、确认与安全恢复

### 工作内容

1. 先明确 Runtime 服务边界、生命周期、资源与输入校验、进程中断和结果回传，再开放从 Desktop 选择模板、配置输入与启动真实运行。
2. 明确确认点的请求、展示、答复与持久化契约，确保答复只作用于对应运行和待确认点；过期、重复或不匹配的答复得到明确处理。
3. 建立恢复前提：验证定义快照、工作区、已发生的外部操作和证据；对于结果不明或不具备安全重试依据的动作停止并提示，不盲目重发。现有 PoC 的阶段驱动和停机行为不能直接当成通用暂停/恢复能力。

### 验收

- 在隔离测试工作区通过真实入口启动，输入与资源校验失败时不触发执行；运行记录可在阶段 1、2 界面中准确查看。
- 确认点未答复时不越级推进；正确答复、过期答复和错误 run 的答复均按契约处理。
- 覆盖安全恢复与不安全恢复：可证明可恢复时继续，不可证明时保持阻塞并解释原因；历史证据不跨 run 拼接。
