# 007 SkillSplice PoC 技术验证工作指导

> 读者：负责实现和验证 PoC 的工程师。本文是交接任务书；具体格式和实现方式由实施者在架构边界内确定。本文所述目标是待完成的工作，不代表已有实现已经满足。

## 1. 要解决的问题

搭建一个可加载 SkillSplice 定义的 Runtime，将现有 `task-dev` 的工作要求翻译为独立的 SkillSplice 定义和配套知识，并验证 **Runtime 能否依照该定义驱动 iCode，完成一个真实 Task 的完整开发流程**。

验证对象是下面这一条链，而非分别演示其中几个组件：

```text
task-dev 原始 Skill 和知识
        ↓ 翻译、固定版本
SkillSplice 定义 + 知识资源
        ↓ 加载、校验、绑定工作区和任务输入
SkillSplice Runtime
        ↓ 按定义控制步骤，调用 iCode / 验证工具
实现与测试 → 两个只读 Review → finding 处置与重验 → CodeCheck → 交接与完成验收
        ↓
同一次运行的状态、报告、代码变化和验证证据
```

最终要回答：**声明式定义能否表达 task-dev 的关键约束，Runtime 能否真正执行这些约束，以及真实 iCode 能否在该控制下完成任务。** 如果因真实依赖不可用未能走到最后，应保留运行并明确报告阻塞，不能用模拟结果宣称完整通过。

本任务是技术验证，不要求交付生产级平台、Desktop 界面或正式协议标准。实现应支持后续替换 Agent 和引擎，但 PoC 的真实端到端验收以 iCode 为准。

## 2. 先建立共同认识

### 2.1 SkillSplice 是什么

SkillSplice 是面向 AI 复杂任务的声明式能力协议。一个 **Unit** 将流程、知识和对外契约组合成可复用能力；Unit 可以调用其他 Unit，组合后的结果仍然是 Unit。它可以类比带知识和契约的函数：输入和输出可描述，内部可以是程序、工具、人工或 Agent，且允许修改工作区等副作用，因此不要求是纯函数。

| 概念 | 在本 PoC 中的作用 |
|---|---|
| Unit | 定义一项能力，如完整 task-dev、语义 Review 或单个 Reviewer。 |
| Call | 在流程中调用一个 Unit，并提供本次输入及绑定。 |
| Link | 表达调用之间的依赖、分支及交接关系。 |
| Port | 在需要明确交接数据时声明输入、输出和约束；不要求所有协作数据都通过 Port。 |
| Resource | 描述固定的知识，以及运行时绑定的代码工作区等资源。 |
| Verification | 描述完成条件和验收方式；Agent 返回并不等于验收成功。 |

Runtime 负责执行声明的依赖、并行、条件、验收和恢复规则，Agent 负责调用内部的理解与操作。流程控制确定，不代表模型结果确定，也不代表 AI 自称通过就证明代码正确。

Unit 的流程、知识、契约与固定子 Unit 引用共同决定其身份；内容改变应形成新身份。修改模板用于后续新运行，**本阶段不承诺修改、迁移正在运行的实例**。资源绑定则属于运行实例：同一 Unit 可以用于不同隔离工作区。

### 2.3 目前实际做到了哪里

以下是已有记录，不是本次新验收：

| 方面 | 现状 | 不能由此推断 |
|---|---|---|
| Runtime | Python 原型有定义快照、SQLite 记录、组合、并行、验收和有限恢复；记录中 18 项受控测试通过。 | 已有通用的独立定义格式、完整 task-dev 或生产级 Runtime。 |
| SkillSplice + iCode | 真实 iCode 曾在隔离 OpsCopilot 副本中修复问题并做两路 Review。 | 两次实验合起来等于一次完整端到端执行。定义和 prompt 主要写在 `real_case.py` 中，finding 处置还依赖案例专用人工续跑。 |
| 原有 AAW task-dev | 另一次实验执行了真实 AAW 工作单的一部分，状态记录在 `006`。 | 该实验已由 SkillSplice Runtime 端到端驱动，或者工作单已完成。 |
| CodeCheck | 仓库当前配套脚本声明为临时实现，输出标识 `mock-codecheck`。 | 返回 0、打印 passed 或 `go vet` 通过就代表正式 CodeCheck 通过。 |

因此，当前缺口不仅是 CodeCheck，还包括：**可加载的定义、完整的流程翻译、由 Runtime 驱动的处置与交付，以及同一次真实执行的完整证据链**。历史证据可能随本机清理或代码变化失效；复用前核验，缺失时重跑，不编造。

## 3. 完成后应呈现什么

接手人交付的 PoC 至少应让另一位工程师能够：

1. 读取一份独立于 Runtime 源码保存的 task-dev 定义，看到所引用的子 Unit、知识、输入、资源、依赖、条件和验收要求。
2. 用公开的本地入口加载并校验该定义，将某个 Task 和隔离工作区绑定到一次运行，而不是修改 Python 源码中为 OpsCopilot 定制的流程与 prompt。
3. 观察 Runtime 依照定义调用真实 iCode，按 task-dev 关键步骤推进；两个 Reviewer 独立且只读，finding 进入实际处置和必要重验。
4. 从记录追溯本次运行的固定定义及知识、输入和工作区、每次调用及尝试、分支原因、工具结果、Review 原件、处置、验证和最终结论。
5. 在真实 CodeCheck 可用且全部门禁通过时得到成功；不可用、失败或结论不明时看到准确阻塞位置和证据，而不是虚假的成功。

PoC 可以使用 JSON、YAML 或其他易审阅格式；格式需有版本标识、加载和校验规则。示例格式不是正式标准，也不要求兼容未来规范。允许某些具体步骤使用 Agent 指导，但**不能把需要 Runtime 控制和观察的整条流程压进一个 prompt**。

## 4. 范围与实施选择

### 4.1 本次必须覆盖

- 递归组合、显式串行与并行、条件分支、声明式完成条件、有限重试、记录和保守恢复；对已设计的 POC-01～13 给出可追溯结果。
- 从原始 task-dev 到可执行 Unit 与知识的可检查翻译，包含适用模式、输入、流程、异常、报告、完成边界；重点验证轻量模式的单个 Task。严格模式也要在翻译清单中映射并给出明确支持/不支持结论，不得混称已验证。
- 真实 iCode 实现、两个只读审查、必要修复/重验、CodeCheck、交接的同一次运行；真实环境不具备依赖时按阻塞报告。
- 隔离 OpsCopilot T1 和 TD-01～06，保存基线、变更与测试证据。

### 4.2 不需要为本次 PoC 扩张

不要求 Desktop UI、任意程序自动翻译、通用流程编辑器、运行中修改/迁移实例、自动解决并行工作区冲突、生产级分布式容错或在所有任务上证明 Agent 的正确性。可以选用现有 Runtime 或候选引擎；完整候选引擎横向选型不是证明上述主链路的前置条件。

### 4.3 task-dev 与 AAW 的状态边界

现有 task-dev 有工作流模式和单独执行模式：前者由 AAW CLI 工作单及 `guidance` 控制，后者跳过 CLI 状态命令和 `done`。本 PoC 推荐先做 **SkillSplice 自主管理的任务执行**：使用准备好的明确任务输入，由 Runtime 维护调用和验收状态，完整执行适用的开发、Review、CodeCheck 与交接要求；可以参考工作流模式的 `implementation.json` 和 `completion.json` 组织证据，但不得虚构 CLI 返回或把自管状态叫作 AAW 工作单状态。

若为了兼容而接入 AAW 工作流，必须使用真实工作单、输入和 CLI 返回的指引，由 CLI 管理其状态，不直接修改 `state.json`；`next` 可能推进阶段，不是只读查询。说明 CLI 和 Runtime 分别对哪些状态负责，以及相互确认、失败时如何停止；不得让两套状态互相覆盖或伪造上游门禁。是否支持真正的 AAW `done`，单独报告。

### 5.1 固定输入与检查环境

2. 确认 Python、Git、Go 和 iCode 可用，记录实际版本、iCode 执行方式及模型配置的非敏感标识。只记录配置存在与否，不保存密钥、令牌或完整环境变量。iCode 不可用时，先完成格式和受控执行，不要伪报真实接入。
3. 测试源为 `D:\dev\tmp\OpsCopilot`，指定基线提交为 `3f5f4e696721ed768a5ad67224cba28f00ce1c9a`。原目录已有未提交内容：不在其中执行会修改文件、暂存区或工作流状态的测试，不执行清理或重置。
4. 在新建的独立目录准备基线副本和证据目录，记录来源、提交、初始状态与绑定路径。先核对目录未被占用及提交存在；可使用本地 clone 后检出指定提交。不要复用旧实验目录冒充新运行。若指定提交不可用，停止该真实案例并报告。
5. 依据 [005](005-task-dev-test-case.md) 准备 T1 的设计、测试规格与任务范围。若接入真实 AAW 工作流，按其要求准备并通过真实上游门禁；不得用 005 直接冒充工作单或门禁。
6. 检查 CodeCheck 是否为正式可用版本、调用方式和原生结果。仓库里的临时 `mock-codecheck` 只可用于标明身份的受控测试；没有真实版本时提前标注最终端到端可能在该门禁阻塞，但继续完成不依赖它的工作。

可使用 `git rev-parse HEAD`、`git status --short`、`git cat-file -e <提交>^{commit}`、`Get-Command icode` 和 `go version` 等命令做只读核查。具体创建命令按本机 Git 配置调整，务必在确认新目标路径后执行。

### 5.2 先建立翻译对照表

开始实现前，逐段阅读原始 Skill、Review prompt/schema 和 CodeCheck Skill，建立可随交付提交的对照表。每一项注明原文位置、翻译到哪个 Unit/知识/验收、由 Runtime 还是执行者负责、如何验证、是否支持。至少覆盖：

| 原有要求 | 翻译时必须说明的边界 |
|---|---|
| 模式与输入 | 严格/轻量的权威来源、任务范围、前置任务和设计门禁；缺失或冲突时停止。 |
| 实现与测试 | 单 Task 范围、设计契约、测试设计是下限、补充测试、失败回流及构建检查。 |
| 状态和报告 | 自管或 AAW 模式下的状态权威、实现与完成证据；哪些 CLI 命令不适用。 |
| 语义 Review | 两路独立只读角色与覆盖范围、允许提供的上下文、扩展规则、报告格式和原件保留。 |
| finding 处置 | 主执行者裁决、修复或有依据拒绝、受影响测试、必要时原 Reviewer 定向复核。 |
| CodeCheck | 调用配套 Skill/真实 CLI，原生结果、低风险修复及复查；不可用或高影响事项暂停。 |
| 交接和停止 | `tasks-overview.md` 执行记录、补充测试及残余风险、候选提交信息、完成验收；不暂存、提交、推送、发布或开始下一 Task。 |

原文存在解释空间时记录实现选择和影响。不要只复制 `SKILL.md` 然后将它作为一个黑箱执行，也不要把未实现的要求隐藏在长 prompt 中声称已经由 Runtime 强制。

## 6. 工作分解与技术要求

### 6.1 定义格式与加载

1. 设计最小的可序列化格式，表达 Unit 身份与类型、固定知识和子 Unit 引用、所需资源、必要输入输出、Call 和 Link、并行与条件、Verification 及有限重试策略。为格式与加载器增加版本标识；不支持的字段或语义应拒绝或明确报不支持，不能静默忽略。
2. 落盘 task-dev 和子 Unit 定义及必要知识。知识可由受控快照或带摘要的固定引用实现；启动时校验实际内容与声明一致，避免文件被修改后仍以旧身份运行。
3. 确保子 Unit、知识或契约变化时相关 Unit 身份变化；旧版本保持可引用，父 Unit 引用变化时父身份也变化。运行固定在选定快照上；新模板不会改变已有运行。
4. 解析前检查依赖缺失、错误引用、循环引用、资源缺失、输入不合法、不可执行条件等问题，并报告定位信息；启动前失败不能产生伪成功。

以下仅展示形状，**不是既定 schema，也不能直接作为可运行配置**：

```yaml
unit: task-dev
kind: composite
knowledge: [task-dev-guidance@固定版本]
resources: [workspace]
calls:
  - id: implement
    unit: implementation@固定版本
  - id: review
    unit: semantic-review@固定版本  # 子 Unit 中明确声明 A/B 并行
    after: [implement]
  - id: resolve
    unit: finding-resolution@固定版本
    after: [review]
  # 还需表达重验、必要时原 Reviewer 复核、CodeCheck、交付与验收。
```

同一份 Runtime 在不修改源代码的情况下应能加载并运行另一份小型组合定义，验证其控制逻辑不是针对 `task-dev` 名称或 OpsCopilot 写死。小型例子可以使用可控执行者，不要求另做真实业务项目。

### 6.2 本案例的数据如何流转

输入、共享工作区和报告的作用不同；具体字段由实施者定义，但必须能追踪下列关系：

| 阶段 | 主要输入 | 主要输出及交接 |
|---|---|---|
| 启动 | 选定的 task-dev 固定定义、T1 设计/用例/任务范围、隔离工作区绑定。 | run ID、定义与知识身份、工作区及输入引用；缺少必需输入时不启动开发。 |
| 实现 | T1 授权范围、设计和用例、工作区。 | 工作区内的实现和测试、测试命令与结果、实现阶段证据；验收通过才启动 Review。 |
| 并行 Review | 同一 Task 与已实现的变更、各自权限范围及审查知识。 | A/B 各自产生独立报告；汇聚后单独形成合并报告，保留 finding 到原报告的对应关系。 |
| 处置与重验 | 合并 finding、原报告和工作区。 | 逐项处置、可能的代码变更、受影响测试结果，以及需要时的原 Reviewer 复核引用。 |
| CodeCheck | 工作区、真实扫描器及其调用约定。 | 扫描器原生结果；若按规则修改代码，交回重验并复查。 |
| 交付验收 | 全部阶段状态与证据、工作区 diff。 | 任务交接、候选提交信息、最终 Verification 和真实结论。 |

以上是步骤之间需要核对的交接，并不要求把代码内容通过 Port 复制；代码可以留在绑定的共享工作区，报告可以按引用传递。

### 6.3 Runtime 与 iCode 适配

1. 将调度、状态、条件和验收放在 Runtime；将具体 Agent 调用放在 iCode 适配器。定义提供该调用所需的能力、知识、输入和输出契约；不要在通用调度器里按案例名称分支生成整套流程。
2. Runtime 决定何时调用：实现成功且通过验收才可启动 Review；两个 Reviewer 均完成并分别通过报告有效性验收后才可汇聚。Reviewer 报告有 finding 仍可代表该 Review 已完成，finding 闭环另行判断。
3. 两位 Reviewer 使用独立执行上下文，按原 Skill 划分关注点，只提供必要输入。使用 iCode 可验证的只读权限或隔离机制，并保存可检查的权限配置和执行证据；只有 prompt 写“只读”或结束后碰巧没有 diff，不足以证明权限被限制。若本机 iCode 无法提供可验证的只读执行，应明确阻塞或限制，不能宣称该要求已通过。
4. 对返回码、超时、不可解析输出、报告不合规、工具缺失和权限问题分开记录。调用结束、执行成功、Verification 通过各自独立；执行者的成功文本不能替代工具输出、结构校验和完成门禁。
5. 尽可能以真实命令和原生输出作为测试与扫描证据，并记录命令、退出状态及产物引用；记录时遮蔽敏感数据。任务实现 Agent 应遵守当前 Task 范围和不操作 Git 暂存区等约束，运行前后核查。

### 6.4 Review、修复与交付

- 依据原始 Review prompt 约束两位 Reviewer 各自的报告片段；`review-report.schema.json` 约束的是主执行者合并后的报告，不要求单个 Reviewer 伪造两个角色。两份原始 Review 报告独立保存；合并、去重和裁决形成单独记录，不回写原报告伪装成复核结果。
- 为每条 finding 建立可追踪的 `fixed` 或 `rejected` 处置及依据；成立的问题由主执行者修复，拒绝需给出证据。修复后执行受影响测试和必要构建；原 Skill 指定的高风险或语义变更由原 Reviewer 定向复核，保留该复核报告。不能保证找到原 Reviewer 的会话/身份时，明确标记为无法满足并暂停，不静默换人冒充。
- 对 finding 修复、复核和 CodeCheck 问题修复设置有限循环及退出条件；失败、超限或需要用户对高影响方案决策时停止并记录，不强行推进。
- CodeCheck 按配套 Skill 的调用与原生结果处理：低风险局部问题可按规则修复、重验并复扫；高影响修改需等待用户决策；不可用或无法判断时阻塞。不得更改规则、用 `go vet` 或模拟输出替代正式扫描。
- 按所选模式生成最终交接：任务状态、文件、实现、设计偏差、待处理事项、后续须知、证据引用，以及「实现期补充与残余风险」；从任务和实际实现生成候选提交信息并核对 diff。仅当所有必需条件成立时才标记完成。

### 6.5 执行记录和恢复

至少记录：定义与固定知识身份、运行 ID、输入及资源绑定、Call 路径与实例、每次尝试、启动/结束、依赖与条件选择、执行结论、Verification 结论及依据、报告和产物引用、阻塞原因与处理记录。

持久化后重启时，已确认结果仅在定义、输入、工作资源及证据仍适用的可证明范围内复用；外部操作已经发出但结果不明时停在 `unknown` 或等价状态，不盲目重试。先明确手动确认/续跑的入口、授权和证据，再实现恢复。不要把案例专用续跑脚本包装成通用恢复能力。动态展开只执行定义预先声明的规则，不代表运行中修改定义。

## 7. 验证方案与通过条件

### 7.1 分层验证

| 层次 | 要做什么 | 可以得出的结论 |
|---|---|---|
| 格式和翻译 | 加载真实文件；校验固定知识、子引用、缺失资源、错误定义和翻译对照表。 | 定义可被解析、引用关系可追踪；覆盖与不足可审查。 |
| Runtime 受控场景 | 运行 [004 的 POC-01～13](004-poc-design.md)，使用可控执行者、屏障和进程中断注入。分别记录通过、失败、不支持。 | 对实际覆盖的执行语义有证据；不代表真实 Agent 已完成任务。 |
| 完整流程控制 | 用模拟 Agent/扫描器覆盖无 finding、有 finding、修复/重验、原 Reviewer 复核、CodeCheck 失败/不可用、交付缺证等路径。 | 验证分支与门禁；模拟结果不能充当真实扫描或真实 Review。 |
| 真实任务 | 同一个 Runtime run 加载 task-dev 定义，驱动真实 iCode 在隔离副本执行 T1，并执行真实测试和 CodeCheck。 | 只有所有必要环节及证据成立，才证明此案例的端到端通过。 |

除 POC-01～13 外，至少验证以下容易造成误判的负向情况：缺少 Reviewer 报告或其中一方未完成；finding 未处置或修复后未重验；需要原 Reviewer 复核但无有效报告；CodeCheck 是 mock、缺失、异常或失败；交接缺少必填项；Agent 返回成功而验收失败；运行中断且外部副作用结果不明。每种情况都不得得到最终成功。

使用屏障而不是根据日志时间差证明并行：两名 Reviewer 均已启动并停在屏障时，下游不得启动；任一未满足汇聚条件也不能推进。只读隔离、条件分支和恢复需要相应机制及可检查证据，而非仅检查 prompt 文本。

### 7.2 OpsCopilot 真实案例

功能验收细节以 [005](005-task-dev-test-case.md) 为准：负数 Cursor 与零等价；上界及有效位置行为保持；返回区间有效；维持字节位置语义及接口，不扩大到 Unicode 位置转换。记录修改前实际复现负数 panic、修改后 TD-01～06 和目标包测试结果；正常位置的原有行为须有独立基线，不可用修改后的结果作为自身预期。建议项比较按内容多重集合处理，不依赖不稳定顺序。

工作范围为单个 T1；不修改原工作区，不操作 Git 暂存区、提交、推送、发布，不开始其他 Task。项目的 `AGENTS.md` 和真实设计冲突时按 task-dev 规则停止并记录，不自行更改设计以迁就实现。

### 7.3 三种结论

| 结论 | 判定 |
|---|---|
| **端到端通过** | 同一个真实 run 加载固定定义并由 Runtime 驱动 iCode；完整适用流程、真实 CodeCheck、任务测试、Review/处置/必要复核、交接和最终 Verification 全部通过，证据闭合。 |
| **部分验证、整体阻塞** | 某些层通过，但真实 CodeCheck、只读权限、原 Reviewer 复核或其他必需条件不可用；准确记录停点和已完成工作。即使模拟链路全绿也只能作此结论。 |
| **验证失败** | 已执行环节违反定义、测试或验收，或证据证明目标无法成立；报告触发条件、预期、实际和可复现材料。 |

如果真实任务恰好没有 finding，不能声称真实 finding 修复分支已经通过；受控分支测试应单独报告。反之，受控测试中的 finding 也不能冒充真实 Review 的发现。补上真实依赖后，可按已实现并验证的安全恢复机制续跑；若无法证明旧结果仍适用，应使用新隔离副本重新执行，不把不同 run 拼成一个通过。

## 8. 执行顺序与检查点

| 阶段 | 工作 | 退出检查点 |
|---|---|---|
| A 基线 | 环境、原始 Skill、现有代码、隔离资源和翻译对照表。 | 输入版本与已知依赖明确；真实缺口有记录。 |
| B 定义 | 最小格式、加载校验、固定知识和 task-dev 定义。 | 从文件加载，递归引用和身份变化可检验；不支持项明确。 |
| C 调度 | Runtime、iCode 适配边界、Verification、记录及安全恢复。 | 受控测试通过或逐项报告失败；另一份组合定义无需改 Runtime 即可运行。 |
| D 流程 | Review、finding、重验、CodeCheck 和交接接入。 | 正负分支均能被触发，缺失证据不能成功；模拟结果明确标识。 |
| E 真实运行 | 新隔离副本、真实 iCode、T1 和真实工具。 | 每个实际步骤关联同一 run；全部通过或在真实阻塞处停止并保留证据。 |
| F 交付 | 整理代码、定义、测试和结果报告。 | 另一位工程师可按文档复现，并能检查每一结论。 |

这些阶段可以交叉推进；遇到真实 CodeCheck 不可用，不应停止可以独立完成的定义、Runtime 和模拟分支工作，也不得通过模拟扫描绕过真实运行的门禁。

## 9. 交付清单与结果报告

提交或移交以下内容；如某项不存在，明确写未完成及原因：

1. PoC 源码、运行入口及环境准备/复现说明；独立的 Unit 定义、固定知识、格式说明和翻译对照表。
2. 适配器、运行记录与恢复方式说明：如何配置 iCode、如何验证 Reviewer 只读、如何绑定资源、如何区分自管运行与 AAW 状态。
3. 受控测试清单与结果：POC-01～13、其他负向场景、命令、结果及证据路径；不支持的功能不得标记为通过。
4. 真实案例证据：代码与定义版本、基线/隔离副本路径、run ID、输入引用、各 Call 和 Verification 状态、两份原始 Review、所有 finding 处置与必要复核、原生 CodeCheck 结果或阻塞、测试命令与输出、最终交接与实际变更。确保路径不包含密钥等敏感信息，必要时提供脱敏副本。
5. 一份结论报告，逐项回答：做了什么、哪些真实执行过、哪些是模拟、与原 Skill 有哪些差异、哪些失败/阻塞及其影响、后续最短动作是什么。证据引用应可定位到具体文件和运行；若依赖本机临时目录，也应注明保存位置及可用性，不把临时路径当作永久归档。

可以沿用 [006](006-poc-results.md) 的结果组织方式，但新增结论必须以本次实际代码和证据为准；历史结论保留为历史记录，不能覆盖不成功的记录。交付时提供一条明确的总体结论：端到端通过、部分验证且阻塞，或验证失败。

结果报告可按下面的格式填写：

```text
总体结论：端到端通过 / 部分验证且阻塞 / 验证失败
代码与定义：提交、工作区状态、Unit 和知识身份
目标及环境：任务、隔离路径、iCode/Go/扫描器版本或不可用原因
翻译覆盖：已覆盖、未覆盖、与原 Skill 的差异及理由
受控验证：场景 ID → 通过/失败/不支持 → 证据
真实运行：run ID → 每阶段状态 → 调用与验收证据
任务结果：修改文件、TD 用例与测试结果、两份 Review、处置与必要复核
CodeCheck：真实原生结果，或具体阻塞；注明是否仅做过模拟
交接与限制：最终状态、候选提交信息、补充测试、残余风险
下一步：解除阻塞或修复失败的具体动作
```
