# 002 SkillSplice 执行语义

本文承接[核心模型](001-model.md)，说明声明式流程的执行和验收原则。

## 执行语义

### 声明式控制

Unit、Call 和 Link 构成声明式流程定义。关键步骤若需要由 Runtime 强制控制、独立观察或验收，应显式建模；Runtime 不能自行跳过被选中且必须执行的 Call。其他执行细节可以保留在 Unit 内部的指导中。

画布和未来可能提供的函数式代码写法，是编辑或呈现定义的方式；它们不能改变底层声明的执行关系。v0.1 不规定具体语法，也不承诺支持将任意程序自动转换为可执行流程。

Runtime 按定义控制流程，不把关键执行顺序隐式交由 Agent 自行决定。这里的确定性是指对声明的控制规则作一致执行，不意味着 Agent 内容生成或 AI 判断的结果确定。

### 分支、并行与动态展开

- **分支**：优先使用明确规则；规则无法覆盖时，可以使用已声明的 AI 判断，并记录判断结果及必要依据。
- **并行**：只有编排时明确声明可并行的 Call 才允许并行；Runtime 不自行扩大并行范围。协议不强制冲突检测、锁定、隔离或自动合并，共享资源冲突由具体 Unit、宿主或使用者处理。
- **动态展开**：编排时定义展开规则，运行时根据实际数据决定实例数量，并记录实际展开的执行。动态展开属于既定规则的执行，不等于运行中修改流程定义。

未被选择的条件分支按定义跳过；必要的汇聚条件和下游推进方式由流程定义表达。

### 完成与验收

每个可执行 Unit 都必须有明确完成判定。执行者返回只说明一次执行动作结束，不自动意味着 Unit 验收成功。

```text
执行者返回结果 → 执行 Verification → 通过：Unit 成功
                                      未通过：按定义处理
                                      无法判断：等待进一步处理
```

Verification 可以采用规则或程序、AI、人工确认，或其组合。Runtime 应记录验收结论及其依据；组合 Unit 的成功不能绕过被选中且必要的子调用，也不能绕过自身验收。验收机制检查的是声明的条件，其结论不等同于对所有业务正确性的保证。

### 失败与恢复

自动重试和修复应有明确边界。恢复优先利用已确认的状态和结果，避免无依据地重复已完成工作；外部副作用是否发生不明时，暂停并确认，不盲目重试。

执行记录至少应能够关联所用定义、资源绑定、Call 执行和尝试、结果及验收依据，支持理解失败位置和恢复决策。运行状态不能只依赖 Agent 的会话上下文或界面显示。状态变化与启动、输入交付等外部操作需要可靠衔接；具体持久化机制由实现决定。

历史结果是否可以复用，需要考虑定义、输入、依赖、工作资源及外部副作用是否仍适用。v0.1 不承诺完整的自动失效分析；无法确认时采取保守处理。

### 产物

产物保留在原有存储中。协议关注产物引用、产生或使用它的执行，以及它与验收证据的关系；不要求把产物迁移到统一存储。引用可访问性和持久化由实现与相应基础设施负责。
