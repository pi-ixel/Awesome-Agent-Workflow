# 004 SkillSplice PoC 设计

> 状态：待评审的验证方案，不是已实现的协议或执行引擎。实际试验前应固定代码、定义和执行环境，并确认测试工作区的建立方式。

本方案使用 [OpsCopilot task-dev 测试需求](005-task-dev-test-case.md)，验证 SkillSplice 架构中最关键的能力。测试目标是执行语义及其证据，不以选择某个引擎为前提。

## 1. 目标与范围

以一项真实但范围受控的代码修改为载体，验证：递归组合、明确声明的依赖和并行、执行与验收分离、有限恢复、定义不可变和工作资源绑定。PoC 可以通过适配层使用候选引擎；每个候选方案应运行同一套语义场景并报告不支持的部分。

首轮使用可控的模拟执行者和隔离工作区，验证 Runtime 自身的行为；随后才用真实 Agent、测试命令和 CodeCheck 验证接入。模拟结果只能证明对应的流程控制，不能证明真实 Agent 遵循任务或实际代码质量合格。

不在本 PoC 中承诺运行中修改或迁移实例、支持任意程序转换为流程图、自动解决并发文件冲突，或构建完整 Desktop 界面。

## 2. 现有 task-dev 的控制边界

当前 [task-dev 指导](../../../skills/task-dev/SKILL.md) 和 [TaskDevManager](../../../skills/aaw-workflow/scripts/cli/task_dev.py) 共同承担控制。两者的约束不能等同：

| 环节 | 当前机制 | 可以确认的边界 |
|---|---|---|
| 工作单与输入 | 严格模式使用模块设计、测试设计和设计门禁；轻量模式使用 `dev-design.md`、`test-design.md` 和 `tasks-overview.md`。 | 输入由工作流定义和工作单标注；必须按所选模式准备，不能只提供本 PoC 需求文本就声称满足工作单。 |
| 状态获取 | `next` 返回 `task_dev.guidance`；运行中的 `next` 可读取并校验一个阶段报告，`status` 用于查看；`next --peek` 为只读查看。 | 阶段进度以 CLI 状态为准；普通 `next` 不能当作无副作用的状态查询。 |
| 实现提交 | `initialized` 阶段要求实现、测试并提交 `implementation.json`；CLI 校验状态字段和检查项后进入 `implemented`。 | CLI 校验提交内容；它本身并不由此证明 Agent 真实执行了测试。 |
| Review 至交付 | `implemented` 后由指导要求两个只读 Reviewer、处置与重验、CodeCheck、回填和候选提交信息；一次提交 `completion.json`。 | 这些动作在 Skill 中有明确顺序，但新流程在 CLI 层以合并报告校验，不应声称 CLI 已逐个调度或观察了这些动作。 |
| 完成门禁 | CLI 校验合并报告的结构、Reviewer 字段、finding 处置、CodeCheck 声明和交付字段；`done` 检查阶段证据及工作记录。 | 结构字段和引用通过不等于报告的真实内容、实际测试执行或质量已被独立证明；具体存在性检查范围以代码为准。 |

已处于旧阶段的存量工作流还有兼容路径；本 PoC 使用新任务的 `initialized → implemented → prepared → completed` 主路径，不修改现有 CLI，也不把 PoC 的行为宣称为当前 CLI 已具备的能力。

## 3. 最小流程设计

```text
TaskDev Unit
  ├── Implementation Unit
  │     ├── 实现当前 Task 并执行指定测试
  │     └── 验收：测试与 implementation 提交满足约定
  ├── Review Unit
  │     ├── Reviewer A ─┐
  │     └── Reviewer B ─┴─ 并行，均只读；汇聚两份结果
  ├── 按 finding 进行处置；有代码修改时重验，必要时原 Reviewer 定向复核
  ├── CodeCheck；若修改代码，再运行受影响测试
  └── 回填与交付验收：completion 报告、执行记录和候选提交信息
```

`TaskDev` 是组合 Unit；`Implementation`、`Review` 和 CodeCheck 是可引用 Unit，Review 的两个 Call 明确声明并行。具体 Unit 粒度与定义格式可在 PoC 实施设计中确定，不要求把每个操作拆为 Call。Reviewer 的完成验收检查审查是否完成、报告是否有效；报告中发现问题不代表 Reviewer 的执行失败，finding 是否闭环由后续处置和最外层验收判断。仅在所有必要 Review 结果完成且通过各自验收后，才汇聚并进入处置；执行失败或无法判断时按声明处理，不静默跳过。

运行输入包括测试需求、对应设计和测试规格、`tasks-overview.md`、固定版本知识和一个逻辑代码工作区。工作区由运行时绑定；测试结果和 Review 报告通过引用关联，代码可以留在共享工作区。可执行 Unit 有各自完成判定，最外层还要检查必要步骤和最终验收。

## 4. 可观察结果

每次运行至少能够关联：定义身份及固定的子 Unit、知识引用；运行 ID；Call 所在位置和实例 ID；尝试次数；开始与结束、依赖和分支决策；工作资源绑定；产物引用；执行结论与 Verification 结论。记录的具体事件格式、存储方式和检查点策略不在本方案中预设。

每个场景应保存初始条件、注入操作、观察到的状态和事件、产物及验收结果。顺序断言以因果关系为准，不依赖毫秒级时间差。并行场景使用可控的同步屏障：两个 Reviewer 均已启动并等待时，下游未启动；释放后才允许汇聚。

## 5. 执行语义验收案例

以下案例是预期行为，不是已通过的测试。每次故障注入使用独立运行和隔离记录；测试执行者必须可控，不依赖模型偶然表现。

| ID | 条件与操作 | 可检查的预期 |
|---|---|---|
| POC-01 | 启动包含 `TaskDev → Review → Reviewer A/B` 的组合定义，输入和 Verification 均有效。 | 三层定义引用和相应执行可关联；子 Unit 和最外层验收均通过后才报告整体成功。 |
| POC-02 | Implementation 进行中或验收未通过。 | 两个 Reviewer 和 CodeCheck 均不启动；任务不成功。 |
| POC-03 | 两个 Reviewer 声明并行并在启动后等待屏障。 | 两者均可进入运行；汇聚及下游尚未启动。任一失败或未验收时不能当作两者成功。 |
| POC-04 | 在另一份定义中将两个 Reviewer 显式设为串行。 | 第一个完成且通过后第二个才启动；Runtime 不因数据独立而自行并行。 |
| POC-05 | Reviewer A 的模拟报告包含一条 finding，B 通过；处置为修复并产生代码变更。 | 两份 Review 均有记录；finding 有对应处置，执行受影响测试；需要定向复核时等待复核。复核和处置记录不覆盖原 Review 报告。 |
| POC-06 | 执行者返回成功文本，但该 Unit 的 Verification 返回未通过；另一轮返回无法判断。 | 分别记录未通过和无法判断，不报告 Unit 成功；下游按流程处理或等待。 |
| POC-07 | 配置最多两次尝试的模拟只读 Call，首次失败、第二次成功；另一次连续失败。 | 前者记录两次不同尝试后继续；后者到上限停止自动重试，不报告成功。 |
| POC-08 | 在已记录 Implementation 成功后中断进程并重启；执行记录和工作区未改变。 | 恢复后能关联已确认结果，不重复执行 Implementation；从可确认的位置继续。 |
| POC-09 | 模拟外部操作已发出但结果未记录，随后中断。 | 恢复时标记结果不明并暂停；不自动再次发出该操作。此案例使用本地可控模拟，不连接真实外部服务。 |
| POC-10 | 创建含固定知识和子 Unit 引用的模板，修改知识或子 Unit 引用并形成新模板。 | 新旧身份及上层引用可区分；旧定义和其他引用不变化；新运行使用明确选定的版本。 |
| POC-11 | 在两次独立运行中，将同一 Unit 定义分别绑定到隔离工作区 A、B。 | Unit 身份相同、绑定记录不同；产物只归属各自运行。 |
| POC-12 | 预先声明对输入集合逐项展开；分别输入空集和三项。 | 实例数分别为零和三，每项有独立执行记录；并行仅在定义明确允许时发生。 |
| POC-13 | `completion` 缺少必要 Review、finding 处置、CodeCheck 或交接证据，分别注入一次。 | 最外层验收拒绝成功并说明缺口；不能用模拟执行者的成功文本替代证据。 |

POC-08 的“已确认”以该场景实际保存的状态和受控工作区为前提，不推广为对所有外部资源可复用的保证。

## 6. 工作区与实际接入

测试源是 `D:\dev\tmp\OpsCopilot`。该目录有用户已有未提交及未跟踪内容；PoC 不在原目录执行写入、清理或重置。试验前使用 [测试需求](005-task-dev-test-case.md) 所列的确定提交，在单独的隔离副本中准备工作流输入和代码修改。隔离副本不会包含原工作区未提交内容；实际创建方式及路径在实施时确认和记录。

先用模拟执行者跑 POC-01 至 POC-13，再在隔离副本中使用真实 Agent 完成测试需求、实际运行目标测试并收集 Review 与 CodeCheck 证据。真实执行时保持 task-dev 的范围：一次只处理一个 Task，不暂存、提交、推送或发布。

## 7. 通过标准和结果报告

每个 POC 场景记录通过、失败或不支持，并附事件与验证依据；不得把未运行的场景记为通过。模拟控制和真实 Agent 接入分别报告。真实任务需达到测试需求的验收标准，且必要流程与证据齐全；任何必需场景失败或未验证时，PoC 不得报告整体通过。

在相同场景下比较候选实现：声明式组合与动态展开、显式并行、外部执行者适配、验收和状态记录、恢复边界、定义固定与隔离资源、实现和运行成本。记录版本、环境、结果和需要的适配；此比较不预设 Flowable、ZCode 或 chrys 已支持全部要求。

PoC 结束后根据结果决定正式定义格式、状态语义和一致性测试，并评估第一方实现。此时才决定是否需要引擎选型或进一步试验。
