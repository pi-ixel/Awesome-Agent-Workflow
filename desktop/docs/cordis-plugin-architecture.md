# Desktop Cordis 插件架构与职责边界

日期：2026-11-09。

状态：经讨论确定的目标架构，用于指导后续重构；不代表当前实现已完成迁移。公开服务名为设计名称，具体签名在实现阶段细化。

保留现有 Cordis、连接池、工厂和运行时重构成果，按职责逐步归位，不因插件改名重写已有机制。本文定义目标边界；[现有 ACP 运行时设计](acp-runtime-design.md)用于核对当前实现和迁移进度。

## 1. 架构原则

- Cordis 是 Desktop 前端内核。有状态、有副作用、有生命周期的能力由插件承载，Rust 保持宿主实现。
- 插件内部可以有多个功能模块。组件、算法和纯类型不必分别成为插件。
- 状态只有一个所有者，其他插件通过公开服务调用或订阅，不直接修改内部 store。
- 业务服务独立于 UI 装配。UI 部分向工作台注册，不加载工作台时核心服务仍能运行。
- 必需依赖通过 Cordis 注入，可选能力通过注册契约接入，禁止跨插件导入内部实现。
- 资源由创建者释放。工作台协调应用退出，各插件完成自己的业务收尾和资源释放。
- 公共操作契约需明确失败结果、完成通知、取消和释放行为。

核心依赖方向：

```text
project → acpRuntime → acpConnection → host → Rust
```

`agents` 从侧面提供启动描述与增强实现。通用运行时不直接导入厂商增强目录。

## 2. 插件与目录

共 15 个插件。以下为目标目录，保留讨论确定的 `acpConnection`、`acpRuntime` 命名；迁移时需同步更新工程约定中的目录规则。

```text
src/
  bootstrap/                  # 创建 Cordis 根上下文、装配插件
  contracts/                  # 按领域组织公共服务、事件和扩展契约
  plugins/
    host/
    configuration/
    diagnostics/
    agents/
      enhancements/
        icode/
        codeagent/
    acpConnection/
    acpRuntime/
    project/
    documents/
    git/
    terminal/
    workflow/
    skills/
    account/
    updates/
    workbench/
  shared/                     # 通用工具、展示组件、日志与 ACP 原文的进程内入口
```

每个插件包含入口、公开服务实现、内部功能模块和测试。功能专属 UI 放在对应模块内，插件顶层 UI 目录负责组合视图。公共契约只暴露必要接口，内部类型留在插件内。

实际目录归位和仍在迁移的服务边界见[迁移记录](cordis-plugin-migration.md#批次-8a-落点)。

### 4.1 增强隔离

- agents 是一个插件，ICode 和 CodeAgent 增强是内部隔离模块。
- 通用管理不解释厂商私有字段，两种增强互不依赖。
- acpRuntime 通过公开接口获取增强，不直接导入具体增强目录。
- project 只消费统一模型，不识别厂商私有报文。
- 不注册某个增强时，其他增强与普通 ACP Agent 仍可运行。
- 会话启动、连接测试和协议自检统一经 acpConnection 申请传输。acpRuntime 注册隔离探查会话工厂，并随 Fiber 装卸启用或撤销。路径探测和启动校验使用 Agents 从 Host 注入的命令端口。

### 4.2 协议与产品边界

| 场景 | project 的产品职责 | acpRuntime 的协议职责 | acpConnection 的连接职责 |
| --- | --- | --- | --- |
| 创建会话 | 项目/Agent 归属、草稿转正式会话、列表更新 | 创建协议会话并返回身份与能力 | 分配连接、完成请求收发 |
| 发送消息 | 内容、附件、能力检查、排队、消息展示 | 执行 prompt，处理响应和增量事件 | 调度请求、传输报文 |
| 审批/表单 | UI、自动应答策略、用户选择、待办状态 | 解析请求、关联应答、处理协议取消和失效 | 请求关联与响应收发 |
| 恢复会话 | 恢复目标、提示/重试策略、历史展示 | 执行 load、恢复协议绑定、报告结果 | 提供可用连接 |
| 关闭项目 | 处理运行任务、未发送及未保存内容等关闭规则 | 结束关联协议操作、释放会话绑定 | 释放租约，按策略回收连接与进程 |

Project 的 `ProjectFactory` 和 `ProjectContext` 管理项目归属、历史目录快照和预热。`acpRuntime` 通过公开端口提供远端目录分页、协议会话及恢复。`acpConnection` 管理物理通道、连接池和请求调度。Host 与两个 ACP 插件通过 `contracts/` 中的连接、会话和进程端口交换数据。

| 文档未保存内容 | documents | 项目关闭与应用退出通过检查接口询问 |

## 8. UI 装配与协作

- Project 注册项目树和会话内容。Workbench 装配侧栏容器、标题栏、底部菜单和会话完整视图。
- Account 注册登录表单，Workbench 提供全屏登录容器和窗控。功能视图通过 Workbench 的 `viewBindings.ts` 读取已注册的服务和视图状态。
- 设置页由 workbench 组合，各插件提供自己的设置项和 UI，configuration 负责存取。
- 文件、Git、终端、工作流拥有自己的状态和 UI，通过项目标识、路径和公开接口关联项目。
- 有明确结果的操作使用 service 调用；已发生事实使用事件通知；可选能力和视图使用扩展注册。
- 跨插件的先后操作须有明确编排负责人。切换 Agent 时的草稿迁移、新会话准备和发送状态变更由 project 协调，不能依靠多个监听器碰巧按正确顺序执行。
- UI 子模块通过公开绑定使用 Workbench。共享分隔线只处理拖拽和键盘操作，Workbench 保存侧栏宽度，Git 保存审查导航宽度。
- 布局、前台会话和工作流快照在 `contracts/` 声明。界面订阅快照并调用声明的操作。回放、审批回调和工作流数据源绑定由各自的插件管理。

## 9. 关闭与释放

### 9.1 关闭或移除项目

由 project 发起。文档、终端等能力通过注册项目关闭参与者，报告未保存内容和运行资源。检查通过后再进行收尾；不能先移除项目，再发事件补救。

### 9.2 退出应用

退出协调属于 workbench 的内部模块，不单设 lifecycle 插件。

1. 关闭窗口、菜单退出、更新安装统一进入请求退出接口。
2. 收集各插件的退出检查，在资源销毁前完成用户确认；取消退出时保持应用可用。
3. 确认后进入退出状态，停止接收新业务操作，执行各插件收尾。
4. 先结束业务执行，再释放协议会话、连接和宿主资源，最终关闭窗口或交接安装。

各插件负责撤销自己的注册项、监听、定时器和 UI。未完成操作应得到明确的取消或失败结果，不能留下永远挂起的请求。具体退出超时与失败策略需在接口实现时明确。

## 10. 重构验收约束

- 依赖守卫禁止跨插件内部导入，禁止底层反向依赖业务 UI。
- 公共契约和共享代码不导入插件实现或应用装配代码。
- 通用链路禁止直接导入具体厂商增强，覆盖不注册增强时的标准 ACP 运行场景。
- 状态归属测试覆盖 Agent 切换、草稿迁移、正式会话归属及跨会话隔离。
- 生命周期测试覆盖注册撤销、请求取消、重复关闭、资源释放及未保存检查。
