## 1. 问题现象

### 1.1 用户可观察现象

- 实际结果：在“原会话连接尚未恢复”页面多次点击“新建会话继续”，页面始终保留原恢复失败横幅、旧消息和旧草稿；发送消息仍提示“尚未连接 agent”。没有可见的新空会话可供继续。
- 预期结果：按 `sessionStart.ts` 的契约，立即切换至独立空草稿并后台建立新连接；成功或失败都应展示当前草稿的真实状态，不能继续显示旧会话恢复页。
- 出现频率：本轮多次真实点击均复现。
- 首次及最近复现版本：当前开发工作树。

### 1.2 复现步骤

1. 打开历史会话并处于 `session/load -32603` 恢复失败状态。
2. 点击“新建会话继续”。
3. 观察页面仍保持原恢复失败状态。
4. 抓取主窗口日志，出现 `forceNew:true` 的“打开会话开始”及随后 `stage:success`。
5. 再次观察前台，没有切换；输入发送仍报告未连接。

### 1.3 影响与风险

- 用户在历史恢复失败后无法通过提供的按钮自助继续，形成核心导航阻断。
- “打开成功”与前台状态不一致，容易让测试误判新会话已建立，污染后续浏览器和全局开关验收。
- 当前没有证据表明这是 iCode 缺陷；`forceNew` 请求由 AAW 发起，前台切换属于 AAW 职责。

## 2. 问题根因

### 2.1 直接原因

已确认按钮触发 `project.sessions.startNewSession`，并产生 `forceNew:true` 的打开调用；但前台没有执行可见的新草稿切换。直接故障位于“新建会话结果→前台聚焦/投影”链路，而不是按钮文字或 OCR。

### 2.2 机制层根因

**待进一步定位，当前不猜测。** `sessionStart.ts` 要求先 `beginDraft`，再通过 `shouldFocus` 和 `draft.isCurrent()` 决定新运行时是否接管前台；`sessionCoordinator.ts` 在打开失败或聚焦条件不满足时还可能回退旧运行时。需要取得该次 `StartSessionResult`、`activated` 和各守卫值，才能确定是新草稿未保持 current、旧运行时回退，还是前台恢复状态未清理。

## 附录 B：根因与引入轨迹补充（2026-11-13）

### B.1 已确认根因

`AcpSession.loadSession` 只有在 `session/load` 成功并解析响应后才给协议 `sessionId` 赋值。恢复失败时，协议 `session.sessionId` 保持 `null`，但恢复分支把旧历史 ID 写入视图 `activeSessionId`，同时设置 `recovery.state="failed"`。

`openWorkspaceNow` 的草稿复用只检查协议 `session.sessionId===null`，未检查视图 `activeSessionId`，因此把恢复失败运行时误判为普通新草稿。`forceNew+draft` 直接复用该旧 store 并返回，造成打开成功但前台不变。

### B.2 引入轨迹

- 草稿复用和恢复状态均随 `08e174b` 引入，父提交中对应文件路径不存在。
- 002 没有修改草稿复用判断，不是引入者。
- 测试缺口是“恢复失败×新建”交叉场景，而不是普通新建或普通恢复单路径。

### B.3 整改与测试方案

完整方案见 `desktop/docs/内嵌浏览器/007整改与测试设计.md`。最小改法是在草稿复用时同时要求协议 sessionId 和视图 activeSessionId 都为 null，保留正常新草稿重试、旧任务保活和全部竞态守卫。

当前处于待方案审核，未修改业务代码。
