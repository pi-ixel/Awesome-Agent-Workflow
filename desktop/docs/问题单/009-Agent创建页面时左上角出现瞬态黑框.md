## 1. 问题现象

### 1.1 用户可观察现象

- 实际结果：AI 打开浏览器时，AAW 左上角先出现一个一闪而逝的黑框，随后右侧内嵌浏览器才显示页面。
- 预期结果：原生子 WebView 首次可见时就位于当前 Browser 内容区域，不在左上角或其他位置闪现；创建、加载和布局过程没有误导性窗口。
- 出现频率：用户在 Agent 创建页面时观察到；本轮未进行逐帧录屏量化持续时间。
- 首次及最近复现版本：当前开发工作树。

### 1.2 复现步骤

1. 在真实 Agent 会话中要求打开一个网页。
2. 观察 AAW 左上角先出现短暂黑框。
3. 随后右侧 Browser 面板打开并显示目标网页。

### 1.3 影响与风险

- 用户会误以为 AAW 打开了额外窗口或外部浏览器，破坏内嵌浏览器的一致体验。
- 原生页面短暂出现在错误区域，可能遮挡工作台其他内容或吸引错误焦点。
- 该现象与 002 的长期残留相似但持续时间不同，需要分开验证创建和销毁两条路径。

## 2. 问题根因

### 2.1 直接原因

MCP 的 `browser_open` 使用固定初始区域 `(0,0,800,600)` 创建原生子 WebView。`add_child` 创建后立即可见，随后才发出面板可见事件，由 React 面板挂载并通过 `setBounds` 将页面移到右侧正确区域。

### 2.2 机制层根因

创建过程把三个动作按错误顺序串联：

1. 以与真实布局无关的固定坐标创建并显示原生页面。
2. 通知工作台打开 Browser 面板。
3. 面板根据实际 DOM 区域重新设置原生页面边界。

因此原生页面在获得正确布局之前已经对用户可见。黑框是该初始原生窗口在内容尚未完成首屏布局时呈现的短暂视觉表现；创建时序已由源码确认，但具体黑帧持续时间和颜色尚未逐帧采集。

### 2.3 证据与排除项

| 结论                     | 支撑证据                                                                                       | 已排除的其他解释                      |
| ------------------------ | ---------------------------------------------------------------------------------------------- | ------------------------------------- |
| MCP 初始位置固定为左上角 | `desktop/src-tauri/src/browser/mcp.rs:616-620` 使用 `x:0,y:0,width:800,height:600`             | 不是用户窗口位置或 DPI 造成的随机坐标 |
| 原生页面创建即显示       | `desktop/src-tauri/src/browser/host.rs:276-282` 直接 `add_child`，创建前没有隐藏控制           | 不是页面内 HTML 黑框或外部浏览器窗口  |
| 正确布局在创建后才应用   | `desktop/src/plugins/browser/ui/BrowserPanel.tsx:391-410` 通过 ResizeObserver 调用 `setBounds` | 不是右侧 CSS 布局整体错位             |
| 与长期残留根因不同       | 002 是销毁协调缺失；本单发生在创建早期                                                         | 不是同一缺陷的简单持续时间变化        |

- 手动新建、崩溃恢复和弹窗创建是否存在同类首次可见时序，需要分别复核。

## 6. 解决方案

### 6.1 推荐方向

首次创建原生页面前就应获得目标 Browser 内容区域，并控制其首次可见时机。原生页面只有在边界与当前会话、窗口和面板归属一致后才能显示。不得通过固定延时、先展示再快速隐藏等方式掩盖时序问题。

具体布局来源和跨进程时序需在实施方案中冻结，避免引入 UI 与 MCP 的循环依赖。

### 6.2 方案比较与决策

| 方案                               | 收益                     | 成本与风险                                               | 验证结果 | 决策                 |
| ---------------------------------- | ------------------------ | -------------------------------------------------------- | -------- | -------------------- |
| 创建前取得正确边界，布局就绪后显示 | 从机制上消除错误位置闪现 | 需要定义面板未打开时的边界来源和失败语义                 | 待验证   | 推荐方向，待方案审核 |
| 保持先创建，收到面板边界后再显示   | 改动集中在可见性控制     | 需要处理迟到布局、面板取消和后台会话，仍可能出现空白等待 | 待验证   | 待评审               |
| 加固定延时后再显示                 | 表面降低闪现概率         | 不同机器时序不稳定，不能解决根因                         | 不可接受 | 放弃                 |

### 6.3 实施范围

- 需要复核 MCP 创建、原生宿主、面板可见性和布局同步。
- 不修改 iCode、002 销毁逻辑、无关窗口和权限模型。
- 需要同步创建时序、后台会话、取消、崩溃恢复和 DPI 交叉测试。

## 附录 C：窗口动态调整与自适应补充约束

### C.1 方案补充

009 的修复不能只保证首次可见位置正确，必须覆盖原生页面的完整布局生命周期：

- 创建期间持续读取最新 Browser 内容区域；在用户正在调整窗口时，首次可见前必须使用最新有效边界，不能使用创建开始时的旧矩形。
- 创建完成后，窗口最大化、还原、拖拽缩放、Browser 右栏宽度变化和 DPI/显示器变化时，原生页面同步跟随目标区域。
- 面板折叠、会话切换或布局失效时，原生页面按公共规则隐藏或重新定位，不能在其他位置“现原形”。
- 高频拖拽期间的迟到布局事件必须按最新代次处理，不能把页面重新设置回旧尺寸或旧位置。
- 逻辑像素、物理像素和窗口偏移必须一致，不能只在某一个 DPI 或窗口尺寸下正确。

### C.2 自适应验收补充

| 场景               | 可验证预期结果                                            | 证据要求                     |
| ------------------ | --------------------------------------------------------- | ---------------------------- |
