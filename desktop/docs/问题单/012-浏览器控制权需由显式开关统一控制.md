## 1. 问题现象

### 1.1 当前设计与产品意图冲突

- 当前设计与实现：用户直接操作网页时，AAW 自动检测输入、取消 Agent 未决动作并切换为人工控制；Agent 之后不得自动重新接管，必须重新申请授权。
- 用户确认的目标：不做自动检测，不做空闲自动交还；用户不能直接操作浏览器，必须先打开人工接管开关。所有浏览器操作权限均由开关明确分配。
- 影响：当前自动接管和重新审批路径与用户期望的明确控制模型冲突，需要修改基线，不是只修一个按钮或错误码。

### 1.2 目标行为

| 开关状态     | 用户浏览器操作 | Agent 浏览器操作 | 控制含义                         |
| ------------ | -------------- | ---------------- | -------------------------------- |
| 人工接管开启 | 允许           | 拒绝             | 用户明确取得浏览器操作权         |
| 人工接管关闭 | 拒绝或阻止     | 允许             | 用户明确将浏览器操作权交给 Agent |

- 用户要操作浏览器时，必须先主动打开人工接管。
- 用户交还控制权时，主动关闭人工接管，Agent 才可获得操作权。
- 不因用户点击、输入、滚动、按键或一段时间未操作而自动改变开关状态。
- 控制权不由模型、页面文本或运行时自报身份改变。

### 1.3 影响与风险

- 当前自动检测会在用户未明确操作开关时改变权限，违背“所有权限归属由开关控制”的原则。
- 仅更换 UI 而不处理输入链路，会造成界面显示 Agent 控制但用户仍能输入的权限假象。
- 开关切换需要处理正在执行的动作和迟到结果，否则可能发生越权操作。

## 2. 问题根因

### 2.1 直接原因

基线采用“用户输入自动接管 + Agent 重新审批”的控制模型，代码也按该模型实现了 `user_input` 和 `browser_request_control`，与用户最新确认的显式开关模型不一致。

### 2.2 机制层根因

现有设计把真实用户输入同时当作“浏览器操作”和“控制权切换信号”，将两种意图隐式合并。目标方案要求控制权只能由开关改变，网页输入不再具有授权语义，因此需要同时调整：

- 需求决策和验收标准。
- 控制状态机与控制代次。
- 原生输入允许/阻止规则。
- Agent 控制校验和重新授权路径。
- 开关界面、状态投影和测试场景。

### 2.4 待设计冻结事项

- 开关按标签还是按会话生效，以及与现有应用级 Agent 总开关的关系。
- Agent 控制时，网页点击、输入、滚动、键盘、触摸和地址导航分别如何阻止，不能只做状态提示。
- 开关切换时未决动作、审批、控制代次和迟到结果的精确转换。
- 接管开关、紧急停止、审批拒绝、证据与数据管理等宿主控件的权限矩阵。
- 跨站点导航、崩溃恢复、新标签、后台会话和历史恢复后的开关状态。

这些事项必须在解决方案和测试设计中明确，不能现场私造默认规则。

## 6. 解决方案

### 6.1 用户已确认的方向

1. 取消以用户网页输入自动切换控制权的规则。
2. 不做空闲计时或自动交还。
3. 通过显式“人工接管”开关分配浏览器操作权。
4. 人工接管开启时允许用户、拒绝 Agent；关闭时允许 Agent、阻止用户浏览器操作。
5. 用户必须先开启人工接管才能操作浏览器。

### 6.2 推荐设计原则

- 开关是控制权的唯一用户侧来源，网页输入不再改变授权。
- 权限切换必须递增控制代次，并处理未决动作和迟到结果，旧请求不能跨代次生效。
- 开关状态必须有明确文本，不能只依赖颜色或图标。
- 全局 Agent 工具开关与页面/会话接管开关分别表达，不混为一个概念。
- 高风险动作审批仍需独立评估，不能因 Agent 获得普通操作权而自动获得全部高风险权限。
- 未覆盖的输入和异常路径 fail-closed。

### 6.3 方案比较与决策

| 方案             | 收益                                     | 成本与风险                                 | 决策                           |
| ---------------- | ---------------------------------------- | ------------------------------------------ | ------------------------------ |
| 显式人工接管开关 | 控制意图明确、可预测、可测试，无空闲猜测 | 用户多一次切换；需要实现输入阻止和切换竞态 | 用户已选择，待技术方案审核     |
| 用户输入自动接管 | 减少一次点击                             | 隐式改变权限，不符合新原则                 | 用户否决                       |
| 空闲自动交还     | 减少交还操作                             | 阅读、思考和表单场景易误接管，竞态复杂     | 用户否决                       |
| 每次重新审批     | 安全边界直接                             | 操作繁琐，也不是用户选择的统一开关模型     | 由新方案取代其普通控制授权语义 |

### 6.4 实施范围

- 需要修改：需求、功能设计、详细设计、测试设计、控制状态机、输入链路、界面和验证证据。
- 明确不修改：iCode；跨会话隔离和全局 Agent 总开关的既定边界不得削弱。
- 开始代码前必须提交技术方案、控件权限矩阵、状态迁移和测试设计，由人类审核。

## 附录 B：最终实施与闭环记录（0.2）

### B.1 最终模型

- `BrowserSpace.manualTakeover` 是会话级唯一事实来源，全部非关闭标签同步投影，新标签继承，A/B 会话隔离。
- 真实切换递增会话与控制代次；开启时取消未决 Agent 请求，双向使旧审批失效。
- 普通控制申请只读确认，不创建审批、不改变开关；高风险动作仍独立审批。
- 页面初始化桥默认阻止真实用户事件，Agent 合成事件不冒充用户。导航、标签、拾取等宿主入口同时校验来源权限。
- 打开开关先剥夺 Agent，再允许用户；关闭开关先阻止用户，再允许 Agent，避免双向放行。
- UI 提供带开/关文本和 `switch` 语义的按钮，证据、数据、停止和审批决定保持独立可用。
