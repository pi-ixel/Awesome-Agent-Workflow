## 1. 用户现象

1. 新开或恢复 AAW 后，Agent 报告 `browser_open` not found，并改用系统默认浏览器。
2. 设置页显示总开关默认关闭；用户开启后再次要求 Agent 尝试，仍然失败。
3. Browser 右栏空白，没有告诉用户当前没有 Browser MCP、如何恢复当前会话。
4. 测试脚本常显式开启总开关，因此测试时工具可用，而用户在新进程或既有会话中可能不可用。

## 2. 已确认根因

### 2.1 默认关闭且没有持久化开启状态

`BrowserHost` 的 `agent_control` 使用 `AtomicBool` 默认值 false；设置页明确写“默认关闭”。当前实现没有持久化用户开启状态，新进程会回到关闭。

用户已作出产品决策：新实例默认允许 Agent 操作浏览器；本单不新增敏感授权持久化。

### 2.2 开启开关只改变原生布尔值，不重建既有会话的 MCP 配置

`desktop/src-tauri/src/browser/host.rs` 的 `browser_set_agent_control` 只写入 `agent_control`；关闭时会撤销授权，开启时没有会话重连或 MCP 重建。

`desktop/src/plugins/project/sessions/sessionCoordinator.ts` 仅在 `prepareRuntime` 时创建端点并把 `mcpServers` 交给 ACP。对已经创建的运行时，开启开关不会补建端点，也不会把工具追加给现有会话。

### 2.3 关闭时静默退化为无浏览器会话

`prepareRuntime` 捕获 `AGENT_CONTROL_DISABLED` 后返回 null，继续以空 `mcpServers` 启动或恢复会话。用户只看到空白右栏，Agent 只能自行选择系统浏览器；界面没有明确状态、原因和恢复动作。

## 3. 原始证据

| 检查 | 原始结果 | 结论 |
|---|---|---|
| 当前总开关 | `browser_agent_control_status = true` | 用户已经真正开启，不是视觉误判 |
| 当前会话最新运行时 | `_chrys/runtime_update.runtime.mcp_tools = {}` | 当前会话仍没有 Browser MCP |
| 当前会话最近恢复 | `session/load.mcpServers = []`（诊断记录 ID 1794998575949000） | 恢复发生在开关开启之前或未经过新端点创建 |
| 用户再次尝试 | Agent 仍返回 `Requested function "browser_open" not found` | 只开启开关不能让当前运行时自行恢复 |
| 玻璃关联 | 024 明确要求保留全局总开关 | 没有证据表明玻璃导致工具未注册 |

## 4. 已批准整改方向

### 4.1 默认与关闭

新实例默认允许 Agent 操作浏览器。用户主动关闭仍立即撤销全部现有端点和浏览器权限；再次开启不得复活已撤销端点。

### 4.2 开启后的恢复语义

开启时识别当前已恢复但缺少 Browser MCP 的会话，提供明确的“重连并恢复浏览器工具”动作；经用户确认后重建 ACP 会话并重新注入端点。不得伪造动态注入成功；重连会停止同一连接上的任务，未完成消息不自动重发。

### 4.3 状态与反馈

- 总开关关闭时，Browser 面板明确提示“Agent 浏览器控制已关闭”，并提供显式开启动作。
- 开启但当前会话尚未恢复时，明确显示“当前会话尚未注册浏览器工具”；只有真实运行时出现 browser_* 后才移除提示。
- Agent 收到工具不可用时不得静默改用系统默认浏览器，应指导用户开启控制并恢复当前会话。
- 重连失败保留真实错误，不把右栏空白或工具列表当作成功证据。

## 7. 重开证据与修正方案

2026-11-19 用户再次实盘失败。当前原生总开关返回 true，但 Agent 的 browser_capabilities、browser_list_tabs 和 browser_open 均返回 `Error: Function failed`；原始错误包含 `HTTP MCP request failed`、`WinError 1225` 和连接拒绝。

当前会话最近 `session/load`（诊断 ID 1795056211224000）注入 `127.0.0.1:56320/mcp`。对该地址的真实 POST 返回 `ECONNREFUSED`；对该端点 ID 执行同会话绑定查询返回 `ENDPOINT_INVALIDATED`。因此根因不是 URL 或模型，而是已撤销端点仍残留在 ACP 运行时。

此前 UI 依赖组件本地保存的开关事件与工具数组引用；组件重建或漏收事件后，旧 browser_* 工具名会再次被误判为健康。修正为：原生提供按会话查询 MCP `active/revoked/not_bound` 状态的公开只读入口；恢复组件在挂载、开关事件和运行时更新后查询；ACP 提示在每次发送前读取同一状态。不得再用本地事件历史代替端点事实。


重开整改后，UI 与 ACP 均直接读取 `browser_mcp_status`，不再依赖组件本地事件历史。最终前端 206 个文件、1738 条测试通过，CI 同款 Rust 140 通过、1 ignored、10 条按规则过滤。实盘完成 active→revoked→确认重连→active，当前会话真实 browser open 和原生 ready 标签快照通过。证据详见 032 实施状态。
