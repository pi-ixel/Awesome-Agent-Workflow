## 1. 问题现象

- 当前人工接管控件是普通矩形文字按钮，显示“人工接管 开/关”。
- 用户期望的是明确的滑动式开关：有轨道与可移动滑块，开启时呈现蓝色，关闭时呈现红色，切换过程有清晰滑动反馈。
- 当前只有边框、背景色和文字变化，无法通过控件形态直观看出这是滑动式开关。

证据：`audit/shots/023-text-takeover-switch.png`。

## 2. 问题根因

### 2.1 当前实现

`desktop/src/plugins/browser/ui/BrowserPanel.tsx` 使用单个 button，设置 `role=switch`、`aria-checked`、文本“人工接管 开/关”以及边框/背景样式。DOM 中没有滑轨和滑块，也没有滑动位移设计。

### 2.2 设计与引入轨迹

1. 012 的正确产品决策是用显式开关统一控制权限，替代自动输入接管。
2. 012 同时要求“状态必须有明确文本，不能只依赖颜色或图标”，并冻结了 `switch` 可访问语义。
3. 但 012 及其高保真只冻结了开/关文本和可访问状态，没有冻结滑轨、滑块、滑动方向、蓝红状态和动效参数。
4. 实现因此采用了最简单的文本按钮，现有测试也只检查 role、aria-checked 和控件权限矩阵，没有检查视觉结构或滑动过程。

**功能权限模型与当前文档一致，但用户所需的滑动视觉没有在 012 中被完整设计和验收。** 本单应补齐视觉契约，而不是改变 012 已验证的权限模型。

### 3.2 与设计的对应结论

- **功能行为符合当前获批设计**：会话级显式开关；开启仅用户、关闭仅 Agent；不做输入自动接管或空闲交还；高风险审批独立。
- **视觉形态不符合用户本次明确期望**：不是滑动式开关，蓝红状态和滑块反馈均不存在。
- 现有“功能已通过”不能覆盖视觉缺陷；本单也不得以改样式为由改写权限逻辑。

## 4. 推荐视觉整改方案（待审核）

### 4.1 控件结构

- 保留可点击的完整人工接管控件和现有公开切换入口。
- 在控件中增加真实的轨道与圆形滑块，开启和关闭分别对应明确的左右位置。
- 开启状态使用蓝色轨道/区域，关闭状态使用红色轨道/区域。
- 滑块随状态滑动，轨道颜色同步过渡；切换期间以真实 Host 返回状态为最终准绳，不提前伪造成功。
- 保留“人工接管”和开/关文本以及 `role=switch`、`aria-checked`，满足 012 的可访问性要求，不只靠蓝红颜色传达权限。
- 保留键盘操作、清晰焦点环和禁用状态；窄窗口中不得挤压地址栏至既有最小宽度以下。

### 4.2 动效与安全边界

- 复用项目颜色与按压反馈规则，增加滑块位移和颜色过渡。
- 遵循 `prefers-reduced-motion`，减少动态效果时直接呈现最终状态。
- 切换中的禁用、防重复点击和失败回滚继续由 012 的真实状态投影处理。
- 不修改 BrowserSpace、控制代次、MCP、原生输入桥、审批和会话归属。
- 不将红色关闭状态误解为错误：文本仍需明确“关 / Agent 控制”。

## 补充：用户反馈“关闭后仍可点击”的复核（2026-11-16）

用户报告开关显示关闭时仍能点击页面元素。Agent 未直接接受或否认该现象，使用当前最新实例执行了真实输入复核：

1. 开关关闭时，BrowserSpace.manualTakeover=false，原生桥 `__aawManualTakeover=false`，会话与标签归属一致。
2. 关闭时真实鼠标点击“点击验证”，页面保持 `WAITING`。
3. 开启后真实点击得到 `CLICK_OK`，真实输入写入 `ON`。
4. 不刷新页面直接关闭，再继续输入 `OFF`，输入框仍只有 `ON`，没有追加。
5. 因此当前实例的关闭状态真实阻止点击和输入；用户报告的那次现象本轮未复现，不能虚构根因。

证据：`audit/shots/023-manual-on-click-ok.png`、`audit/shots/023-manual-off-input-blocked.png`。

本单仍只处理滑动视觉缺陷。若后续再次出现关闭后可操作，应保留当次会话、页面和时序证据，另查切换竞态或页面桥不一致，不能用本次通过覆盖后续失败。

## 补充：完全使用 DeskPilot 操作开关的复核（2026-11-16）

应用户要求，本轮不再用 CDP 代替用户点击开关：

1. DeskPilot 点击“人工接管 关”后，公开快照变为 manualTakeover=true，标签 controller=user，aria-checked=true；真实页面点击得到 CLICK_OK。
2. DeskPilot 再次点击开关后，manualTakeover=false，controller=agent，aria-checked=false；控制代次从 11 变为 12。
3. 关闭后在原页面继续输入 OFF，没有刷新页面，输入框仍保持 ON，没有追加 OFF。

证据：`audit/shots/023-deskpilot-on-click-ok.png`、`audit/shots/023-deskpilot-off-input-blocked.png`。

结论：当前实例开关功能生效，用户所述失效在本轮仍未复现，不能给出虚构根因。缺少玻璃遮挡和状态反馈会造成“不可操作不明显”的可感知性问题，但它是视觉/反馈缺口，不等同于权限功能失效的证据。

## 补充：玻璃层同时消除视觉反馈（2026-11-16）

用户明确要求：AI 接管时不仅不能产生业务操作，也不能出现悬停、按下、焦点或其他让人误以为可操作的视觉反馈。

冻结方案：

1. 玻璃层位于原生 WebView 内部，覆盖完整页面并接收鼠标/触摸命中，使底层元素不再出现 hover、active 或点击反馈。
2. 进入 AI 接管时清除当前页面焦点；键盘、滚轮、触摸及业务权限继续由原生权限桥处理。
3. 人工接管时完全移除玻璃，不自动恢复旧焦点，恢复正常页面交互。
4. 玻璃只负责交互命中和视觉反馈，不作为唯一权限边界；网页篡改玻璃也不得绕过原生权限桥。
5. 玻璃与滑动开关共用 BrowserSpace 真实状态，不引入第二个控制事实来源。
6. 保持页面清晰可观察，Agent 的 DOM 动作、元素定位、截图与证据链路不受影响。
7. 覆盖导航、刷新、新标签、A/B 会话、元素拾取和网页顶层能力的交叉测试。

该要求与 023 的蓝红滑动开关一并实施；021 的全局模态遮挡先独立整改。

## 补充：玻璃层必须跟随视口变化（2026-11-16）

用户补充要求：窗口、右栏或原生视口改变大小后，玻璃不得超出页面，也不得留下未遮挡区域。

玻璃使用原生页面内部的 fixed 全视口覆盖，inset 为 0，不持久化旧像素宽高。窗口和右栏仍由 009/022 的边界同步负责；玻璃随 WebView 当前视口重新排版。验收必须包含自动尺寸断言及真实最大化、还原截图。

## 补充：中心透明的蓝色渐变玻璃（2026-11-16）

用户明确视觉方向：页面中心必须纯透明，越靠近边缘越蓝，让用户能观察 AI 操作，同时明确当前不可操作。玻璃采用以中心为起点的径向蓝色渐变，中心不使用模糊；整层仍接收鼠标和触摸命中，不能因中心透明而失去隔离。
