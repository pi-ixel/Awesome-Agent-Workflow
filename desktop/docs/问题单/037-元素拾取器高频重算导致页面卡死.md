## 1. 问题现象

### 1.1 用户可观察现象

用户在内嵌浏览器中开启元素拾取后，电脑直接卡死，任务管理器显示 CPU 100%。

- 实际结果：拾取一旦开启，页面主线程被高频重算与重排占满，整机响应困难。
- 预期结果：拾取开启后仅在有实际变化时更新高亮，静止页面与静止鼠标下不产生持续布局计算。
- 出现频率：用户环境必现；复杂或持续变更 DOM 的页面更易触发。
- 首次发现版本：当前主线。
- 最近复现版本：同上。

### 1.2 复现步骤

1. 打开内嵌浏览器并进入真实页面，尤其是带定时器、轮播或实时列表的页面。
2. 点击「拾取元素」。
3. 移动鼠标，或保持鼠标不动观察持续变更 DOM 的页面。
4. 观察 WebView 进程 CPU 与整机响应。

### 1.3 影响与风险

- 阻断拾取功能使用，且影响整机其它应用。
- 不改变拾取数据、权限或会话归属；无越权与数据丢失风险。
- 修复必须保持 026/031 已验收行为：唯一高亮框、几何跟随、目标删除清理、Esc 与显式取消、单击提交引用。

## 2. 问题根因

### 2.1 直接原因

注入页面的拾取脚本把「完整高亮重算」直接挂在高频事件上，且每次重算都读写交错触发布局，导致主线程被占满。

### 2.2 机制层根因

1. `pointermove` 以捕获方式挂在 document 上，目标未变化时也执行 `update()`，见 `src-tauri/src/browser/enhancements.rs` 的 `hover`。
2. `update()` 内先写高亮框样式，再读 `label.offsetWidth/offsetHeight`，再写标签位置，再读两次 `getBoundingClientRect()`，形成「写—读—写—读」的强制同步布局。
3. `MutationObserver` 观察整个 `document.documentElement` 的 `childList + subtree`，任何节点增删都同步执行完整 `update()`；持续变更 DOM 的页面在鼠标静止时也持续重算。
4. `selectorFor` 在每次 `update()` 重新计算，向父级最多走 8 层，每层执行 `Array.from(parent.children).filter(...)`，成本随页面规模放大。
5. 所有入口都没有 `requestAnimationFrame` 合并或相同输入去重，单位时间工作量随事件频率线性增长。

### 2.3 证据与排除项

| 结论                             | 支撑证据                                                             | 已排除的其他解释           |
| -------------------------------- | -------------------------------------------------------------------- | -------------------------- |
| 目标未变的鼠标移动也触发完整重算 | `hover` 中 `target===event.target` 分支仍调用 `update()`             | 不是只有跨元素移动才昂贵   |
| 每次重算存在强制同步布局         | `update()` 内写样式后读 `offsetWidth` 与多次 `getBoundingClientRect` | 不是单纯绘制成本高         |
| 页面自身 DOM 变更即可触发重算    | 全文档 `childList+subtree` 观察，回调直接 `update()`                 | 不是必须有用户输入才高负载 |
| 选择器计算被重复执行             | `state.targetSelector=selectorFor(target)` 位于每次 `update()`       | 不是一次性初始化成本       |
| 前端面板不是主要热源             | 面板仅有 picking 状态与取消调用，无轮询与动画循环                    | 不是 React 重渲染导致      |

### 2.4 未确认事项

用户机器上 `pointermove` 与 MutationObserver 两条路径各自的占比尚未定量；需真实页面 Performance/CDP 采样。该事项不影响已确认的无节流缺陷，但真实性能验收仍需补测。

## 6. 解决方案

### 6.1 推荐方案

为拾取脚本建立「单帧一次」的更新调度，并消除无效重算：

- 所有触发源（pointermove、scroll、resize、visualViewport、MutationObserver、ResizeObserver）只负责登记变化并调度一次 `requestAnimationFrame`，不在事件回调里直接做布局工作。
- 悬停目标未变化时不调度；目标变化时才重新计算 selector/role 并重建 ResizeObserver。
- 每帧更新先集中读取布局，再集中写入高亮框与标签，消除「写—读—写—读」。
- MutationObserver 保留目标删除清理能力，但回调仅调度帧更新，不再同步重算。
- 同一帧内矩形与目标均未变化时跳过写入，避免无效样式失效。
- cleanup 取消待执行帧、断开观察器并移除监听，保证取消后零布局读取。
- 保持公开状态字段、事件形状、唯一高亮框与单击提交行为不变。

### 6.2 方案比较与决策

| 方案                                | 收益                             | 成本与风险                                 | 决策 |
| ----------------------------------- | -------------------------------- | ------------------------------------------ | ---- |
| A. 帧合并 + 相同目标去重 + 读写分离 | 工作量有硬上限，保留全部既有行为 | 高亮更新延迟到下一帧，需要补性能与回归用例 | 采用 |
| B. 仅给 pointermove 加固定毫秒节流  | 改动小                           | DOM 变更路径仍无上限，节流间隔主观         | 放弃 |
| C. 删除 MutationObserver            | 减少一个触发源                   | 目标删除后高亮残留，破坏 026 已验收行为    | 放弃 |
| D. 改为原生轮询几何                 | 脚本简单                         | 引入固定频率轮询，静止时也耗 CPU           | 放弃 |
