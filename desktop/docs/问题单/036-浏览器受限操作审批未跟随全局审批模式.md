## 1. 问题现象

### 1.1 用户可观察现象

用户已在 AAW 设置中开启「审批默认模式：自动放行」，Agent 执行普通工具调用不再询问。但 Agent 执行浏览器受限操作时：

- 浏览器面板底部仍出现「浏览器高风险操作审批」，只有「拒绝」和「批准一次」；
- Agent 执行 `browser_execute_script` 时，每段脚本都要再次人工批准；
- 表单提交与文件上传同样强制人工批准；
- 设置页没有浏览器审批相关开关或说明，用户无法判断为什么自动放行没有生效。

实际结果：浏览器受限操作使用独立审批闸门，不读取 AAW 的审批默认模式。
预期结果：浏览器受限操作与 Agent 其它权限请求使用同一套审批策略和同一个审批入口；自动放行时不再弹窗，人工审批时进入统一审批弹窗。

### 1.2 复现步骤

1. 在 AAW 设置中把「审批默认模式」设为「自动放行」。
2. 打开内嵌浏览器并开启 Agent 浏览器控制。
3. 让 Agent 执行 `browser_execute_script`、`browser_submit` 或 `browser_upload`。
4. 观察浏览器面板是否仍出现独立审批条。

### 1.3 影响与风险

- 用户已经表达的放行意愿被浏览器子系统忽略，交互预期被打破。
- 同一会话存在两个审批入口和两套策略，用户无法形成稳定心智模型。
- 高频脚本场景被迫逐条点击，Agent 自动化价值下降。
- 不影响审批记录与页面代次的绑定，不产生越权；相反，统一后仍需保留页面代次与动作摘要约束。

## 2. 问题根因

### 2.1 直接原因

浏览器 MCP 在原生侧对受限动作执行 `require_approval`，把审批结果以 `APPROVAL_REQUIRED:<id>` 返回；AAW 前端由浏览器面板自行渲染审批条并直接调用 `decideApproval`。这条链路从不进入项目会话的审批 store，因此「审批默认模式」没有作用点。

### 2.2 机制层根因

1. 受限动作在原生侧要求审批：`browser_submit`、`browser_execute_script`、`browser_upload` 分别调用 `require_approval` 并发出 `aaw://browser-approval`，见 `src-tauri/src/browser/mcp.rs` 对应分支与 `src-tauri/src/browser/security.rs` 的审批注册表。
2. 浏览器审批事件只被 `BrowserPanel` 订阅，见 `src/plugins/browser/ui/BrowserPanel.tsx` 的审批快照、事件订阅与审批条渲染。
3. 浏览器面板直接调用 `host.decideApproval`，不读取项目偏好，也不经过 `approvalStore`。
4. 全局审批默认模式只在 `sessionCoordinator` 处理 ACP `session/request_permission` 时生效，见 `src/plugins/project/sessions/sessionCoordinator.ts` 的 `onPermissionRequest` 与 `src/plugins/project/interactions/permissionPolicy.ts`。
5. 两条链路没有桥接：浏览器审批不是 ACP 反向请求，项目审批 store 不知道它存在；浏览器面板也不知道全局审批模式。
6. 审批对象按动作摘要与页面代次绑定（脚本按内容摘要、上传按路径），批准一次即消费，所以每次新脚本都会重新询问。

### 2.3 证据与排除项

| 结论                            | 支撑证据                                                         | 已排除的其他解释             |
| ------------------------------- | ---------------------------------------------------------------- | ---------------------------- |
| 受限动作确实在原生侧强制审批    | 三个动作分支均调用 `require_approval` 并返回 `APPROVAL_REQUIRED` | 不是 Agent 自行决定询问      |
| 全局自动放行只覆盖 ACP 权限请求 | `onPermissionRequest` 是唯一读取审批默认模式的入口               | 不是设置未保存或未生效       |
| 浏览器审批 UI 由浏览器面板独占  | 审批条、快照和事件订阅只在 `BrowserPanel` 中                     | 不是统一审批弹窗的另一种皮肤 |
| 批准一次后仍会再次询问          | 审批记录在执行后消费；脚本摘要变化即新审批                       | 不是用户漏点或按钮失效       |
| 无法通过 Agent 侧自动模式绕过   | 原生闸门在 Agent 之外，先于页面执行                              | 不是 Agent 权限模式配置错误  |

### 2.4 未确认事项

无。用户已明确决定统一跟随 AAW 权限审批，不再保留独立策略。

## 6. 解决方案

### 6.1 推荐方案

建立「浏览器审批桥」：把原生浏览器审批事件翻译成标准权限请求，送进会话已有的审批 store，与 ACP 权限请求共用同一套默认模式与同一个审批弹窗。

- 浏览器审批到达后，按动作生成标题、原始输入摘要和「允许一次 / 拒绝」两个选项。
- 读取全局审批默认模式：自动放行时直接向原生审批记录写入批准；人工模式时通过统一审批弹窗等待决策。
- 用户在统一弹窗选择允许则批准，选择拒绝、取消或会话挂起则拒绝；原生侧继续按页面代次与动作摘要校验。
- 会话就绪时加载该会话已有的待审批记录，避免重连后丢失；会话销毁时释放桥并拒绝未决项。
- 移除浏览器面板内的独立审批条与审批订阅，避免出现第二个入口。
- ACP 权限请求链路保持原样，不改变现有行为。

### 6.2 方案比较与决策

| 方案                           | 收益                                 | 成本与风险                                     | 决策 |
| ------------------------------ | ------------------------------------ | ---------------------------------------------- | ---- |
| A. 浏览器审批桥 + 统一审批弹窗 | 策略与入口真正统一，自动放行覆盖完整 | 需要新增桥接层，移除面板审批条，补接线测试     | 采用 |
| B. 只让面板读取全局模式        | 改动较小                             | 仍有两个审批入口与两种呈现，未满足「不要分开」 | 放弃 |
| C. 直接删除原生审批            | 不再询问                             | 失去防提示注入闸门，提交、上传、脚本完全裸奔   | 放弃 |
| D. 让 Agent 侧自行批准         | 不改 AAW                             | 原生闸门在 Agent 之外，技术上绕不过；且不可控  | 放弃 |

### 6.3 实施范围

- 需要新增：浏览器审批到权限请求的纯映射、会话级审批桥。
- 需要修改：会话装配处挂接与释放审批桥；浏览器面板移除独立审批状态、订阅和审批条。
- 明确不修改：原生审批注册表、`require_approval` / `validate_approval` / `consume_approval`、脚本能力限制、上传路径校验、ACP 权限请求链路。
- 需要同步的文档与测试：本问题单、`036实施状态.md`、浏览器面板既有审批用例、项目审批桥用例、会话装配接线用例。
