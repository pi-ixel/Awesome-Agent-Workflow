# Ctrl+滚轮缩放后比例显示不更新

## 文档控制

| 项目 | 内容 |
|---|---|
| 问题编号 | 033 |
| 状态 | 已闭环；原生缩放事件、比例投影、重置和全量回归均通过 |
| 优先级 | 中；页面实际缩放与界面反馈不一致 |
| 发现日期 | 2026-11-19 |
| 关联范围 | 原生 WebView 页面缩放、BrowserHost 事件、BrowserPanel 状态投影 |

## 1. 用户现象

用户在网页上操作 Ctrl+滚轮后，页面缩放比例发生变化，但工具栏仍一直显示 100%。该问题与窗口尺寸、自适应布局和自由 CSS 视口无关。

## 2. 代码证据与根因

1. 原生 WebView 在 `desktop/src-tauri/src/browser/host.rs:434` 启用 `zoom_hotkeys_enabled(true)`，Ctrl+滚轮可由原生页面直接消费并改变缩放。
2. 工具栏数值只读取 `navigation.pageZoom`，见 `desktop/src/plugins/browser/ui/BrowserPanel.tsx:868`。
3. 该状态只在 React `onWheel` 中通过 `changeZoom` 更新，见 `BrowserPanel.tsx:701` 和 `BrowserPanel.tsx:1023`。
4. 原生页面是独立子 WebView，当前没有 ZoomFactorChanged 等原生缩放事件到 BrowserHost/BrowserPanel 的接线，也没有读取实际缩放值的公开查询。因此原生缩放后，React 数值可以保持旧值。
5. 现有测试仅覆盖 `changeBrowserPageZoom` 纯函数计算，没有覆盖真实 Ctrl+滚轮、原生事件、当前标签投影和 A/B 隔离。

结论：页面缩放执行与比例显示是两条未闭环的链路。不能通过在 UI 中本地累加数值来修补，因为这会继续把预期值冒充原生实际值。

## 3. 推荐整改方案

- 穿刺并接入 WebView2 原生缩放变化通知；原生读取真实 ZoomFactor 后，发送包含会话、标签、代次和实际比例的事件。
- BrowserHost 提供公开订阅；BrowserPanel 只让当前会话、当前标签、当前代次的事件更新比例。
- 已有 `setZoom`、Ctrl+0 和原生 Ctrl+滚轮统一由真实缩放事件收口；失败保留真实错误。
- 页面缩放与 P1 预览缩放继续独立；不根据窗口尺寸推算缩放比例。
- 若当前 Tauri 接口不能直接监听缩放变化，先穿刺底层 WebView2 能力，禁止用定时猜测或本地累加代替。

## 4. 测试契约

| 场景 | 必测结果 |
|---|---|
| 原生 Ctrl+滚轮放大/缩小 | 工具栏显示原生返回的实际比例，不再固定 100% |
| Ctrl+0 | 显示并恢复原生 100% |
| 原生事件装配 | 当前会话、标签和代次精确更新；A/B 与旧代次事件不串写 |
| 缩放失败 | 显示真实错误，不伪造比例变化 |
| 窗口尺寸变化 | 仅改变布局，不伪造缩放变化 |
| 真实 DeskPilot | 页面实际缩放、数值更新和重置均有截图及原生事件证据 |
