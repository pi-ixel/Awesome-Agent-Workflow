## 1. 问题现象

- 完整原生套件单次可返回 24 项通过，但随后 `path_exists`、Agent 状态查询及下一次测试均在 15～35 秒超时。
- 最小“创建→清理→再调用”可通过，复杂操作后的清理更容易出现。
- 日志显示第一次 `path_exists` 已进入 Rust，后续命令不再派发，说明不是简单前端等待或进程退出。

预期清理必须等原生浏览数据清理完成后再关闭 WebView，后续 IPC 和下一次会话可立即使用。

## 2. 问题根因

### 2.1 直接原因

`clear_session_partition` 使用 Wry `clear_all_browsing_data()`，该调用只注册完成回调就返回。实现随即关闭标签、撤销端点并继续后续工作，没有等待真实清理完成。

### 2.2 机制层根因

复杂会话存在下载、对话框、CDP 请求和多个页面资源时，原生清理回调可能尚未完成。提前关闭 WebView 使清理与资源销毁、后续 IPC 产生竞态，导致主进程命令派发或响应异常。

### 2.3 证据与排除项

| 结论                    | 支撑证据                                              | 已排除的其他解释            |
| ----------------------- | ----------------------------------------------------- | --------------------------- |
| 清理完成竞态存在        | 等待 `ClearBrowsingDataAll` 回调后，普通 IPC 立即恢复 | 不是 `path_exists` 自身故障 |
| 与复杂会话状态相关      | 最小清理可通过，完整操作后更容易悬挂                  | 不是任何清理都必现          |
| 与更新安装无关          | 无安装器进程，`update_install` 仅在显式命令触发       | 不是自动更新放行            |
| 与 CDP 对话框为独立问题 | CDP 决定已完成后仍出现悬挂                            | 不合并进 016 根因           |

## 4. 问题属类分析

- 主要属类：异步资源回收竞态。
- 次要属类：错误可诊断性与重复运行稳定性。
- 安全边界：清理范围、会话隔离和端点撤销顺序不变，不扩大删除范围。
- 独立问题：与 016 对话框和 017 隐藏截图分开闭环。

## 6. 解决方案

### 6.1 实施方案

- 使用 `ICoreWebView2Profile2.ClearBrowsingDataAll` 和 `ClearBrowsingDataCompletedHandler`。
- 等待真实完成回调后再关闭标签、移除标签映射、撤销 MCP 端点、清理权限和证据。
- 清理入口改为异步；工作区批量清理由主线程派发异步任务，不在主线程阻塞等待。
- 注册或回调失败、超时均显式返回，不伪装 completed。

### 6.2 约束

- 不增加等待上限来掩盖问题；15 秒超时只作为错误边界，不作为正常路径。
- 不改变清理范围、会话归属、既有证据历史和返回状态。
- 不通过重启应用代替产品修复。
