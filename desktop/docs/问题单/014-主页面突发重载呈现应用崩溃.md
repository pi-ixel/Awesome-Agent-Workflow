## 1. 问题现象

### 1.1 用户可观察现象

- 实际结果：AAW 突然出现类似崩溃的重载，随后恢复历史会话，当前用户上下文和任务连续性受到影响。
- 预期结果：没有用户明确刷新或经批准的恢复动作时，主页面不得重载；即使原生进程未退出，也不能出现类似崩溃的突发重置。
- 事故定性：用户可感知的重大稳定性事故，不因“只是 WebView 重载”降级。

### 1.2 已确认事实

- `desktop.exe` 始终是同一进程，未发生原生进程退出。
- `performance.timeOrigin` 证明主 WebView 在 2026-11-13 08:41:56 UTC 发生 `reload`。
- 重载后 ACP 自动恢复多个历史会话，产生“应用重启”的用户感知。
- 更新包 `0.1.31` 已下载但 `installed=false`，不是更新安装重启。
- 原生源码自 12:01 后未改变，Vite 没有对应的文件监听重载日志。
- 系统 Application 日志没有对应 `desktop.exe` 或 WebView2 崩溃事件。
- 观察期内未再次出现重载，触发源尚未确定，不能据此关闭。

## 2. 问题根因

### 2.1 当前直接故障

主 WebView 被非预期重载，触发前端初始化和 ACP 历史恢复。真正需要定位的是**谁发起该重载**，而不是把进程未退出当作无事故。

### 2.2 候选路径与当前证据

| 候选                          | 当前证据                                                     | 状态                         |
| ----------------------------- | ------------------------------------------------------------ | ---------------------------- |
| Vite 文件变化触发 full-reload | 无对应源码变化或服务端日志                                   | 暂未支持                     |
| Vite WebSocket 断线重连后刷新 | 客户端存在该路径，但历史日志没有 `server connection lost`    | 暂未支持                     |
| 显式 `window.location.reload` | 仅 `ErrorBoundary.tsx:60` 有源码入口，需要用户点击“刷新页面” | 待确认是否用户操作           |
| Agent/内嵌浏览器误刷新主窗口  | 现有 Browser reload 通过标签映射到子 WebView                 | 暂无支持，需检查标签失效竞态 |
| 原生 WebView 崩溃或自动恢复   | 进程未退出，系统无崩溃事件，当前文档发生 reload              | 未完全排除                   |
| 更新安装                      | ready 包存在但 installed=false                               | 已排除本次安装重启           |

### 2.3 未确认事项

- 本次 `reload` 的发起者、调用时间和触发上下文。
- 是否与用户操作、系统锁屏/休眠、Vite 客户端重连、调试端口操作或原生窗口事件有关。
- 生产构建是否存在同类问题；当前 `tauri dev` 不能代表生产结论。

## 6. 解决方案方向

### 6.1 当前门禁

根因未确认前不修改业务代码，不用阻止所有刷新的方式掩盖问题，也不以生产环境“可能不存在”作为关闭理由。

### 6.2 方案原则

- 非用户明确操作不得出现主 WebView 重载。
- 开发环境的基础设施不得无提示地重置用户工作上下文。
- 如果确需恢复，应展示明确原因、保留可恢复状态，并保证 ACP、审批、浏览器和原生资源按代次处理。
- 修复必须同时覆盖触发源和用户可感知结果，不能只隐藏恢复日志。

## 附录 B：断线复现与整改方案（2026-11-13）

### B.1 机制证据

在隔离端口 1422 上，停止并恢复真实 Vite 服务后，浏览器 `generation` 从 1 变为 2。Vite 客户端源码在 `vite:ws:disconnect` 分支中轮询服务恢复并执行 `location.reload()`，与该结果一致。

这证明事故所表现的“主 WebView 自动重载→ACP 恢复→用户感到崩溃”机制成立。事故当次断线的网络/系统原因没有被完整日志保留，不伪造该部分结论。

### B.2 整改方案

在 `desktop/vite.config.ts` 中仅对 Tauri 原生开发禁用 HMR 自动刷新；`AAW_DEV_BRIDGE=1` 的 dev:web 和显式远程 host 配置保持现有策略，生产构建不变，第三方依赖不修改。

代价是 Tauri 前端开发需要显式刷新才能看到前端变化，以消除开发服务器对用户工作上下文的突然重置。

完整测试设计见 `desktop/docs/内嵌浏览器/014整改与测试设计.md`，当前待方案审核，未修改配置。

## 附录 C：最终整改与闭环记录（2026-11-16）

### C.1 最终机制与方案

最终没有采用“全面禁用 HMR”或“删除客户端模块”的路线，而是只处理 Vite 客户端的自动刷新副作用：

- 在 Tauri 原生开发的 `/@vite/client` HTTP 响应中，将 `location.reload()` 替换为无副作用表达式。
- 保留 Vite 的完整客户端、`createHotContext`、常量注入和模块解析，不修改 `node_modules`。
- 响应使用 `Cache-Control: no-store`，避免旧刷新逻辑从缓存继续执行。
- `AAW_DEV_BRIDGE=1` 和显式 `TAURI_DEV_HOST` 不加载该治理插件，生产构建不受影响。

### C.2 被证伪并撤回的路线

- 单纯 `hmr=false`：Vite 仍注入客户端且断线后刷新。
- 删除 HTML 注入或自定义客户端：动态模块加载失败，包括 `rolldown/experimental/runtime`、`@vite/env` 和注入常量缺失。
- 包装普通 `transform`：不能覆盖 Vite 客户端的真实服务路径。
- 仅 `ws=false`：仍出现断线刷新。
- 所有失败实现均已撤回，最终仅保留响应级禁刷。

### C.3 验证证据

| 验证项                          | 实际结果                                                                               | 判定     | 证据位置                                      |
| ------------------------------- | -------------------------------------------------------------------------------------- | -------- | --------------------------------------------- |
| 静态 HTTP 停服恢复              | `performance.timeOrigin` 完全不变，未发生浏览器自身刷新                                | 通过     | `browserReloadSpike.ts` static 输出           |
| Vite 可见页面停服恢复（未治理） | timeOrigin 改变并重新进入登录页，缺陷复现                                              | 有效红色 | 可见 Vite 对照输出                            |
| Vite 响应治理                   | 响应中 `location.reload()` 数量为 0，`createHotContext` 保留，`Cache-Control=no-store` | 通过     | `tests/runtime/viteConfig.test.ts` 与响应检查 |
| 配置边界                        | Tauri 原生加载禁刷插件，dev:web 和远程 host 不加载                                     | 通过     | TD-014-U01、TD-014-B01 共 2 条通过            |
| 真实 AAW 主窗口                 | 显式加载新客户端后停止并恢复 Vite，timeOrigin 保持 `1794800905708.5`，页面内容不重置   | 通过     | 真实主窗口前后 CDP 输出                       |

### C.4 闭环结论

014 **已闭环**。问题根因是 Vite 客户端断线恢复时的自动刷新，最终方案只禁止该副作用，不破坏模块加载和开发能力。生产构建不经过该开发响应路径。长时间稳定性、企业内网和其他崩溃原因不扩大为已验证结论。
