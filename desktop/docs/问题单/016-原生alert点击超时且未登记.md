## 1. 问题现象

### 1.1 实际结果与预期结果

- 实际结果：点击 `#dialog-target` 后，MCP 请求进入未决并最终 `TIMEOUT`，`browser_dialog_snapshot` 为空。部分运行能登记并接受，重复运行不稳定。
- 预期结果：每次触发 JavaScript 对话框都生成属于当前会话、标签和代次的记录，用户或 Agent 可接受、取消或输入 prompt，后续动作与清理可继续。
- 出现频率：多次真实运行中反复出现，一次成功不能代表稳定。

### 1.2 影响与风险

- AC-016 无法验收，Agent 可能把对话框超时误判为普通页面失败。
- 未处理对话框会阻塞页面动作和后续原生综合测试。

## 2. 问题根因

### 2.1 直接原因

原生 `ScriptDialogOpening` 注册路径在本机多子 WebView 场景下不稳定，注册返回成功但事件经常不投递。随后引入 CDP 事件后，初次决定仍失败，因为 CDP 条目被错误放入线程本地表，事件线程与决定线程不同，读取时返回 `DIALOG_NATIVE_REQUIRED`。

### 2.2 机制层根因

系统有两类对话框来源：WebView2 原生事件和 CDP 事件。它们不能共享同一套线程本地生命周期模型。原生 `args/deferral` 必须保留 UI 线程归属；CDP 条目则需要跨线程可见，并通过 `Page.handleJavaScriptDialog` 异步完成决定。

### 2.3 证据与排除项

| 结论 | 支撑证据 | 已排除的其他解释 |
|---|---|---|
| 原生事件注册不稳定 | 注册多次 `Ok(())`，多数无 `ScriptDialogOpening` 回调；快照为空 | 不是测试按钮不存在或 alert 未执行 |
| CDP 通道可登记 | `Page.javascriptDialogOpening` 返回 `AAW_DIALOG_PROBE`、会话和标签 | 不是 alert 被永久禁用 |
| 初次决定失败是跨线程读取问题 | 原始错误为 `DIALOG_NATIVE_REQUIRED`，CDP 记录存在但决定线程读不到 | 不是 prompt 参数或审批代次错误 |
| 清理悬挂是独立问题 | 对话框接受后仍有 IPC 超时，等待清理完成回调后恢复 | 不由对话框事件根因单独解释 |

## 4. 问题属类分析

- 主要属类：对话框事件接入缺陷。
- 次要属类：跨线程状态所有权缺陷。
- 安全边界：不默认接受，不跨会话共享记录，决定仍校验会话、标签和代次。
- 独立问题：018 的清理完成竞态单独闭环，不混入本单。

## 6. 解决方案

### 6.1 实施方案

- 使用 `Page.javascriptDialogOpening` 读取类型、消息、URL 和默认 prompt，复用现有 `DialogRegistry`。
- CDP 条目存入跨线程共享 `CDP_DIALOGS`，保留 WebView 句柄。
- 原生条目继续保留 UI 线程归属和 `args/deferral`。
- 决定按来源分流：原生走 COM 完成，CDP 走 `Page.handleJavaScriptDialog`，完成后再更新记录。
- 取消与超时同样分流，主线程只执行原生 COM 操作，不阻塞异步 CDP 等待。

### 6.2 约束

- 不默认接受、不返回假成功、不跨会话读取、不将 CDP 条目放入线程本地表。
- 不使用脚本覆写 alert/confirm/prompt 来伪造同步返回值。
- 不修改 iCode，不改变 MCP 工具名称和记录字段。
