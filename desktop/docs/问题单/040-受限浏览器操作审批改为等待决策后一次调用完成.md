## 1. 问题现象

### 1.1 用户可观察现象

用户已选择「自动放行」，Agent 执行 `browser_execute_script` 仍连续返回 `APPROVAL_REQUIRED:approval-62 → 66`，并据此告诉用户“需要人工批准、无法执行”。

- 实际结果：AAW 已自动批准，但 Agent 只看到首次调用返回的错误，不知道要携带 `approvalId` 重试。
- 预期结果：审批未决时原生等待决策；自动放行时一次调用直接返回执行结果，人工模式下用户点完后同一次调用继续执行。
- 出现频率：所有不带 `approvalId` 的受限动作调用。
- 首次发现版本：036 实盘验收期间。
- 最近复现版本：同上。

### 1.2 复现步骤

1. 设置「审批默认模式」为自动放行。
2. 让 Agent 调用 `browser_execute_script`。
3. 观察首次返回为 `APPROVAL_REQUIRED:<id>`，Agent 不带 `approvalId` 反复新调用。

### 1.3 影响与风险

- Agent 误判为权限失败，放弃动作或改用非预期工具。
- 每次重试生成新审批记录，审批列表膨胀。
- 等待化必须保持安全边界：拒绝、失效、页面代次变化、会话销毁都要终止等待并显式报错，不得静默放行。

## 2. 问题根因

### 2.1 直接原因

原生在缺少 `approvalId` 时创建审批后立即返回 `APPROVAL_REQUIRED`，把「申请审批」和「执行动作」拆成两次调用；AAW 的自动批准发生在首次返回之后，Agent 无法感知。

### 2.2 机制层根因

1. 三个受限分支在 `else` 路径中 `require_approval` → `emit(aaw://browser-approval)` → `return Err(APPROVAL_REQUIRED)`，见 `src-tauri/src/browser/mcp.rs`。
2. 036 的审批桥在事件到达后自动调用 `browser_approval_decide`，但这发生在 Agent 已收到错误之后。
3. 原生只在第二次携带 `approvalId` 的调用中 `validate_approval` 并执行，Agent 不重试就永远停在建审批阶段。
4. 工具描述未要求 Agent 必须重试，Agent 倾向于把错误当成最终失败。

### 2.3 证据与排除项

| 结论                         | 支撑证据                                      | 已排除的其他解释     |
| ---------------------------- | --------------------------------------------- | -------------------- |
| 自动放行确实批准了           | approval-64/66 日志「自动决策 approved=true」 | 不是审批桥未生效     |
| Agent 未携带 approvalId 重试 | 审批号连续递增且动作摘要相同                  | 不是页面代次失效导致 |
| 原生首次调用立即返回         | 三个分支的 `return Err(APPROVAL_REQUIRED)`    | 不是前端弹窗遮挡     |

### 2.4 未确认事项

Agent 侧 MCP 客户端自身的请求超时阈值未确认；等待超时必须显式返回并保留 `approvalId` 重试路径，不能无限等待。

## 4. 问题属类分析

- 主要属类：设计缺陷，审批时序与调用契约不匹配。
- 次要属类：文档缺陷，工具描述未说明重试规则。
- 是否涉及安全或隐私：涉及。等待化不能削弱审批，拒绝与失效必须 fail-closed。
- 是否破坏既有兼容或基线：改变首次调用的返回时机；保留 `APPROVAL_REQUIRED` 超时返回和 `approvalId` 显式重试，属于已批准的行为调整。
- 是否属于相邻但独立的问题：是，与 036 分开闭环。

## 6. 解决方案

### 6.1 推荐方案

把「创建审批」后的立即返回改为有界等待决策：

- 缺少 `approvalId` 时仍先创建审批并发出 `aaw://browser-approval`，随后进入轮询等待。
- 等待结果：
  - `approved`：继续按原有 `validate_approval` 校验会话、标签、代次与动作摘要，然后执行并消费审批；
  - `denied`：返回 `APPROVAL_DENIED`；
  - `invalidated` 或记录被删除：返回 `APPROVAL_INVALIDATED` / `APPROVAL_NOT_FOUND`；
  - 超过等待上限：返回 `APPROVAL_REQUIRED:<id>`，保留显式重试能力。
- 已携带 `approvalId` 的调用保持原路径，不进入等待。
- 轮询不在持锁状态下休眠，避免阻塞 `browser_approval_decide` 与失效处理。
- 等待上限 60 秒、轮询间隔 100ms，写入工具描述与恢复文档，说明超时后可用 `approvalId` 重试。

### 6.2 方案比较与决策

| 方案                  | 收益                                     | 成本与风险                             | 决策 |
| --------------------- | ---------------------------------------- | -------------------------------------- | ---- |
| A. 原生有界等待决策   | 自动放行一次调用完成，人工模式同调用继续 | 需要处理超时、失效与锁边界             | 采用 |
| B. 仅补工具描述       | 改动小                                   | 仍两次调用，依赖 Agent 遵守            | 放弃 |
| C. 自动放行时跳过审批 | 无等待                                   | 失去审批记录与安全闸门，违反已批准设计 | 放弃 |

### 6.3 实施范围

- 需要修改：`security.rs` 增加有界等待；`mcp.rs` 三个受限分支复用等待与统一校验；工具描述补重试规则。
- 明确不修改：审批注册表结构、代次校验、脚本能力限制、上传路径校验、036 审批桥、ACP 权限链路。
- 需要同步的文档与测试：本问题单、`040实施状态.md`、Rust 等待用例、真实 MCP 与真实 Agent 验收。

## 10. 闭环结论

已闭环。`browser_submit`、`browser_execute_script`、`browser_upload` 在缺少 approvalId 时创建审批并等待决策；批准后同一调用执行并消费审批，拒绝/失效/超时显式报错。真实 Agent 自动放行下已能一次调用拿到页面标题。
