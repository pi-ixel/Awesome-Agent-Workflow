## 1. 问题现象

### 1.1 用户可观察现象

- 实际结果：当会话已有 `tab-1` 时，Agent 请求 `browser_open(url=?agent=global-switch)`，工具仍返回旧的 `tab-1` 和旧 URL `?agent=takeover`，没有创建或导航到新 URL。关闭该标签后再次调用，工具甚至返回 `lifecycle=closed` 的同一旧标签，后续 `browser_wait` 返回 `TAB_NOT_READY`。
- 预期结果：`browser_open` 按标签创建契约创建可用受控页面并返回新标签及真实目标 URL；不得把已关闭标签作为打开成功结果返回。
- 出现频率：已有可用标签和已关闭标签两种路径均在真实会话中复现。
- 首次及最近复现版本：当前开发工作树。

### 1.2 复现步骤

1. 新会话中让 Agent 调用 `browser_open` 打开 `?agent=takeover`，首次成功返回 `tab-1`。
2. 再让 Agent 调用 `browser_open` 打开 `?agent=global-switch`。
3. 观察返回仍是旧 `tab-1`、旧 `committedUrl`，没有新页面。
4. 通过真实界面关闭 `tab-1`，再次请求打开新 URL。
5. 工具返回旧 `tab-1` 且 `lifecycle=closed`；后续等待失败。

### 1.3 影响与风险

- Agent 只能在会话的首次空状态下可靠创建页面，多步骤、多页面和关闭后重开任务被阻断。
- 工具返回看似成功的标签对象，但目标 URL 和生命周期不符合请求，容易诱导 Agent 在错误页面继续操作。
- 已关闭标签被返回破坏生命周期契约，后续错误被推迟到等待、截图或动作阶段，增加错误归因难度。

## 2. 问题根因

### 2.1 直接原因

`browser_open` 在会话空间存在时读取 `space.tabs.values().last()`；只要存在任意标签就直接返回，不判断目标 URL、标签生命周期，也不执行创建分支。

### 2.2 机制层根因

实现把“打开页面”错误简化为“有标签就返回最后一个，没有才创建”。标签集合包含 `closed` 状态对象，因此同样的复用逻辑也会选中已关闭标签。目标 `url` 只在 `None` 创建分支使用，已有标签时完全被忽略，导致工具名称、输入和实际副作用不一致。

### 2.3 证据与排除项

| 结论                     | 支撑证据                                                                              | 已排除的其他解释                             |
| ------------------------ | ------------------------------------------------------------------------------------- | -------------------------------------------- |
| 新 URL 被忽略            | 真实 Agent 返回旧 `committedUrl=?agent=takeover`，页面没有跳到 `?agent=global-switch` | 不是 Agent 读错 URL 或页面重定向             |
| 已关闭标签仍作为打开结果 | 真实返回 `tabId=tab-1`、`lifecycle=closed`，后续 `TAB_NOT_READY`                      | 不是单纯界面未刷新                           |
| 复用逻辑来自 MCP 路由    | `desktop/src-tauri/src/browser/mcp.rs:601-625` 读取最后一个标签，`Some(tab)` 直接返回 | 不是原生创建能力缺失；首次空调用已证明能创建 |
| URL 只在创建分支使用     | 同段代码中 `url` 仅传给 `create_tab_for`，已有标签不进入该分支                        | 不是目标 URL 参数未传到 MCP                  |

### 2.4 未确认事项

- 是否存在设计上独立的“复用当前标签”工具语义，需要在整改时核对；DD-03 当前将本能力定义为“标签创建”，不能擅自改成导航或复用。
- 多标签顺序是否依赖哈希表迭代顺序，需要在修复后验证目标选择确定性；当前缺陷已足够成立，不依赖该假设。

## 6. 解决方案

### 6.1 推荐方向

按已基线的“标签创建”语义，让每次合法 `browser_open` 都通过统一原生创建入口生成受控页面，返回真实新标签和目标 URL。不得复用 `closed` 标签，不得在已有标签时静默忽略 URL，也不得擅自增加隐式导航或复用策略。具体改法和测试设计在代码修改前审批。

### 6.2 方案比较与决策

| 方案                                | 收益                                     | 成本与风险                                 | 验证结果     | 决策       |
| ----------------------------------- | ---------------------------------------- | ------------------------------------------ | ------------ | ---------- |
| 始终通过公共创建入口创建受控标签    | 符合 DD-03，结果确定，复用原生权限和预算 | 需要回归多标签、预算和后台显示意图         | 待验证       | 待方案审核 |
| 仅过滤 `closed`，继续复用可用旧标签 | 可消除关闭对象返回                       | 仍然忽略新 URL，不符合创建语义             | 不完整       | 不推荐     |
| 复用旧标签并导航到新 URL            | 减少标签数量                             | 变成隐式导航，可能覆盖用户页面并混淆控制权 | 风险不可接受 | 放弃       |
