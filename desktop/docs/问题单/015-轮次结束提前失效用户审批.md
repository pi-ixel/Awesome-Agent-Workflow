## 1. 问题现象与根因

`browser_request_control` 返回 `APPROVAL_REQUIRED` 后，Agent 当前轮次结束。`onPromptSettled` 调用 `browser_cancel_requests`，该函数除取消请求外，还把所有 pending/approved 审批置为 invalidated。

因此用户看到审批卡时，审批实际已被上一轮清理；点击批准返回 `APPROVAL_CLOSED`，下一轮再带 approvalId 返回 `APPROVAL_INVALIDATED`。审批跨轮次等待用户决定这一基本场景无法成立。

## 2. 引入轨迹

- ACP 接入时为 onCancel/onPromptSettled 统一复用了完整会话取消入口。
- 后续审批失效规则与显式停止、会话撤销共用同一实现，没有区分“轮次工作取消”和“用户审批生命周期”。
- 真实审批卡可见后，才发现轮次结束提前失效，003 的遮挡曾掩盖该问题。

## 3. 方案

- 新增轮次级取消公共入口，只取消请求，不修改审批状态。
- ACP onCancel/onPromptSettled 使用该轮次入口。
- 显式停止按钮继续使用完整取消入口，按既定规则失效审批。
- 会话销毁、全局关闭、用户接管和代次变化保持原有审批失效规则，不新增降级。
- 不修改 iCode、审批内容、一次性消费和代次校验。

## 4. 测试设计与交叉面

| 用例              | 维度               | 场景与直接断言                                                                          |
| ----------------- | ------------------ | --------------------------------------------------------------------------------------- |
| TD-015-A01 [装配] | 轮次取消保留审批   | 调用轮次取消入口后，请求取消，审批 status 仍为 pending；直接来自原始记录                |
| TD-015-A02 [装配] | 显式停止仍失效审批 | 完整取消入口仍把 pending/approved 置为 invalidated                                      |
| TD-015-M01 [手工] | 跨轮次批准         | Agent 返回 APPROVAL_REQUIRED 后，用户批准；下一轮带 approvalId 可获得控制并执行目标动作 |

交叉面：onCancel、onPromptSettled、显式停止、全局关闭、会话销毁、用户接管、代次变化、批准/拒绝和重复消费。
