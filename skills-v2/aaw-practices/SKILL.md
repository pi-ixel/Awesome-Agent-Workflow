# AAW 工作方法

本技能不驱动任何流程，也不依赖任何命令行工具。它说明在 AAW 的研发链路里怎样把事情做对；具体每一步怎么做，见各自的技能。流程由谁推进（工作流引擎、用户本人）都适用。

## 一、需求先立住

- **原始需求原样保存**。用户明确作为需求提供的文本保持原文：不总结、不改写、不做设计性加工；分布在多段时按原顺序完整保存。普通讨论、Agent 的解释和设计推导不得混入。
- **保存后回显核对**。把保存下来的原文回显给用户（较长时回显开头若干行并注明总行数），请用户确认一致。用户指出不一致时，先修正原文、重新核对，再继续往下做。
- **拿不准就问**。无法判断用户是否已经提供了原始需求时，先向用户收集，不得以空内容或臆造内容开始设计。
- 原始需求是后续设计与门禁的权威对照；任何步骤都不得修改或覆盖它。

## 二、按规模选链路

| 链路 | 适用 | 主要成果物 |
|---|---|---|
| 完整链路（从 SR 开始） | 多人协作、复杂度高、需要分阶段留痕评审的需求 | SR 设计 → AR 拆分 → 每个 AR 的范围、模块边界、ASIS / TOBE 详细设计、测试设计、模块门禁 → 任务计划与逐任务开发 |
| 从单个 AR 开始 | 已有 SR 设计和架构基线，只推进其中一个 AR | AR 范围文档起，后同完整链路 |
| 轻量链路 | 一个人能独立设计并实现、无需多角色交接的需求 | `dev-design.md`、`test-design.md`、轻量门禁报告、`tasks-overview.md` |

判断标准是需求规模，不是赶时间。轻量链路把功能设计、模块边界与详细设计合成一份口径统一的文档，面向贯穿设计到开发的同一个人；如果团队要求这些阶段分开评审，就走完整链路。

## 三、做每一步时

- **以实际成果判断进度，不靠记忆**。上下文压缩、会话恢复或换人接手后，重新读取已有的文档、门禁报告和任务执行记录，从实际状态继续。
- **必需输入缺失就停**。设计依据、门禁结论、架构基线等必需输入不存在或不可读时，说清缺什么、为什么需要，不要用推断或记忆补位。
- **已有成果当基线**。当前步骤的输出文件已存在时，仍按当前要求完整执行：先读取并评估，复用仍有效的信息和已确认的答案，只问当前确实无法确定的问题，可局部修改或整体重写，写回原位置。
- **不编造**。代码能回答的问题先查代码，并在提问时说明查过什么；代码证不出、需要拍板的事交给用户决定，不默认采纳自己的推荐。
- **文档放在约定位置**。调用方指定了位置就用它；没有指定时用各技能里写的默认布局，同一需求的文档放在一起，并告诉用户放在哪里。
- **项目架构基线**是 `.sdd/software_architecture.md`（由 `repo-init` 生成和维护）。模块边界以它为准，缺失时按各技能的降级口径处理并明确记录。

## 四、门禁与返工

- **门禁是准入，不是直通**。每一轮门禁都要生成或更新门禁报告，通过、不通过、阻塞都一样；不允许只在会话里口头给结论。
- **不通过就原地修上游**。结论为不通过或阻塞时，不要推进下游；默认修正对应的上游成果物后重新执行门禁：SR 设计门禁修 `SR-design.md`，模块设计门禁修 ASIS / TOBE / 测试设计，轻量门禁修 `dev-design.md` 或 `test-design.md`。
- **复检要全量**。保留上一轮的问题编号，逐项给出关闭、转非阻断或仍阻断的状态；复检仍做全量检查，不只看历史问题。
- **不擅自回退**。只有用户明确要求重走上游步骤时才返工。返工前先讲清：退回到哪一步、哪些下游成果会失效、涉及哪些文件；再请用户选择「保留已有成果，在其基础上返工」还是「丢弃这些成果，从有效的上游输入重做」。
- **关键边界要用户点头**。进入实现之前（任务计划确认）、正式基线确认之类的边界，等用户明确确认后再往下走。

## 五、技能地图

| 技能 | 做什么 | 接在谁后面 |
|---|---|---|
| `repo-init` | 初始化或更新项目架构基线 `.sdd/software_architecture.md` | 项目开始时 |
| `sr-design` | 把原始需求收敛为 SR 级功能与技术设计 | 原始需求 |
| `sr-design-gate` | SR 设计准入门禁 | `sr-design` |
| `ar-clarify` | 为一个 AR 澄清范围，产出可独立设计的 AR 范围文档 | AR 拆分或用户直接给的 AR |
| `module-boundary-design` | 确定承接模块与模块组 | `ar-clarify` |
| `module-asis-analysis` | 模块现状（ASIS）取证分析 | 模块边界 |
| `module-tobe-design` | 模块目标设计（TOBE） | ASIS |
| `module-test-design` | 测试用例设计（严格 / 轻量两种模式） | TOBE 或 `dev-design` |
| `module-design-gate` | 模块设计准入门禁 | 模块设计与测试设计 |
| `dev-design` | 轻量链路的单份设计 | 确认后的需求 |
| `dev-design-gate` | 轻量链路的准入门禁 | `dev-design` 与轻量测试设计 |
| `task-split` | 把已评审设计组织成有序的薄任务计划 | 门禁通过 |
| `task-dev` | 一次实现一个任务：实现、测试、评审、重验、代码检查、交接 | 用户确认的任务计划 |
| `code-check` | 代码规范与基本质量检查 | `task-dev` 的代码检查步骤，也可单独使用 |
| `module-deep-research` | 长程的既有模块研究 | 需要深入理解存量模块时 |
| `effective-document-writing`、`mermaid-diagram` | 写文档与画图 | 任意步骤 |

问题池（question tracker）是各设计技能共用的提问记录：问题先入池、按轮次向用户提出、答案回填；中断后从池里恢复，不要另起炉灶。在工作流引擎的节点里，问题池由每次运行统一建好，只开放 `add_questions`、`answer_question`、`update_answer`、`get_status` 四个工具；各技能里列池、建池、重开、清空、归档的步骤在这种情况下跳过。
