# 编写 AAW 工作流

AAW 工作流是一个目录（工作流包），里面是 YAML 源码、提示词和知识文件、可选的 Python 脚本。应用里的工作流引擎把源码编译后按流程调度 Agent 节点。本技能讲怎样写对、写好；完整格式见 `references/workflow-format.md`（在 AAW Desktop 的编辑会话里，同样的内容在草稿的 `.guide/workflow-format.md`）。

## 一、先读懂再动手

- 先读 `workflow.yaml`：工作流的 id、名称、说明，以及有哪些**起点**（entries）、每个起点要用户填什么。
- 再读 `flows/` 下的流程文件：每个文件是一个流程，`entry` 是第一步，`steps` 是步骤，`next` 是路线。
- 改之前用一两句话复述现在的流程，再说要怎么改，避免改错地方。

## 二、写对

- 每个 Agent 节点都要声明 `result`（要交的结果字段）。路线的 `when` 只能引用声明过的字段；拿取值固定的字段和列表外的值比较是错误。
- 每个步骤的 `next` 最后放一条不带条件的兜底路线（通常是 `$blocked`），条件都不满足时流程才不会卡住。
- 需要用户点头才能往下走的地方，在路线上写 `confirm: must`；可选的确认写 `confirm: ask`。
- 节点会产出文件时写 `cleanup`（用户回退并选「丢弃重做」时删除哪些文件）；对外影响撤不回的节点写 `irreversible` 并写明原因。
- Python 节点的脚本放在包里，用相对路径引用。导入别人的工作流时，脚本要用户确认信任后才能运行。
- **每次改完都检查**：在 AAW Desktop 的编辑会话里调用 `check_workflow` 工具；在别处运行 `workflow_service check <工作流目录>`。没通过就按给出的文件、行号和原因修正，再检查，直到通过。不需要运行工作流本身。

## 三、写得让人读得懂

- 节点和步骤用有意义的名字；`label` 写给人看的名称；`does` 写这个节点会做的几件事，画布上会显示。
- 结果字段写 `labels`：`report: 评审报告`、`decision.revise: 需要修正`。同名字段在不同节点含义不同时（例如 `reference` 有时是需求文档、有时是设计文档），按节点分别写。
- 用 `stages` 给流程分阶段，画布按阶段分带显示。
- 提示词（`prompt`）写清这一步要做什么、交什么、什么情况下算阻塞；长的方法论放进 `knowledge/`，用 `knowledge:` 引用。

## 四、不要做的事

- 不要在定义里写具体用哪个 Agent 或模型：这些因机器而异，由用户在本机设置。
- 不要改 `.guide/`、`.draft.json` 这类以点开头的文件：它们不属于工作流。
- 不要为了让编译通过而删掉兜底路线或结果字段。
