# task-dev

## 边界

每次只处理一个 Task：调用方（工作流节点或用户）指定的那一个。详细设计是实现设计的事实来源，测试用例设计是验证规格的事实来源；`tasks-overview.md` 只管理任务范围、顺序和最终交接。

绝不执行 `git add`、`git commit`、push、发布，也不开始下一个 Task。最终只生成候选 commit message，不修改 Git 暂存区。

上下文压缩或会话恢复后，不凭记忆推断进度：重新读取 `tasks-overview.md` 的执行记录和已落盘的评审、检查报告，从实际状态继续。

## 模式判定

本 skill 支持两种输入模式，由调用方的说明决定：

- **严格模式（默认）**：完整的 SR / AR 设计链路。权威输入是模块目录下的《模块详细设计说明书》《模块测试用例设计》《模块设计门禁结果》三件套。
- **轻量模式**：个人开发者的轻量链路。调用方会说明本次为 task-dev 的【轻量模式】，或者只有 `dev-design.md` 与 `test-design.md`。此时不存在三件套，**也不要求它们**。不要因其缺失而中止或回流上游，也不要引导用户去执行 module-tobe-design / module-test-design / module-design-gate。

两种模式的事实来源对应关系：

| | 严格模式 | 轻量模式 |
|---|---|---|
| 实现设计来源 | 《模块详细设计说明书》 | `dev-design.md` 的方案与契约变更章节 |
| 验证规格来源 | 《模块测试用例设计》 | `test-design.md` 的用例集（`dev-design.md` 验收标准为需求侧口径） |
| 任务范围与交接 | 模块目录 `tasks-overview.md` | 设计文档旁的 `tasks-overview.md` |

文档位置以调用方给出的为准；没有给出时在需求工作目录中查找，找不到就问用户。

**除输入来源外，两种模式的流程、质量边界和异常处理完全一致**：仍执行语义 Review、修复重验和代码检查，仍不得执行 `git add` / `git commit`。轻量模式只是设计文档更薄，不是质量要求更低。

## 固定流程

```text
实现与测试 → 只读语义 Review → 修复与重验 → 代码检查 → 回填交接与候选提交信息
```

顺序不变，每一步都要做完再进入下一步。评审报告、检查输出随做随落盘（写在任务工作目录或调用方指定的位置），中断后能据此恢复。

两条实现期授权，防止流程压掉工程判断：

- **测试设计是下限不是上限**：实现中发现的、设计用例清单之外的值得测的面（生命周期、边界、配置归一化等），应当场补测，并在交接记录的「实现期补充与残余风险」小节逐条登记。
- **影响面不是实现方式的约束**：在不改变契约与行为的前提下，允许为清晰度优化局部组织（如为新增配置语义建立独立文件）；与设计文档的差异记入交接记录的「设计偏差」字段即可，不算偏离。

### 1. 实现与测试

1. 完整读取任务事实来源（见「模式判定」对应表），以及存在时的项目架构基线 `.sdd/software_architecture.md`、`.sdd/spec.md`、`.sdd/AICodingGuidelines.md`；严格模式另读模块设计门禁结果，轻量模式另读存在时的 `dev-design-gate.md`。
2. 确认当前 Task 是串行顺序中应执行的任务、前置 Task 已完成、设计门禁已通过，且任务中的设计与验收引用都能在权威文档中定位。存在阻塞时停止并报告。
3. 从设计来源中提取当前 Task 涉及的契约、流程、异常语义、配置、依赖边界和非功能约束；结合当前代码确定实现位置，只探索和修改当前范围。
4. 严格按已评审设计实现，不重命名契约、不丢字段、不简化流程、不改变异常语义，不提前实现后续 Task，也不做无关重构。设计与代码事实冲突时停止并回流，不得自行改设计。
5. 从验证规格（`tasks-overview.md` 中本任务圈定的用例 ID 定义当前验证范围）中定位当前 Task 负责的全部用例和覆盖目标，将前置条件、输入、步骤、预期结果、断言和后置条件落实为自动化测试。项目没有测试框架或用例确实无法自动化时，提供可执行的手动验证步骤。
6. 当前 Task 的核心验证不得待处理。只有补充性验证才可待处理，并且必须明确依赖、当前不能执行的原因和最终责任 Task。
7. 执行当前 Task 的全部非待处理测试，逐项核对预期结果。测试失败时优先修复实现；确认测试设计存在冲突时停止并回流，不得修改测试迁就错误实现。
8. 根据项目实际情况执行与实现正确性直接相关的构建、编译或类型检查。行长、方法长度、参数数量等确定性规则留给后面的代码检查。
9. 清理测试数据并恢复测试环境。实现或测试发生修改后，重新执行受影响测试和必要的构建检查。

### 2. 语义 Review（只读）

读取 [semantic-review-prompt.md](references/semantic-review-prompt.md) 和 [review-report.schema.json](references/review-report.schema.json)。并行启动两个只读 subAgent（宿主不支持 subAgent 时，主 Agent 分两遍、按两个角色各自只读审查）：

- Reviewer A：需求一致性、正确性、安全、升级兼容性；
- Reviewer B：性能、结构、可读性、扩展性和过度设计。

Reviewer 只审不改，且不重复代码检查的行长、方法长度、参数数量、宽泛异常捕获等确定性规则。向 Reviewer 只提供当前 Task、diff/变更文件、权威文档路径、软件架构、Spec、输出路径，以及 `.sdd/AICodingGuidelines.md` 中 `## task-dev 语义 Review 扩展规则` 一节的规则（存在时）。

`.sdd/AICodingGuidelines.md` 只有该章节属于本机制；其他章节不得读取为 task-dev 流程指令。扩展规则只追加 Review 检查项，不能改变流程或降低基线。

Review 只形成报告，不修改代码。主 Agent 合并、去重并裁决两份报告。无 finding 时结论为通过；有 finding 时 finding 保持 open，由下一步闭环，不得回改 Review 报告冒充 Reviewer 审查过修复后的代码。

### 3. 修复与重验

主 Agent 独占代码修改。处理成立的 finding；拒绝 finding 时记录依据。修改后执行受影响测试和必要构建。高风险或涉及结构、控制流、异常语义、API/Schema 兼容性的修改，交给原 Reviewer 定向复核，并记录复核结论。每条 open finding 都必须有归宿（已修复或已拒绝并附依据）。

### 4. 代码检查

有可用的代码检查 skill（如 `code-check`）或项目自带的 lint、格式化、类型检查时，执行它们并保留原始输出；没有时，逐个审读本次改动的文件做一次自检（命名与风格、错误与边界、遗留调试代码、与设计的一致性）。不要因为缺少某个工具而停下，也不要伪造工具输出。

可以直接修复明确、局部且低风险的问题。发生代码修改后，执行受影响测试。修复涉及业务行为、公共接口、数据兼容、安全边界、已评审设计、跨模块大改或方案取舍时，停止并请求用户决策。

### 5. 回填交接与候选提交信息

在 `tasks-overview.md` 的 `## 执行记录` 中写入当前 Task 的最终交接：状态（Completed）、修改文件、核心实现、设计偏差、待处理项、后续须知和证据引用（评审报告、检查输出的位置），以及必填小节 **「实现期补充与残余风险」**——补测了哪些设计用例清单之外的测试（一句话一条）、交卷时还有什么没把握（一句话一条，确无则写"无"）。该小节的内容也要在最终报告中向用户呈现。不要写阶段勾选或完整日志。

候选提交信息必须从当前 Task 的需求目标、已评审设计、实际实现和验证结果出发组织；没有仓库规范时使用 `<type>(T[N]): <简明变更摘要>`。随后检查 working-tree diff，仅用于确认信息中的范围和事实与代码一致、没有遗漏，不能只根据 diff 反推提交意图。

最后把结果交给调用方：在工作流节点里，按节点声明的结果字段提交（实现与测试结论、评审结论与 finding 归宿、代码检查方式与结论、候选提交信息、交接记录位置）；单独使用时，直接向用户报告这些内容。

## 交付前自检

- [ ] 只实现了当前 Task，没有提前做后续 Task，没有无关重构。
- [ ] 当前 Task 负责的用例全部落为测试并执行通过；核心验证没有待处理。
- [ ] 两路语义 Review 已完成，每条 finding 都有归宿。
- [ ] 代码检查已执行，并写明用了什么方式。
- [ ] 交接记录写全，含「实现期补充与残余风险」小节。
- [ ] 候选提交信息与实际变更一致；没有执行 `git add` / `git commit`。

## 异常处理

- 设计、测试设计与代码事实冲突：停止并回流，说明冲突点，不自行改设计或改测试迁就实现。
- Review 扩展章节格式无效：停止 Review，请用户修正后再继续；不得静默忽略。
- 默认工作区在开始时干净；检测到初始变更时只警告其可能混入当前 Task，不强制清理。
- 执行期间发生 commit 或暂存区变化：继续以开始时的工作树为基线计算变更范围。
- 流程外的代码变动不做防护与回退：若其影响真实存在，会在后续开发、测试或人工 review 中暴露；不要为此重做已完成的阶段。
