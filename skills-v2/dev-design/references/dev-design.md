# {需求名称} · dev 设计

## 1. 需求

### 1.1 目标
要达成的业务/功能目标，可验证。

### 1.2 范围边界
明确做什么、不做什么、延期项。从需求的原始文字取，不加工不扩充。

## 2. 现状摘要（可选）

> 几句话概括现状核心结论：现有实现怎么满足（或不满足）本次需求、关键改造点在哪、有无架构基线。此为方案推理的起点；全量取证细节不集中堆放，引用内联在第 3-5 节用到它的位置。

改动完全不涉及现有代码时可省略本节。若无 `.sdd/software_architecture.md` 且涉及代码改动，在此写明"无架构基线，探索边界由需求文本与代码结构推断"。

## 3. 方案

选定的整体方案与理由，承接上一节的现状推导。存在备选方案时写明权衡与选择结论，不写"待定"。关于现有代码的论断在句中直接带 `file:line` 引用。

- 方案：……
- 备选考虑：…… / 未采纳原因

### 3.1 关键流程/状态变化
改动发生处的处理流程或状态流转说明。

## 4. 契约变更

新增/修改的每一项，下游 task-dev 直接照此实现。逐项写全：名称、位置、签名/字段、类型、调用方、错误语义、兼容策略；"位置""调用方"等现状论断带 `file:line`。没有则不写"无"，直接省略一节。

- 接口 / 函数：……
- 数据结构 / DTO / 配置项：……
- 错误码 / 异常语义：……
- 兼容 / 灰度 / 回退：……

## 5. 影响面

列出实际要修改的文件路径，逐文件一行；每项标注改动性质（新增/修改/删除）。路径须经取证确认，不写猜测路径；必要时附一句取证依据（`file:line`）。

- `path/to/file.py` —— 修改：……

- [ ] 验收 3

## 7. 存疑
